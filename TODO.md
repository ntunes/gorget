  Because the call site at stage1.c:295180 does NOT include a `SpannedType__clone` call. The unwrap path SKIPPED the clone (likely because `resource_meta_for("SpannedType")` returned None — it's a user struct, not a runtime resource).   But the caller of `type_mentions_iter(ta)` IS `type_mentions_iter(targs.get(i).unwrap())` — `targs.get(i).unwrap()` produces an `Option[SpannedType]` whose `Some_0` payload was byte-copied from `targs[i]`. That Option is materialised on the stack (`__s40` / `__s67` at stage1.c:295474/295499) via `memcpy`. Then the body reads `Some_0` and passes it to the recursive call. **The byte-copy is fine** until somewhere a drop fires on `targs[i]` or its parent struct, invalidating the in-flight Option's payload pointers. The drop site is in **the outer `loader___function_mentions_iter` or `loader___ast_mentions_std_iter_need`** which COMMIT 3 made emit a `<Type>__drop` at scope exit on their owned `SpannedFunction` / `SpannedAST` locals — those recursive drops walk INTO the type's String/Vector fields and free them while the recursive `type_mentions_iter` is still iterating over the same data.

  **Root cause**: COMMIT 3's drops fire **at scope-exit-of-the-current-function** (the LIFO walk at `pop_drop_scope`), but the local being dropped may be a **caller-supplied by-value struct param** whose data is shared with the caller's still-live aggregate. Function entry registers `!arg` params for drop (`lower.gg:5821-5833`), but the same shape applies to bare-by-value resource-aggregate params: the callee got a byte-copy, doesn't own the contained heap, but COMMIT 3 still walks the recursive struct drop into the contained fields when it fires. Or — more directly — a SVarDecl bound to a function-call result like `SpannedFunction f = parse_function(...)` is registered LoOwned and gets dropped at scope exit. The dropping function walks into the SpannedFunction's String/Vector fields and frees them; in the meantime, a sibling/recursive call is still walking `f.body` and the String data is gone.

  **Two failure classes to address before COMMIT 3 ships safely**:

  1. **Param-aliasing for bare-by-value resource params.** The Prereq B fix only covers SVarDecl init from EFieldAccess / collection-getter calls. It does NOT cover the case where a function takes a `T` (bare resource) param and the caller passes by value — the param's contents are a byte-copy alias of the caller's data. If the param is registered for drop (currently only `!arg`, not bare), it would double-free. If the param is NOT registered (current state), but the param is used to bind a local that IS registered (`SpannedType ta = self.ty` where `ta` ends up LoOwned because `self.ty` is read via field-access), the chain of byte-copies can leave a registered LoOwned local pointing at heap the caller will free. The actual class is broader: **any heap data accessed through a chain of by-value struct copies aliases the original heap**, and drop emission must either trace the chain to skip aliased locals (impractical without type-flow analysis) or emit a clone at the binding site that converts the alias to ownership (architectural fix).

  2. **Recursive `<Type>__drop` semantics**. The auto-generated `<Type>__drop` walks ALL resource-typed fields and calls their drop. For a struct like `SpannedType { Span span; Type ty; }` where `Type` is an enum containing `TNamed(String, Vector[SpannedType])`, the drop recursively walks into String + Vector + the recursive SpannedType inside. Combined with the param-aliasing class, dropping a function's owned `SpannedType` local in the middle of a recursive walk over the SAME data (`type_mentions_iter(ta)` where `ta` aliases the parent's data) frees data the iteration is still reading.

- **🆕🐛 [MED — `@derive(Equatable)` ON A GENERIC STRUCT DOES NOT REQUIRE ITS PARAMETER TO BE `Equatable`, so `Pair[NonEquatable] == Pair[NonEquatable]` slips through D46's gate and answers address identity. Filed by R49 Track F-G, which took the exemption deliberately.] The one corner D46's equality gate leaves open.**
  - **MEASURED at HEAD, and the pair is the whole finding.**
    - `@derive(Equatable) struct Pair[T]` + `Pair[Point] == Pair[Point]` where `Point` has no `Equatable` → **`gg check` rc 0**, and the comparison answers by address identity. The derive registered an `Equatable` impl for `Pair`, so the gate sees an impl and stops; nothing ever asks whether `T` can be compared.
    - `@derive(Equatable) struct Pair[Equatable T]` + the same comparison → **`error[E_UnsatisfiedTraitBound]: type `Point` does not satisfy trait bound `T is Equatable``**. ⭐ **The bound machinery ALREADY WORKS END TO END** — the `[Trait ParamName]` spelling parses (`src/parser/mod.rs`, "Try to parse inline trait bounds"), `extract_generic_bounds` feeds `struct_generic_bounds` (`src/semantic/resolve.rs`), and the checker consults it. Nothing is missing except the derive's own declaration of intent.
  - ⇒ **THE FIX IS NOT NEW MACHINERY: `@derive(Equatable)` should IMPLY `Equatable` on every type parameter the generated body compares** — i.e. expansion records the bound it already depends on, and the existing check does the rest. The same argument applies to `@derive(Hashable)` / `@derive(Cloneable)` and their parameters; check the sibling derives in the same pass (Core #4).
  - **THE RELATED EXEMPTION, and why it is not the same defect.** D46's gate exempts a BARE generic parameter (`ResolvedType::Defined` whose `DefKind` is `GenericParam`) — so `bool same[T](T a, T b): a == b` called at `same[Point]` is also accepted. Gating there without the bound does not buy the catch: it would reject on `T` blindly, refusing `same[int]` identically, which is a judgement about nothing. And the neighbouring surface is ungated for EVERY operator — `T + T` inside a generic function is rc 0 at HEAD too — so this is one corner of a pre-existing class-wide gap, not a new one. Pinned as an ACCEPT by `d46_eq_generic_param_exempt` (`tests/fixtures/d46_equality/accept_eq_generic_param.gg`) so a later tightening has to face it deliberately.
  - **INTENDED:** `Pair[Point] == Pair[Point]` with a non-`Equatable` `Point` is rejected, naming `Point`, whether or not the author wrote the bound by hand.

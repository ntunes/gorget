- **🆕🧹 [LOW — A ROW THAT HAS TWICE MEASURED CLEAN AND IS STILL ON THE LIST. Split out of the `--bless` track so that deferred work does not live in a closed item's prose.]**

  `dict_iter_enumerate`'s row in `tests/sanitize/LEAK_ALLOWLIST.txt` admits two classes. It has now come back with **no leak record of any class**, `MEASURED`, in two independent targeted sweeps — the scout's, and again in the sweep that exercised the write-back apparatus. The sweep's own advisory names it under *"no longer leaking — DELETE these rows"*, and `new_class` was empty for it both times, which is the corroborating precondition the sweep's header asks for.

  **WHY IT WAS NOT RETIRED WHEN IT WAS MEASURED.** Both runs were `FIXLIST` sweeps over a few dozen fixtures, not the corpus. That is a real limitation and not a formality:

  - ⚠ **The instrument cannot tell a fixed leak from a RENAMED FRAME.** A class key is a stack frame name, so extracting a `static inline` helper makes the old key vanish while the leak is untouched — this tree has a measured instance of exactly that (`[[t1360]]` is the sibling defect; the allowlist header carries the `__gorget_array_reserve_one` war story). A rename normally also trips `❌ NEW LEAK CLASS` under the new name, but not if the renamed class happens to be tolerated already at the resulting count.
  - ⚠ **A retirement moves SHARED COUNTERS.** Removing the row moves `LEAK_CEILING`, `LEAK_CLASS_PAIRS` and `LEAK_RECORDS`, and — because the row is uncited — `UNCITED_LEAK_CLASS_PAIRS` as well. The last of those is `bless = never` and needs a hand edit with a justification, plus a re-check of the two `todo/` waivers keyed to its digits in `scripts/figures.db` (measured: moving that pin reds `python3 scripts/figures.py scan` on three declarations until they are re-seeded).

  **INTENDED, and it is now cheap because the apparatus exists:**

  1. Run a full sweep at HEAD, allowlist unedited — `bash scripts/sanitize_sweep.sh` publishes its verdict automatically, with provenance.
  2. Confirm the stem is in `[fixed_leak]` and absent from `[new_class]` in that verdict.
  3. Delete the row, then `python3 scripts/bless_leak_allowlist.py --apply`. It adjudicates the deletion against that verdict and rewrites the three blessable pins in **both** `tests/lints.rs` and `scripts/figures.db`; it will refuse if the corpus-wide verdict does not in fact name the row, which is the whole point of waiting for one.
  4. Hand-edit `UNCITED_LEAK_CLASS_PAIRS` — the tool names it and exits non-zero rather than reporting success — and write the re-seed narrative above the constants, which the tool deliberately does not fabricate.

  ⚠ **DO NOT delete the row on a targeted sweep's say-so.** That is precisely the shape `[[t1360]]` was filed against: the sweep cannot distinguish *"no longer leaks"* from *"never ran"*, and the three-state sort protects the second case only for rows the run actually reached.

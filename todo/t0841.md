- **THE MECHANISM, AND WHY IT IS ITS OWN DEFECT.** The comprehension body `s` does not mention the loop variable, so it is evaluated to the SAME `String` three times and three ALIASES of one heap buffer land in the vector. Each is live past the push (`s` is still in scope), so the compiler contract says CLONE: `AGENTS.md` § "Ownership at Consuming Positions" — *"Borrow, OR owned but live past this call → clone before call"*, and a comprehension's accumulate is a consuming position exactly like `push`. Freeing the array then frees one buffer three times. ⚠ The payload must be **heap-forced** (`mk("a","b")`, not a literal) or the double free is invisible.

- **⚠ WHAT DISCRIMINATES IT FROM THE FILED COMPREHENSION FAMILY — read this before merging it into `t0003`.** `t0003`'s axis is the ACCUMULATOR'S ELEMENT TYPE: the result element minted from the source element's size/destructor, whose recorded symptoms are *"result is a RESOURCE → ICE before codegen"* and *"result SMALLER → crash"*. Here nothing is mis-minted — the element type is right, the values are right, and the program would print the correct answer if it did not free three times. **The axis is ALIASING OF THE BODY VALUE, not minting of the element**, and it is visible only when the body is loop-INVARIANT. `t0002`'s *"COMPREHENSION-built vector … DOUBLE-FREES at run (rc 134)"* is about `unwrap()` on the read side, not about the build.

- **🆕🧹 [MED — LATENT SILENT-DISAGREEMENT SOURCE, no live defect known; found 2026-07-27 while root-causing the Family-1 auto-propagate family] `resolve_tuple_field_type` returns `I64_TYPE` on a MISS, not `None` (`src/ir/lowering/exprs/type_reg.rs`).** A caller that wants "the type, or nothing" gets a plausible WRONG answer instead of an unknown, and no fail-safe downstream can distinguish the two. Concretely dangerous for any predicate whose `None` branch is the safe one: a bogus `I64_TYPE` reads as "not a propagating `Result`", which is exactly the answer that licenses skipping `maybe_auto_propagate`. **Avoided rather than fixed for now:** `place_expr_type_only`'s `TupleFieldAccess` arm does the struct-field lookup INLINE and returns `None` on a miss, precisely so that `None` keeps meaning UNKNOWN there — see its comment. The fallback stays because `resolve_tuple_field_type`'s other callers (`patterns.rs`, the tuple-field read arm) want a type unconditionally. **Reference-grade shape: split it** — a `try_resolve_tuple_field_type -> Option<TypeId>` core plus a thin `resolve_tuple_field_type` that applies the `I64_TYPE` default for callers that genuinely want it — so no future caller silently inherits a wrong type. Audit the existing callers when doing so; the fallback's own comment records a past mis-typing bug it was added to paper over, which suggests at least one of them would rather have the `Option`. ⚠ **NAME THE WHOLE FAMILY, not this one function (Core #15e Q3):** `infer_collection_element_type` has the IDENTICAL shape — its own doc says "or `I64_TYPE` if unknown" — and `place_expr_type_only`'s `Index` arm calls it one line below the `TupleFieldAccess` arm that was hardened against exactly this. That arm is reachable today only via `Deque` (separately broken upstream, its own filing), so no live defect is claimed — but the two are one class and should be split together, along with any other `-> TypeId`-with-a-default helper feeding a predicate whose `None` branch is the safe one.

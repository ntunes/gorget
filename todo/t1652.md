  - ⚠ **ARCHITECTURE IS THE DISCRIMINATOR, AND IT IS WHY THIS SAT UNSEEN.** Measured GREEN — correct output, rc 0, ASan-clean — on macOS/aarch64 AND on linux/aarch64 in the same container image. Measured rc 139 on linux/amd64. AArch64 returns a large struct through the **dedicated** `x8` register, so a sret pointer does not displace `x0`/`x1`; SysV x86_64 passes it in **`RDI`**, displacing every declared argument by one slot. A dev box that is not x86_64 cannot see this class at all.
  - **MECHANISM — the emitted C states it in two lines.** From `void_map`, the `Callable[void(String)]` parameter's call site:
    ```c
    __v28 = ((Str(*)(void*, void*))(((void**)__v26)[0]))(((void**)__v26)[1], __v27);
    ```
    and the adapter it actually reaches:
    ```c
    void __adapt_shout(void* __env, void* __p0) { shout(__p0); }
    ```
    The pointer is cast to return `Str` (32 bytes, MEMORY class); the callee returns `void`. The caller therefore passes `(sret, env, arg)` and the callee reads `(env=sret, __p0=env)`. The environment of a top-level-function adapter is `NULL`, so `shout` receives `NULL`, `mk` dereferences it, and the program dies in the runtime rather than in the mistyped frame. **`__p0` arriving NULL is the shift's signature**: the call site passes `__v27 = &__s15`, which is never NULL.
  - **WHERE THE `Str` COMES FROM, AND WHY IT DISAGREES WITH THE SLOT IT FEEDS.** Two decisions in one lowering disagree: the fn-pointer cast takes the receiver's payload type (`Str`), while the result slot is built as `__gg_Option__int64_t` and copied `sizeof(int64_t)` — `infer_closure_return_type`'s last-resort `I64_TYPE` (`src/ir/lowering/exprs/methods.rs:4808`). Both are downstream of `callable_param_return_type` (`src/ir/lowering/exprs/methods.rs:4746`) **deliberately returning `None` for a recovered `unit`** (`:4773-4776`); each caller then falls through to its own unrelated default. Regenerate: `grep -n 'fn callable_param_return_type\|I64_TYPE$' src/ir/lowering/exprs/methods.rs`.
  - ⭐ **THE WRITE SITE, LOCATED (Core #1).** `call_closure_in_adapter`, the `Callable`-PARAMETER fallback arm:
    ```
    grep -n 'let ret_type = callable_param_return_type' src/ir/lowering/exprs/methods.rs
    ```
    ```rust
    let ret_type = callable_param_return_type(ctx, closure_op).unwrap_or(fallback_ret_type);
    let dst = ctx.call_indirect_tracked(builder, IndirectCallee::Value { .. }, final_args, ret_type);
    ```

    `callable_param_return_type` answers `None` for a recovered `unit` BY DESIGN (`:4773-4776`), so `ret_type` becomes `fallback_ret_type` — which this arm's own comment names as RECEIVER-derived (`some_ok_type` for `map`). That is the `Str` in the cast. **The arm's comment states the invariant this breaks in the same breath**: *"so the slot's TYPE and the indirect call's CAST are always the same fact"* — under a `unit` return they are two different facts, and neither is the callee's.
  - ⊕ **THE CORRECT SHAPE IS ALREADY WRITTEN ONE SCREEN UP, IN THIS SAME FUNCTION.** The closure-TYPE arm (`ctx.closure_call_fn_for_type` path) reads the real signature and does:
    ```rust
    if ret_type == UNIT_TYPE { builder.call_void(&call_fn, final_args); return Operand::Constant(Constant::Unit); }
    ```
    The `CallableParam` arm has no such branch. **This is Core #4's shape exactly** — one position of an enumerated set handles `unit`, its sibling does not — so the fix is the class (every arm that builds an indirect-call cast reads the CALLEE's signature, `unit` included), not this one call.
  - ⚠ **AND THE SAME `None` POISONS THE OTHER READER, WHICH IS WHY THE TWO TYPES DISAGREE.** `infer_closure_return_type` (reader 1, sizes the result SLOT) also loses the `unit` and falls through to its `I64_TYPE` last resort, so `result_type` takes the `mapped_ret != some_ok_type && != UNIT_TYPE` branch and mints `Option__int64_t` instead of the `recv_type` the `UNIT_TYPE` branch would have given it. **Restoring the truth at `callable_param_return_type` fixes both readers at once — but it is exactly the edit whose FIRST draft measured rc 139 on both backends** (the fixture's own header records it), because the callers then have to decide what a void `map` EVALUATES to. That half is `[[t0729]]`'s open owner question. The ABI half is not, and a `call_void` in the `CallableParam` arm settles it without touching the other.

  - ⭐ **THE ABI HALF IS NOT THE OPEN SEMANTICS QUESTION, AND MUST NOT WAIT ON IT.** `[[t0729]]` leaves *"what the result TYPE of a void `map` should be"* OPEN and unprescribed, and says so as an owner-level call. **Calling a `void` function through a `Str`-returning function pointer is undefined behaviour under EVERY answer to that question**, including the ratified-today one (`callable_param_return_type`'s own comment: a void `map` *"runs `f` for its effect and keeps the receiver's payload type"*). Whatever the result type ends up being, the CALL must be emitted with the callee's real signature and the result synthesized rather than read out of a register that holds nothing.

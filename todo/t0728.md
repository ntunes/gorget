- **[MED — A NAME MATCH OUTRANKS THE USER'S TYPED DECLARATION: an `extern` bound to `malloc`/`calloc`/`realloc` has its declared return type silently overridden, and the LLVM lane then emits invalid IR. Found 2026-08-29 by the R47 Track C scout, mechanism established by the executor.]**
  - **REPRODUCED AT HEAD.** `extern int c_malloc(int n) = "malloc"` + `if p != 0:` → `gg build --backend=llvm` fails with
    ```
    llc: error: '%v4' defined with type 'i64' but expected 'ptr'
      %v5 = icmp ne ptr %v1, %v4
    ```
    The C lane builds the same source and prints `nonzero`. Repro: `tests/fixtures/known_gaps/llvm_extern_allocator_name_overrides_declared_return_type.gg`, wired `#[ignore]`d as `llvm_extern_allocator_respects_declared_return_type` (`tests/integration.rs`, which pins `--backend=llvm` explicitly so it reddens regardless of `GG_BACKEND`).
  - **MECHANISM — this is a Layering-discipline rule 2 violation, not a typing bug.** `src/lir/types.rs`'s extern-return-type resolution opens with a `match name` that returns `Some(LirType::Ptr)` for `"malloc" | "calloc" | "realloc"` **before** it ever consults the extern the user registered. So the decision is made from a STRING, and the user's `int` loses to it. Isolated by axis probe rather than by reading: all three name-matched symbols fail identically, and an otherwise-identical `extern int c_abs(int n) = "abs"` builds and runs fine. The name match IS the mechanism.
  - **THE WRITE SITE IS THE FIX (Core #1).** The special case's own comment says why it exists: BIR synthesis (`src/bir/synth.rs`, e.g. the sort aux buffer) emits a raw `Inst::CallExtern { name: "malloc", … }` **without registering a matching `LirExtern`**, so the reader was left reconstructing a type from a name the writer failed to carry. Register the typed extern at the synthesis site and the read-side name match deletes itself — along with the collision with user code that happens to bind the same symbol.
  - **SEVERITY.** Build-time hard failure, not a miscompile — `llc` rejects the module, so no wrong binary ships. But it is unreachable-by-workaround for the user: nothing they can write about their own declaration changes the outcome, and the diagnostic points at emitted IR rather than at their `extern`.

- **🆕🚨 [HIGH — D46's RIDER MAKES SIX MORE AGGREGATES INTRINSICALLY COMPARABLE AND NONE OF THEM HAS A LOWERING: `Some(1) == Some(1)` prints `false`, `[1,2] == [1,2]` prints `false`, `Ok(1) == Ok(1)` prints `false`. Filed by R49 Track F-G, which shipped D46's REJECT half; this is the ACCEPT half.]**
  - **SIBLING OF `t0683`, WHICH COVERS THE TUPLE CELL ONLY.** D46 half 1 ruled tuples intrinsic; the 2026-09-04 rider extended the same rule, on the same element-comparability gate, to **`Option[T]` · `Result[T,E]` · `Vector[T]` · `Set[T]` · `Dict[K,V]` · `Array[T,N]` · `Range`**, because the rationale was always ANNOTATABILITY and every one of those is a type the user cannot annotate.   - **MEASURED at HEAD (`tests/fixtures/d46_equality/accept_eq_still_legal.gg`, run on C).** `int` / `String` / `float` / `bool` / `@derive(Equatable)` / user-`equip` all answer CORRECTLY — those are the controls, and they prove the accept path reaches a real implementation.   - **MECHANISM** (regenerate the site with `grep -n '__eq' src/ir/lowering/exprs/operators.rs`). The equality lowering dispatches by building `format!("{type_name}__eq")` and testing `fn_sigs.contains_key`, **and the whole arm is gated on `GirType::Named`** — so a tuple, an `Option`, a `Vector` never even reach it. When no such function exists there is **no structural fallback**: the lowering falls through to a raw pointer compare, which is exactly why every accepted aggregate answers address identity. The fix is the seven structural lowerings, recursive over element types, on **C + LLVM + self-host** (Core #9).
  - ⚖ **CARRIES ITS OWN UNRULED QUESTION: `Set` / `Dict` ORDER-INDEPENDENCE.** Two sets with the same members in a different insertion order must compare equal; D46 and its rider say nothing about it, and a naive element-wise walk gets it wrong. That is an owner ask, not an implementation choice.

Making these families REJECT instead would be a NEW over-reject on code that compiles today, so `d46_eq_accept_side_still_checks` pins them as accepted and deliberately asserts only that they CHECK, never what they print: pinning today's output would ratify the wrong answer.

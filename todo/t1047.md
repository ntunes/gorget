- **[MED — CLASS-RETIRING GUARD, filed 2026-09-03; the class already fired once and cost a RED CI gate for three days] Nothing asserts that `verdict.py`'s build-failure marker tables cover every build-failure message `src/main.rs` can emit.**
  - **The class, and its one measured firing.** `BUILD_DELIVER_FAIL_MARKERS` (`scripts/verdict.py`) is a tuple of stderr substrings meaning *"the compiler accepted the program and then failed to deliver a binary"*. It listed the four C-backend spellings and **none of the LLVM ones**. An unlisted spelling does not degrade gracefully: it falls through to the `build_rc1_unmarked` ambiguity cell ([[t0646]]) and the run reports UNKNOWN for a cause that is perfectly discriminable. Consequence, measured: `gg build --backend=llvm` on a program whose generated C is rejected read UNKNOWN while the identical C-lane failure read BUILD-FAIL, so five robustness-map cells diverged across lanes on nothing but the table, and CI's *"Beginner-code robustness map (C + LLVM)"* step was RED from 2026-08-31 until the table was completed. [[t0863]] filed those five cells and misread them as *"a divergence in classification GRANULARITY, not in behaviour"*; the granularity was a missing row.
  - **Why prose is not enough here (Core #6).** The table is a contract across a PROCESS boundary — this classifier reads gg's stderr, so it cannot consult typed metadata and the "put the flag on the typed declaration" fix in `AGENTS.md`'s *No name matching* section does not apply. The substring list genuinely is the interface. That makes it exactly the kind of hand-kept parallel list that section says rots, with no compiler to catch the drift.
  - **⚠ THE SIBLING DEFECT IS ALREADY FIXED, AND IS THE REASON TO DISTRUST A GREP.** `prove_exclusive`'s marker vocabulary was a SECOND hand-written copy of the same tables, sitting a few hundred lines below them; `Failed to run C compiler '`, `for linking:` and every LLVM spelling were in a table and absent from that list, so the proof never touched them and structurally could not have noticed the LLVM rows were missing. That one was retired properly — the vocabulary now DERIVES from the tables (14 → 35 markers, 19080 → 113580 tuples, 0 violations). This item is the half that could not be fixed the same way, because the other end of the link is Rust source, not a Python tuple.
  - **What the guard must do.** Assert every build-delivery failure message in `src/main.rs` matches some entry in `BUILD_DELIVER_FAIL_MARKERS` (or is explicitly exempted with a reason), and fail when a new one appears unlisted. **Q2 (`AGENTS.md`, the six questions): can the guard catch its OWN class?** A guard built as another literal grep cannot — regenerate the census with
    ```
    grep -nE '"(Guest|Host|Runtime|llc) compilation failed|"C compiler exited with|"Failed to run|"Linking failed' src/main.rs
    ```
    and note that it returns **one false positive** (`eprintln!("Failed to run tests for …")`, the `gg test` runner, not a build path). A pattern that already mis-classifies a site is not a basis for a completeness proof. Prefer a STRUCTURAL predicate — the `Err(format!(…))`/`return Err(format!(…))` sites reachable from the build entry points — over another substring list, or the guard reproduces the defect it retires.
  - **Do NOT quote a site count here.** It moves whenever anyone adds a build diagnostic; run the census. At filing the census returned 15 real sites plus the one false positive above.

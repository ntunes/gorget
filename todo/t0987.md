- **🆕🐛 [HIGH — Core #10 lower-or-reject violated by a `_ =>` FALL-THROUGH, which Core #10 names as a
  MISCOMPILE-CLASS DEFECT verbatim; both backends; ⚠ **THIS ITEM WAS FILED WITH TWO FALSE CLAIMS ON
  2026-09-03 AND IS CORRECTED HERE, same day, after the owner asked where `Vector.for_each` comes from**]
  A MISSING IMPORT turns an ordinary "no such method" into a FABRICATED RUNTIME SYMBOL.**
  - ⭐ **THE DISCRIMINATOR IS THE IMPORT — measured, three probes, one variable:**

    | program | result |
    |---|---|
    | `from std.collections import Vector` only, `v.for_each(show)` | **BUILD FAIL** — `implicit declaration of function 'gorget_array_for_each'` |
    | same, `v.for_each((int x): print(x))` | **BUILD FAIL** — identical |
    | ⭐ **`+ from std.iter import Iterable`**, `v.for_each(show)` | ✅ **builds, prints `1` / `2`, rc 0** |

  - **WHAT `for_each` ACTUALLY IS.** A **user-space** method: `lib/std/iter.gg:416-417` —
    `void for_each[F](&self, F f): self.iter().for_each[F](f)` — inside an `equip Vector` block, alongside
    `each` at `:413`. It is **documented as live** (`docs/book/19-stdlib.md:323` lists `.for_each(f)`;
    `docs/devbook/23-stdlib.md:229` and `:309`), and `typecheck.rs:9004` gives it a return type. **It is not
    a builtin and correctly has no `BuiltinMethodDecl`** — that table means *"builtin-lowered"*.
  - **MECHANISM.** With `std.iter` unimported the `equip` block is not in scope, so the method does not
    resolve. Control reaches `src/lir/lower/calls.rs:400` (orchestrator-verified):
    ```rust
    _ => return Some(format!("gorget_array_{method}")),
    ```
    which **invents a symbol name from the method name**. `gorget_array_for_each` exists **nowhere** in the
    tree. ⇒ Core #10 verbatim: *"a `_ =>` fall-through … is a miscompile-class defect"* — and here it does
    not merely discard, it emits a call to a function nobody wrote.
  - ⭐ **WHY THIS MATTERS MORE THAN THE ORIGINAL FILING SUGGESTED: a forgotten import is an ORDINARY USER
    MISTAKE.** The correct response is a resolution error naming the method — ideally *"no method
    `for_each` on `Vector[int]`; did you mean to import `std.iter`?"*. What the user gets instead is a **C
    compiler error about a symbol that does not exist**, with nothing pointing at the missing import.
  - ⛔ **TWO CLAIMS IN THE ORIGINAL FILING WERE FALSE — recorded because the correction is the useful part:**
    1. *"Fails for ANY `f` — closure or named fn"* — **FALSE.** It fails for any `f` **only when `std.iter`
       is unimported**; with the import, both spellings work.
    2. *"ZERO corpus cells use `.for_each(` or `.each(`"* — **FALSE.** Four fixtures use them, and
       **`vector_userspace_hofs.gg:58` is `v.for_each(show)` and is GREEN at HEAD**, as are
       `vector_each_userspace.gg` and `stdlib_iter_terminals.gg` (all three build and run rc 0).
       ⇒ The original *"2000+ fixtures never saw it"* reasoning was wrong: **the corpus DOES cover the
       working path, and covers only that path** — every cell imports `std.iter`. The gap is the
       **unimported** cell, which no fixture writes.
  - **SIBLING SET (Core #4) — the catch-all is the class, not the instance.** Enumerate every method that
    reaches `calls.rs:400` and give each a disposition: a real runtime symbol, an exclusion at `:356-363`,
    or a rejection. ⚠ **Every user-space `equip Vector` method has this shape**, so the sibling set is at
    least `each` · `for_each` · `any` · `all` · `find` · `find_index` · `fold` (`lib/std/iter.gg:396`'s own
    list) — **a catch-all that mints names cannot be made correct by adding one arm.**
  - **INTENDED:** an unresolved method on a builtin collection is **REJECTED at check time, naming the
    method** — never lowered to a fabricated symbol. ⊕ A *"did you mean to import `std.iter`?"* note is the
    reference-grade shape and would also serve the beginner-map corpus (`t0018`).

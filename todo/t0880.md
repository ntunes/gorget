- **🆕🐛 [MED — a stdout-invisible 5-byte leak on every `Result.unwrap_or` with a heap default; found R48 Track A while widening the `t0772` ASan net]**
  - `Result[String, String] o = Ok(mk("re", "s"))` then `o.unwrap_or(mk("no", "pe"))` leaks: `Direct leak of 5 byte(s) in 1 object(s)` from `gorget_string_copy_cow`, under `ASAN_OPTIONS=detect_leaks=1`, on the Ok path (the default is materialized and then neither consumed nor registered for drop).
  - **⭐ THE DISCRIMINATOR THAT LOCATES IT.** `Option[String] o = None()` then `o.unwrap_or(mk("no", "pe"))` is ASan-CLEAN. Same method name, same argument shape, two receivers, opposite results — so the temp IS normally registered at this argument position and the `Result` arm specifically drops it. That also rules out "the temp was never registered" as the mechanism.
  - **⚠ PRE-EXISTING AND A DIFFERENT CLASS FROM ITS NEIGHBOURS.** Measured identical before and after R48 Track A's `receiver_was_cloned` gate (`t0772`), which is about the RECEIVER's drop registration, not an ARGUMENT's. It is not `t0872` either — that one is an inline-CONSTRUCTOR receiver temp never registered on the adapter path; this argument temp's `Option` twin proves registration normally happens here.
  - **WHY THE SIBLING FIXTURE AVOIDS IT:** `tests/fixtures/security/combinator_named_receiver_no_leak.gg` deliberately spells its observations with `.unwrap()` / `unwrap_or_else` so this pre-existing leak cannot mask the signal it exists to carry.
  - **INTENDED:** prints `res`, rc 0, ASan-clean under `detect_leaks=1`, on C and LLVM. Repro `tests/fixtures/security/result_unwrap_or_heap_default_leak.gg`, wired `#[ignore]`d as `known_gap_result_unwrap_or_heap_default_leak`.

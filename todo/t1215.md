- **🆕🐛 [MED — a HOF result array minted with no element metadata on the LLVM lane, and the SAME program not linking at all on C; found 2026-09-04 by R49 Track N2 while closing the same class at the `HofExpand` write site] `v.map(f)` where `f` is a `Callable[…]` PARAMETER rather than a literal or a named callee misses the fix that closes the class everywhere else.**
  ```gorget
  Vector[String] apply_all(Vector[String] v, Callable[String(String)] f):
      return v.map(f)

  String bang(String s):
      return mk(s, "!")

  void main():
      Vector[String] v = Vector[String]()
      v.push(mk("aa", "bc"))
      Vector[String] r = apply_all(v, bang)      # LLVM: leaks. C: does not link.
  ```
  **THREE CELLS, and they are three different defects that happen to share one program.** Measured 2026-09-04, `gg build --sanitize`:

  | cell | lane | measured |
  |---|---|---|
  | `map` through an opaque `Ptr` callable | LLVM | rc 1, **6 bytes in 1 object**, `str_alloc_copy ← gorget_string_clone_to_owned` |
  | same program | C | **BUILD FAIL** — `undefined reference to 'Vector__GorgetString__map'`, surfaced as a raw `ld` error, not a `gg` diagnostic |
  | `flat_map` through an opaque `Ptr` callable | either | **not reachable** — `E_TypeMismatch: expected Pair, found String` at check time |

  ⭐ **THE ENTRY CONDITION IS THE CALLABLE'S TYPE BEING ERASED TO A BARE `Ptr`**, which is why the `HofExpand` fix does not reach it: this shape lowers to a `CallExtern`-shaped generic call, so there is no `HofExpand` instruction to carry the result element's typed metadata on. Repairing it at the fallback would be a read-site patch (Core #1) — the erasure is upstream, and repairing THAT means the fallback is never entered at all.
  ⛔ **AND THE FALLBACK IS THE LITERAL SHAPE `AGENTS.md`'s "No name matching" section FORBIDS.** It is dispatched by `parse_vector_hof`, which does `strip_prefix("Vector__")` plus a method-name match to decide what the call MEANS. Patching the hooks in there entrenches that path; the fix belongs at the erasure.
  ⚠ **THE TWO ARMS HAVE DIFFERENT DEFECT SETS — do not treat them as one row.** The `map` arm already sizes the result correctly from the adapter's return type and misses only the HOOKS. The `flat_map` arm mints from the SOURCE element (wrong size), installs no hooks, AND never frees the drained husk. A fix aimed at "the fallback" that only reads the `map` arm leaves two thirds of the `flat_map` arm open.
  ⭐ **THE C CELL IS ITS OWN DEFECT AND IS NOT COLLATERAL.** `Callable[T]` parameters are a first-class surface feature and `apply_all(v, f): return v.map(f)` is the idiomatic spelling; C is missing a monomorphization for it. Whatever the LLVM disposition, a missing mono should reach the user as a `gg` diagnostic and not as `collect2: error: ld returned 1 exit status`. **Verified pre-existing: byte-identical before and after Track N2's change.**
  **DISCRIMINATED from `todo/t0954`** (no longer open): that was the accumulator an `HofExpand` mints carrying a NULL `elem_drop`, reachable with a literal or named callee and closed by writing the element hooks through on the instruction. This one has no `HofExpand` at all — the callable's type is gone by the time the call is lowered, so there is no carrier. Same symptom, different write site, and the closed item's fix provably does not reach it.

- **🆕🐛 [LOW — DIAGNOSTIC QUALITY, pre-existing and wider than the gate that surfaced it: an error raised inside `f"{...}"` renders its caret at a FIXED END-OF-FILE position, one line past the last line of the file, with a blank excerpt. Found 2026-09-04 by R49 Track F-G while landing D46's f-string whitelist arm.]**
  - **MEASURED 2026-09-04.** A 7-line program whose only error is inside an interpolation renders its caret at `:8:1` with a BLANK excerpt line — one past the last line of the file. Padding the file moves the caret with the file's end, so it is the end-of-file position, not a constant offset from the real site. **Not introduced by D46** — the `E_NoMethodFound` control, which was already on the interpolation-retention whitelist, points at the same fictional location.
  - **WHY IT IS WORTH FIXING RATHER THAN TOLERATING.** D46's `Owed:` clause (`docs/define-gorget/decisions.md`) calls for a TEACHING diagnostic, and `f"{a == b}"` is the position a comparison is most often written. The MESSAGE teaches correctly — it names `Equatable` and suggests `@derive` — but inside an interpolation it names no location, so the reader is told what is wrong and not where. A file with several interpolations gives no way to tell which.
  - **NOT A CONFORMANCE PROBLEM.** The spectest seeds compare exit code, stdout and the `E_` code, never spans, so `reject_eq_no_equatable_in_fstring.gg` MATCHes on all four lanes today. This is purely the human-facing render.
  - **INTENDED:** the caret points at the interpolated expression, the way it does for the identical expression outside an f-string.

- **[MED — A SECOND FICTIONAL FEATURE IN THE SAME NARRATIVE `RawPtr` LIVED IN: `Sendable`/`Syncable` are documented as compile-time-enforced marker traits and the compiler has never heard of either name. Found 2026-08-30 by R47 Track D3b while deleting the `unsafe equip` block that sat inside this section; grep-before-file done.]**
  - **VERIFIED AT HEAD.** `grep -rn 'Sendable' src/ | wc -l` → **0**. Same for `Syncable`, and same across `spec/` and `lib/`. The section at `docs/language-design.md` § "Thread Safety: Sendable & Syncable" (inside `## 10. Concurrency`) states that Gorget *"uses two marker traits to enforce thread safety at compile time, similar to Rust's `Send`/`Sync`"*, describes auto-derivation over field types, and asserts *"The `thread.spawn` function has an implicit `[Sendable F]` bound, so the compiler rejects any attempt to send non-Sendable types across threads"*. **Nothing enforces any of it, because neither trait exists.**
  - **⚠ EVERY PROBE OF IT IS ACCIDENTALLY CORRECT — this is why it survived.** `equip H with Sendable: pass` → `gg check` **rc 0**; `void f[Sendable F](F x)` → **rc 0**. Both look like the feature working. They are not: the identical probes with an invented name are also rc 0 — `equip H with Zorkmid: pass` → **rc 0**, `void f[Zorkmid F](F x)` → **rc 0**. The names are accepted because an undefined type/trait name in an `equip … with` or generic-bound position is never resolved, which is **`t0038`'s** class (*"an UNDEFINED TYPE NAME is silently accepted in 9 of 10 type positions"*). So the Sendable narrative reads as verified by anyone who probes it the obvious way. Probe it at a position `t0038` does NOT cover (a local binding) and there is nothing to probe, because the traits have no values.
  - **WHAT DISCRIMINATES IT FROM ITS TWO SIBLINGS.** `t0733` is the same shape for `RawPtr[T]`/`ConstRawPtr[T]` (a documented *type* that does not exist); `t0411` is the same shape for `thread.spawn` (a documented *function* that does not exist). This entry is the *trait* member of that family, and all three sit in the SAME two-page stretch of `docs/language-design.md` — the concurrency/FFI narrative is the tree's densest concentration of documented-but-absent surface. `t0038` is the MECHANISM that hides all three from casual probing; it is not a duplicate of any of them.
  - **DISPOSITION IS AN OWNER CALL, exactly as `t0733`'s is, and for the same reason:** docs state INTENDED behaviour, so a doc-vs-code conflict here is not automatically resolved in the code's favour. Two coherent options: (a) **implement** `Sendable`/`Syncable` as real auto-derived marker traits with a bound that `thread_spawn` actually carries, or (b) **mark the section planned** and stop asserting compile-time enforcement that does not happen. Not interchangeable — (a) is a type-system feature, (b) is a paragraph.
  - ⚠ **Fixing `t0038` FIRST would turn this from a silent fiction into a loud one** — once undefined names are rejected in bound/equip positions, `equip H with Sendable` starts failing, and any user code written from this documentation breaks at that moment. Sequence accordingly: whichever of (a)/(b) is chosen should land no later than `t0038`'s fix.
  - **REGENERATE:** `grep -rn 'Sendable\|Syncable' src/ spec/ lib/ | wc -l` (expect 0) and the four rc-0 probes above (two named, two invented) — the pair is the point, not either half.

- **[MED — Layering rule 4, two sites; found while closing `t0699`] TWO consumers re-derive f-string interpolations from RAW TEXT while the parser's typed interpolation expressions sit unread beside them.** `Expr::StringLiteral(StringLiteral, Vec<Spanned<Expr>>)`'s second field is, in the AST's own words (`src/parser/ast.rs`), *"one parsed `Expr` per `StringSegment::Interpolation`, in order — populated by the parser for `Format`-kind strings **so that semantic passes (resolution, typecheck, method-mangling rewriter) process the interpolation expressions naturally**"*. Two consumers ignore it:
  - **`src/semantic/safety/check_expr.rs`, the `Expr::StringLiteral` arm.** It calls `crate::parser::Parser::new(var_name).parse_expr()` per segment and then `check_interpolation_expr(&parsed, expr.span)` — re-parsing the raw text and passing the *f-string's* span for error reporting *"since the re-parsed expression has synthetic spans"*, which is the comment conceding the defect. Consequence: every borrow-check diagnostic raised inside an interpolation points at the whole f-string instead of the offending sub-expression, and every span-keyed side table the borrow checker consults (`expr_types`, `method_resolutions`, `resolution_map`) misses on those nodes because the typechecker populated them for the REAL nodes, not the re-parsed copies.
  - **`src/parser/visitor.rs`, `walk_expr`'s `Expr::StringLiteral(s, _)` arm.** It fabricates a `Spanned { node: Expr::Identifier(name.clone()), span: Span::dummy() }` per segment and visits *that*, so every `ExprVisitor` in the tree sees a dummy identifier where an expression is. Its own comment says *"visitors needing precise interpolation spans should override"* — i.e. the walker under-approximates by construction and each consumer is expected to notice. (`visit_expr_children` at the bottom of the same file gets it RIGHT: it walks `interps`. The two helpers in one file disagree.)
- **MEASURED, and it was a memory-safety hole until 2026-08-29.** The CoW prescan walks the TYPED interpolation expressions; the safety pass classified only the re-parsed copies. So the receiver-mutation write-through had a hole exactly the width of an f-string, and a user `&self` mutator called from an interpolation (`print(f"{h.grow()}")`, with a reallocating push) was rc 139 on both backends — `t0699` in a different costume. Closed for THIS axis by classifying the typed field in the `StringLiteral` arm; the underlying re-parse is untouched and every other axis that flows through it is still on synthetic spans. Instrument that found it: `GG_REPORT_RECV_MUT=1 gg build F` prints one `[recv-mut-miss] <name>` per prescan query with no semantic answer.
- **Fix:** walk `interpolations` with `check_expr` and delete the re-parse (keeping the raw-text path only for the empty-`parts` case — non-format literals and lowering-synthesized ones); fix `walk_expr`'s arm to descend into the typed field like `visit_expr_children` does. Both are behaviour-affecting (real spans change which diagnostics fire and where, and `walk_expr` feeds closure-capture and return-borrow analyses), so each wants its own measured landing, not a drive-by.
- **Guard when it lands:** a diagnostics fixture asserting a borrow error inside an interpolation is reported at the SUB-EXPRESSION's span, plus a lint asserting `Expr::StringLiteral(_, _)` has no `parse_expr()` re-parse consumer left.

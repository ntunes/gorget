- **[MED — a documented suspension point is not one under `scheduler=single`] Under `directive scheduler=single` (the N:1 cooperative event loop), `sleep` does NOT run other tasks; a pending spawned task stays pending across the whole sleep and only runs at the next `await`.** `docs/book/14-concurrency.md` states the model without qualification: *"tasks run cooperatively, and a task yields control at explicit suspension points: `await`, `sleep`, blocking I/O. At each such point, the runtime releases all held locks, **runs other tasks**, then reacquires the locks on resumption."* One of the four shipped scheduler backends does not honour it for `sleep`. **MEASURED at HEAD `176909d8` with one pinned release binary, 40 runs at parallelism 4 per cell, every cell 40/40 identical (a property, not a race)** — program: `spawn worker(&x)`, `sleep(0.1)`, print, `with x: print(x)`, `t.await()`, `print(x)`:
  - `scheduler=pool`, both lanes → `worker runs | after sleep | 1 | 1` (documented behaviour: the worker runs during the sleep)
  - `scheduler=single`, Rust lane → `after sleep | 0 | worker runs | 1`
  - `scheduler=single`, self-host lane → `after sleep | 0 | worker runs | 1`
  Both lanes agree because the scheduler runtime is shared C (`src/backend/c/runtime`, selected by `SchedulerMode` — `src/ir/mod.rs`), so this is a RUNTIME defect and there is no lane divergence to reconcile (Core #9 satisfied by the shared root, not by a promise). **Why it matters beyond tidiness:** a program that sleeps while waiting for a spawned task to make progress cannot make that progress under `single` — that is a livelock shape, not a scheduling preference — and `single` is the mode eleven fixtures select precisely to get deterministic interleaving. **Durable repro:** `tests/fixtures/known_gaps/sched_single_sleep_does_not_yield.gg`, wired as the `#[ignore]`d `sched_single_sleep_does_not_yield` in `tests/integration.rs` asserting the INTENDED (book-documented, pool-matching) output `worker runs\nafter sleep\n1\n1`; RED at HEAD by construction. **Fix = drain the ready queue at a `sleep` in the N:1 loop** (the loop already drains at `await`), then un-ignore the test and promote the fixture out of `known_gaps/`. ⚠ **BLAST RADIUS — 11 fixtures declare `scheduler=single`, but only TWO call `sleep()`** and can therefore be affected: `shared_with_check_then_act` and `shared_stale_blocking` (`grep -n "sleep(" tests/fixtures/shared_stale_*.gg tests/fixtures/shared_with_check_then_act.gg` → exactly those two; the other three that merely IMPORT `sleep` never call it). Both are stdout-pinned AND byte-compared by `self_host_runtime` and `self_host_runtime_diff`, and **both are unaffected — verifiable by inspection, not merely reasoned**: in `shared_with_check_then_act` the worker runs after the `if x == 0` check under either ordering, so all three lines are identical; in `shared_stale_blocking` the branch reads `int val = x` captured BEFORE the sleep, so the ordering cannot change it, and the trailing `print(x)` is `1` either way. Still re-run both when the fix lands — inspection is cheaper than a sweep, not a substitute for one. ⊕ **Possible OWNER question rather than a bug** if the N:1 loop's `sleep` is deliberately a thread-blocking sleep: then the BOOK is what needs correcting, and the doc must say which suspension points each backend honours. The asymmetry is currently undocumented either way.

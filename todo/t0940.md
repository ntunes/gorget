- **🆕🐛 [MED — Core #10 SILENT DROP: `gg check` ACCEPTS, the C build dies] `Guard[T].clone()` lowers to a call on `gorget_guard_clone`, a symbol that does not exist.**
  ```
  Mutex[int] m = Mutex[int](1)
  Guard[int] g = m.lock()
  Guard[int] g2 = g.clone()
  ```
  → `gg check`: `OK: no semantic errors`; C compile: `error: implicit declaration of function 'gorget_guard_clone'; did you mean 'gorget_map_clone'?` and `incompatible types when assigning to type 'Guard__int64_t'`.
  **`Guard` is registered with `clone_fn: None`** (`src/ir/lowering/builtins.rs:695`) — it is one of the four genuinely clone-less builtins alongside `Mutex` (`:674`), `RWLock` (`:724`) and `TaskGroup` (`:1074`). So the lowering had the typed metadata saying "no clone path" and manufactured a runtime symbol name anyway. **Core #10 (lower-or-reject): the arm must emit a check-time rejection.** Fixing it at the diagnostic layer is not enough — the acceptance happens before any diagnostic is chosen.
  ⚠ **THE PREDICATE ALREADY EXISTS AND IS NOT CONSULTED HERE.** `clone_fn` presence is the typed answer to "does this type have a clone path"; a `.clone()` arm that does not read it is Layering rule 2 (typed metadata, not name-matching / convention). ⊕ Related but NOT the same: `t0936` is the inverse — a type that HAS a `clone_fn` whose value form never reaches it.
  ⛔ **Do not generalise from this to "the carve-out set has no clone path"** — that claim is FALSE and cost this round two wrong framings. The set SPLITS: `Box`, `Task`, `Owned` have no `BuiltinTypeProtocol` row at all yet `b.clone()` builds and runs correctly; `Callable`/`MutCallable` have a real `clone_fn`; only the four above are clone-less.

- **🆕🐛 [MED — a LEAK from ordinary safe syntax, both backends, `gg check` clean; and the code comment that licenses it asserts an invariant this repro FALSIFIES (Core #14); found 2026-09-02 by R48 Track R's executor while ASan-attributing `t0936`'s fixtures] A `Callable` stored in a STRUCT FIELD leaks its captured environment.**
  ```gorget
  struct Holder:
      Callable[int(int)] f

  int base = 40
  Callable[int(int)] c = (int x): x + base
  Holder h = Holder(^c)          # 16 bytes leaked at exit
  ```
  `gg build --emit-gir` prints `type Holder = struct { f: fn(i64) -> i64 } [drop: None, copy: Copy]`, so nothing ever calls `gorget_closure_free` on the field. Measured with a **heap-forced** value (the closure CAPTURES `base`, so the env is a real malloc rather than the 0-byte placeholder a non-capturing closure gets): ASan reports `16 byte(s) leaked in 1 allocation(s)`, top frame `__gorget_closure_env_alloc`.
  **THE WRITE SITE** is `field_is_transitively_droppable` (`src/ir/types.rs:527-546`), which deliberately excludes bare `GirType::FnPtr` fields to stay in lockstep with `upgrade_types_from_fields` — the post-hoc writer-side authority on transitive drop. The exclusion is defended by an invariant in its own doc-comment:
  > "(See `closures.rs` for closure layout: captures use `MutPtr(T)` / value fields, never `FnPtr`-as-field. The `Callable[T()]` local case where FnPtr DOES own a heap env is a function-body local, not a struct field.)"
  ⭐ **THAT INVARIANT IS FALSE.** It is true of COMPILER-SYNTHESIZED closure-env structs; it says nothing about a USER-DECLARED struct with a `Callable` field, which is ordinary safe syntax and puts an owning `FnPtr` in exactly the position the comment says cannot exist. **Core #14: an invariant-asserting comment with no enforcing guard.** Whatever the fix, that parenthesis must be corrected or deleted — it is what a future reader will use to justify leaving the hole open.
  ⚠ **Both writers must move together, or they desynchronise** — the predicate and `upgrade_types_from_fields` are deliberately in lockstep, and changing one alone reintroduces the coherence split Tier 1c exists to close. Expect a real blast radius: flipping FnPtr to droppable changes the drop strategy of every struct with a Callable field, and vtable-entry `FnPtr` fields must stay excluded (they own nothing).

Different write site, different predicate, and fixing either leaves the other leaking. **DISCRIMINATED from `t0939`**: that is the struct-field CALL `s.f(1)` failing to LINK; this fixture reads the field through `.clone()` precisely so the link failure does not mask the leak. **NOT `t0936`**: the clone route is ASan-clean in isolation, measured.

- **🆕📐 [LOW — DOC FRAMING ON AN UNRATIFIED POSITION; surfaced 2026-09-05 by the R50 Track C2 construct-scoped doc scan]** The "read-only borrow" label on a collection-element READ is loose in exactly the way the bare `for`-element label was, and the ledger has not ruled on it.

  `docs/book/12-borrowing.md` (§"Collection Element Borrowing") — *"Reading an element from a collection returns a **read-only borrow**"* — and `docs/language-reference.md` §9.6 — *"**Collection `.get()` returns a read-only borrow.**"* — describe the same position.

  **Measured** (`String x = v.get(0).unwrap()` then `x = "zz"` on a `Vector[String]`): the write is **ACCEPTED**, `x` prints `zz`, and the collection still prints `aa`. So the binding behaves as a **mutable private copy**, not a read-only borrow — the CoW default, and the same substance the 2026-08-18 entry ratified for the bare `for` element.

  ⚖ **WHY IT WAS NOT CHANGED WITH THAT ENTRY, AND WHY THIS IS LOW.** The ratified entry scopes itself — *"only the bare form was in question"* — and it is about the **`for`-loop element binding**, a different construct from a `.get()` bind. Both docs already state the *outcome* correctly on the next line (mutating the bound value materializes a private copy; the collection is untouched), so nothing here is FALSE about behaviour; what is stale is only the LABEL. And the reference and the book use the SAME phrase for this position, so correcting one without the other would manufacture a fresh inconsistency of exactly the kind R50 Track C2 spent three commits removing.

  **INTENDED:** one decision covering both files at once — either the label follows the `for`-element precedent (a bare collection-element bind is a *mutable private copy*), or the docs state explicitly why this position keeps the older framing. ⛔ **This is a semantics-doc question about a position the ledger has not ruled on, so it is an OWNER ask, not an executor edit** — `docs/define-gorget/decisions.md` is owner-only.

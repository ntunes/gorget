- **🆕🧹 [MED — the `AtomicInt` / `AtomicBool` SIBLING ARMS in the same `unify`, still name-matched. `[[t0718]]`'s own text calls this pair *"the tell that this is a class and not a site"*; R51 Track C migrated the `Mutex`/`Shared`/`RWLock` arms directly above them and DELIBERATELY LEFT THESE, because they are a different arm SHAPE with a different row set.]**
  - **THE SITES** (regenerate: `grep -n 'AtomicInt' src/semantic/typecheck.rs`) are the two arms immediately below the migrated pair, deciding `AtomicInt ↔ int` / `AtomicBool ↔ bool` from `name == "AtomicInt"` / `name == "AtomicBool"`.
  - **⛔ WHY IT IS NOT A ONE-LINE EXTENSION OF THE MIGRATION, and this is the finding.** The migrated arms are `ResolvedType::Generic(def_id, args) if args.len() == 1` — a guard nothing else reaches. The atomics arms are `ResolvedType::Defined(def_id)`, i.e. **the general `Defined`-vs-anything MISMATCH FALL-THROUGH**: the same arm every non-atomic user type falls into on its way to `E_TypeMismatch`. Folding the atomics into `BuiltinTypeKind` therefore means editing an arm that fires on ordinary user types, with its own accept/reject surface to pin — **not** the additive, single-purpose edit the coercion arms were. R51 Track C's brief-review measured the arm firing **5** times corpus-wide, all on user types (`Tagged` / `AppError` / `UserId` / `AccountId`) and **zero** on `AtomicInt`/`AtomicBool`.
  - **✅ THE SEED IS ALREADY THERE, so this is a migration and not a feature.** `struct AtomicInt` and `struct AtomicBool` are declared in `lib/std/sync.gg` (regenerate: `grep -n 'struct Atomic' lib/std/sync.gg`) and `std.sync` is a builtin module (`src/stdlib.rs`, `is_builtin_module`) — **the identical position as `struct RWLock[T]`, which the identity seeds today at seed site B.** Adding two variants to `BuiltinTypeKind` plus a fourth per-axis accessor is all the mechanism needed.
    ⚠ **A CLASS OF REGISTRATION IS INVISIBLE TO A GREP FOR ITS MEMBERS.** An earlier pass concluded the atomics had *"no seed site at all"* from `grep -rn 'AtomicInt' src/semantic/` — but seed site B is **name-agnostic by construction**: it reads the name off the AST of any builtin-module struct. Do not re-derive the negative that way.
  - **THE LIVE CELL, with a working control:** `newtype AtomicInt(int)` + `take_int(m)` → rc 0, while `newtype NotAtomic(int)` → rc 1. Same family as the ten `coercion_identity/user_*` rows: a user type inherits a builtin's coercion because the decision is keyed on the spelling.

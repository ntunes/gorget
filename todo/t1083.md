- **🆕🐛 [HIGH — a program the compiler ACCEPTS emits C that a C compiler REFUSES: `error: redefinition of 'Box__Robot__drop'`. Found 2026-09-04 by R49 Track M2 while enumerating the cells adjacent to the trait-object pack; measured pre-existing and unchanged by that fix.]**
  - **MEASURED (bare rc, R49 HEAD):** `gg build tests/fixtures/known_gaps/box_concrete_elem_drop_redefinition.gg` → rc 1. `gg check` passes; the failure is at `cc`.
  - **TWO PRODUCERS, ONE SYMBOL.** In the emitted `.c`:
    - `static inline void Box__Robot__drop(Box__Robot self) { GORGET_FREE(self, sizeof(__gg_Robot)); }` — the collection element-drop helper, box-by-value.
    - `void Box__Robot__drop(void* slot) { … }` — the vtable slot-drop, whose address `__gg_Speaker_VTable __lir_g0 = {…, (void*)&Box__Robot__drop}` stores.
    Neither emitter knows about the other, so a program needing BOTH — a **concrete** box held in a collection, of a type that is **also** trait-equipped — collides. Layering rule 3: one axis (how a `Box[T]` is dropped), two locations, two spellings.
  - ⭐ **DISCRIMINATOR, as filed:** the same program with the element typed as the TRAIT box (`Vector[Box[Speaker]]`) compiles and runs. Only the CONCRETE-box element reaches both emitters, because that is the shape that is simultaneously a collection element (element-drop helper) and a vtable subject (slot-drop).

  - ⛔⛔ **SCOPE WIDENED AND THE DISCRIMINATOR CORRECTED 2026-09-05 (R50 Track J's executor, measured; this absorbs the duplicate filing `t1421`).** The trait is **not** the discriminator and the vtable is **not** the second producer. **`Vector[Box[int]]` — no trait, no vtable, no user struct — collides identically**, and the emitted C contains **zero** `VTable`/`_TraitObj` references (`grep -c 'VTable\|_TraitObj'` on the generated `.c` → 0). The by-slot definition's address is taken by the **ARRAY's `elem_drop` hook** (`__v3 = (void*)Box__int64_t__drop`), not by a vtable slot. And the by-VALUE spelling is the **Box type's own drop method**, not the collection helper — the two producers were swapped in the original analysis.
    ⇒ **THE SCOPE IS EVERY `Vector[Box[T]]`, FOR EVERY `T`** (`Box[int]` and `Box[String]` measured; a plain `.push` is enough, so it is method-independent too). This is a whole uncompilable type combination, not a rare trait+collection corner. ⚠ **A fix that unifies only the vtable path leaves the minimal cell red** — hence the second repro, `tests/fixtures/known_gaps/t1083_vector_box_int_elem_drop_redefinition.gg`, wired `#[ignore]`d as `vector_box_int_elem_drop_redefinition`.
    ⚠ **`t1421` WAS THIS ITEM, RE-FILED** (R50 Track J's scout, 2026-09-05) under the mechanism *"the monomorphizer emits the drop glue for the unsubstituted type parameter `T`"* — also false, since both names are substituted. It has been folded here and removed; nothing else cited it.

  - ⭐ **AND IT GATES TWO RUNTIME CELLS (from `t1407`'s closure).** This is the only surface route to the element-hook configurations `elem_drop != NULL && elem_clone == NULL` and its mirror `elem_clone != NULL && elem_drop == NULL`, both of which `src/backend/c/runtime/runtime_array.c` documents as legitimate and `gorget_array_fill` either asserts on or would leak in. While this gap is open **nothing in the corpus exercises either configuration**, so a defect living there is invisible today — which is why `t1407` had to record both as named omissions rather than pin them. **Whatever fixes this owes a fixture for BOTH directions**, not just the one the runtime abort names; *"likely uninhabited"* is a claim to MEASURE once the combination compiles, not a reason to skip the cell.
  - ⚠ **NOT `t0700`.** That item is `elem_drop_fn_for_type` returning `None` for a registered `{inner}_TraitObj`, i.e. a `Vector[Box[Trait]]` never dropping its elements — a LEAK in a program that builds. This is a BUILD failure in the concrete-box case, from the opposite side: the element-drop helper IS emitted and collides with the vtable's. Fixing `t0700` by widening the element-drop path without unifying the symbol would make this collision MORE reachable, not less — check this repro when landing it.

Recorded in the fixture header so a reader does not mistake one for the other.

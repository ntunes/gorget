- **🆕🧹 [MED — a GUARD THAT LIES ABOUT WHICH THING IS BROKEN when its own tooling fails; isolated 2026-09-03 by R48 Track U's output review while adjudicating three intermittent lint failures] `scripts/clone_meter_check.sh` swallows a `git` failure and reports it as a pin defect.**
  **MEASURED 2026-09-03**, `cargo test --test lints --release` in an agent worktree, 1 failing run in 4 identical ones:
  ```
  clone-meter pin staleness (tip )
  fatal: detected dubious ownership in repository at '<worktree>'
  ❌ PINNED-BY sha 4c473a88 does not resolve in this repo
  ```
  Read the first line: **`(tip )` with an EMPTY sha.** `git rev-parse` was refused, its output was captured anyway, the empty string was used as the tip, and the script then concluded that the PIN does not resolve — which is a statement about the pin, and it is false. The pin is fine; git refused the repository. Four lint tests fail this way (`clone_meter_check_refuses_an_unattributed_track`, `clone_meter_pins_carry_their_provenance`, `clone_meter_pin_provenance_shas_resolve`, `code_doc_citations_resolve`), each with a message that sends the reader after a different non-existent defect: *"the closure is wrong"*, *"the band anchor names no round open on this history"*, *"re-write the provenance line from a sha that exists"*.
  ⚠ **`code_doc_citations_resolve` is the CONTRAST that shows the fix.** Handed the same refusal it says: *"git ls-files exited non-zero TWICE (exit status: 128); refusing to scan an unknown file set"* and prints git's stderr. It checks the status, names the tool, and refuses to draw a conclusion. That is the shape every consumer of a `git` call in this tree should have, and it is already written down here.
  **THE FIX:** check the exit status of every `git` invocation in `scripts/clone_meter_check.sh`, and on failure print git's own stderr and exit non-zero at the git call — never continue with an empty capture. An empty tip is not a fact about the repository, it is the absence of one.
  ⛔ **DO NOT close this by adding a global `safe.directory` entry.** That is adjusting the instrument until it agrees: it makes these four tests pass without changing the fact that the script cannot tell "git refused" from "your pin is wrong", and the next environment that refuses git — CI in a container, a fresh clone with different ownership, a sandbox — gets the same false verdict with no warning. The ownership condition is the TRIGGER; the swallowed status is the DEFECT.
  **WHY IT IS ONLY INTERMITTENT:** the refusal depends on how the test process's git invocation inherits its environment, so a full parallel run trips it while the same test alone passes. That intermittency is itself the argument for the fix — a guard that fails in a way its own message misattributes will be re-run until green and then believed.
  **NOT REPRODUCIBLE ON DEMAND** (it needs the ownership refusal), so no `known_gaps/` repro is filed. The verification is direct: make `git rev-parse` fail inside the script's environment and check that it exits at the git call with git's message, rather than printing `(tip )`.

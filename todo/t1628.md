- **🧹 [MED — the mechanism AGENTS.md Core #6 names as the answer to pin churn does not exist] There is no LOWER-ONLY `--bless` write-back for a `tests/lints.rs` pin, so the sanctioned way to pay a debt pin down is unavailable and every burn-down still costs a hand edit.**

  Core #6 now reads (owner 2026-09-08): *"KEEP THE EXACT `==`; SLACK IS WHAT ROTS. An improvement lowers the pin by auto-lowering write-back (`--bless`, LOWER-ONLY) — never by hand, never by widening to `<=`. Terminus: burn the debt to 0 and assert `== 0`."*

  The first half is enforced today — the pins are exact `==`. The second half has no implementation: `grep -n 'bless' tests/lints.rs` finds only prose and the `scripts/convergence.sh --bless` pointer, which writes `scripts/baselines/debt_ledger.tsv` (a BIDIRECTIONAL baseline, explicitly a different thing) and never touches a pin.

  **What this blocks, measured 2026-09-08.** Three guards carry the bulk of the file's hand-edited data and each is correct as written — an exact `==` is the right shape for all three, so the only sound way to remove their churn is the write-back:

  | guard | data | what a legitimate improvement costs today |
  |---|---|---|
  | `sanitize_allowlists_shrink_only` | 6 `assert_eq!` totals over `tests/sanitize/LEAK_ALLOWLIST.txt` — `LEAK_CEILING`, `LEAK_CLASS_PAIRS`, `LEAK_RECORDS`, `LEAK_LOOSE_SIGNATURES`, `UNCITED_LEAK_CLASS_PAIRS`, `CORRUPTION_CEILING` (values live at those constants; do not re-spell them here) | any leak fix moves up to 5 of the 6 by hand |
  | `expr_stmt_walker_population_is_pinned` | 107 rows (105 HAND-ROLLED, 1 ROUTED, 1 CHOKEPOINT) | routing a walker onto the chokepoint — the improvement the guard exists to drive — reds the test |
  | `indirect_dispatch_results_registered_at_birth` | `RAW_PRODUCER_CENSUS`, 28 `(spelling, file, count)` rows over `src/ir/lowering/` | routing a raw producer through `call_indirect_tracked` reds the test |

  ⚠ **Do NOT "fix" any of these by widening to `<=`** — that is the move the owner ruling forbids, and `tests/lints.rs`'s own `assert_exact_ratchet` doc carries the measurement of why (a probe added TWENTY fresh `starts_with("X__")` sites to `src/` under a slack budget and the gate passed).

  ⚠ And do not replace the walker population's SET with a count in either direction: the set is what names *which* walker arrived, and its own docstring records that a count *"goes green again the moment an unrelated walker is deleted"* — a delete-plus-add in one commit is invisible to any count.

  **What the write-back owes:** a lower-only path (an env gate or a `--bless`-style flag) that rewrites the pin in `tests/lints.rs` from the measured value **only when the measured value is better**, refuses to raise, and leaves a green run byte-identical. A raise stays a hand edit with a justification, which is the review event the pin exists to force.

  ## ⭐ SCOPED AND RE-AIMED 2026-09-09 BY THE GUARD WITNESS CUT — THE POPULATION IS A QUARTER OF WHAT THIS ITEM ASSUMED, AND THE MECHANISM NEEDS TWO EXCLUSIONS

  The cut classified all sixty-one CENSUS-DIRECTIONAL guards against the question *"could a witness replace this pin?"*. Result:

  **A minority genuinely need `--bless`** — the rest fall away, and **not because they found witnesses.** Only a handful have a real one. The others fall away because of **the property they hold**, which this item's framing did not distinguish:

  ⛔ **AGREEMENT IS NOT MAGNITUDE, AND A LOWER-ONLY WRITE-BACK IS THE WRONG OPERATION ON IT.** `single_owner_init_helper_call_sites` pins the number of ownership boundaries routed through a shared helper. Routing **one more** through it — the improvement you actually want — moves the count **up**. A lower-only bless cannot record that, and if it ever fired on such a guard it would ratchet the pin down onto a tree that legitimately grew. Core #6's `--bless, LOWER-ONLY` clause is correct for a **ceiling over a debt magnitude** and wrong for a **count of things that should agree**; the clause does not currently distinguish them.

  ⛔ **AND `provenance = policy` MUST BE SKIPPED, OR THE FIRST RUN BLOCKS THREE FILED ITEMS.** `AGENTS_MD_SIZE_CEILING` is a deliberate editorial budget, not a debt. Regenerate the headroom:

  ```
  echo $(( $(grep -oP 'AGENTS_MD_SIZE_CEILING: u64 = \K[0-9_]+' tests/lints.rs | tr -d _) - $(wc -c < AGENTS.md) ))
  ```

  An auto-lowering write-back sets that ceiling to the file's current size, taking the headroom to **zero** and silently blocking `[[t0577]]`, `[[t0714]]` and `[[t1629]]`, all of which need bytes in that file. ⭐ **THE DISCRIMINATOR ALREADY EXISTS IN-TREE** — `scripts/figures.db` carries `provenance` per row and already classes this pin `policy`. **Read polarity and provenance from the DB; do not re-derive them.** `CLEAN_FLOOR` rows are `>=` floors and take the write-back in the opposite direction.

  ⛔ **AND DO NOT KEY THE MECHANISM ON `const NAME: TYPE = <digits>;`** — see `[[t1618]]`'s 2026-09-09 addendum: that predicate is blind to a fixed-length `[&str; N]` allowlist and to six inline tuple budgets, which are exactly the hand-maintained magnitudes `--bless` exists to maintain.

  ⚠ **WHAT THE CUT COULD NOT SETTLE** (named here so it does not die with the brief):
  - **`code_doc_citations_resolve`** was classified as needing bless after confirming no companion enumerator exists in `scripts/`; the cut did **not** exhaustively search outside `scripts/`. A missed witness would only *lower* the population.
  - **Whether ggdef's single `PartialMove` emit site is structurally FORCED** the way the Rust lane's move-operand chokepoint is. It is one site today and no lint links it; establishing forcedness is a design question about ggdef's move-source path, not a count.

  ## 🚨 A COLLAPSE BLESSES THE WHOLE BACKLOG TO ZERO, AND THE OBVIOUS RED-VERIFY CANNOT SEE IT — FOUND 2026-09-09 BY BRIEF-REVIEW PASS 1

  Precedence: this addendum > everything above.

  **(1) 🚨 THE FAILURE MODE THE DIRECTION RULE DOES NOT COVER.** `sanitize_allowlists_shrink_only` reads its allowlists with `read_to_string(...).unwrap_or_else(|e| panic!(...))`, so an **unreadable** file is closed. A **TRUNCATED** file is not: the read succeeds, the comment/blank filter yields zero rows, and `LEAK_CEILING`, `LEAK_CLASS_PAIRS`, `LEAK_RECORDS` and `UNCITED_LEAK_CLASS_PAIRS` **all collapse to 0**. Every one is then `measured < pin`, so a lower-only write-back rewrites **all four pins to 0**, reports it as progress, and passes. `cargo test --test lints` is green afterwards.

  ⛔ **AND `UNCITED_LEAK_CLASS_PAIRS`'s OWN ASSERT MESSAGE SAYS "TARGET IS 0".** A truncation therefore blesses the entire leak backlog to precisely the number Core #6 calls the **terminus** — and nothing in the tree distinguishes that from the round that earned it. *"Measured > pin fails regardless of env"* closes the RAISE direction and is silent on a COLLAPSE.

  **(2) ⛔ AND THE NATURAL RED-VERIFY IS THAT SAME EXPERIMENT.** *"Shorten the allowlist, watch the pin bless down, confirm green"* is the collapse, performed deliberately and read as success — SIX-Q #6. The demonstration cannot tell the mechanism working from the mechanism destroying the ledger.

  ⭐ **REFERENCE-GRADE, three parts:**
  1. **Bound the write, do not merely direct it.** Refuse unless the parse is non-vacuous and the drop is plausible — a fire-count/floor precondition asserted **before** any rewrite, whose refusal names the collapse.
  2. **Report the delta as ROWS, not a number.** A bless that names the retired stems is auditable; one that prints `245 → 0` is not.
  3. **Make the LOAD-BEARING red-verify the REFUSAL:** truncate the allowlist to its comment header, run with the bless env set, and show it **refuses**. Without that case the mechanism is unverified in the only direction that matters.

  **(3) ⛔ THE GUARD HAS SIX PINNED CONSTANTS, NOT FOUR — AND TWO ARE DOCUMENTED IN-TREE AS UN-BLESSABLE.** *"Env-gate a write-back inside that guard"* catches all six. Regenerate the set, then read each row's `caveat` in `scripts/figures.db`:

  - **`CORRUPTION_CEILING`** — its one row is the sanitizer's **positive control** (a fixture whose whole purpose is to prove the stack guard fires). The DB says the honest target *"is 1 and not 0"*. A lower-only bless deletes the pin on the positive control.
  - **`LEAK_LOOSE_SIGNATURES`** — the DB calls it *"NOT a debt-magnitude number: it is an ADMISSION count"*. That is Core #6's **AGREEMENT COUNT** exactly, which the amended clause says is pinned and never blessed.

  ⇒ **KEY THE MECHANISM TO AN EXPLICIT ALLOWLIST OF THE FOUR NAMED CONSTANTS — never to "the constants in this guard".** Present all six with a disposition per row (Core #15b).

  **(4) ⚠ AND STATE THE CIRCULARITY RATHER THAN LET IT BE DISCOVERED.** These pins are `provenance = derived` from a **hand-edited declaration**, not from the sweep: a human edits `LEAK_ALLOWLIST.txt`, and the bless then rewrites the pin *from that edit*. The evidence for "debt was burned" is circular. It does not sink the design — the churn is real and worth removing — but the non-circular reading is the sweep's own verdict output, and the brief must say so.

- **🆕🧹 [MED — A PROCESS TRAP THAT SHIPPED A DEFECT THIS ROUND; found 2026-08-24 by R44 Track A, on itself] `git mv` + "stage explicitly by file name" silently drops every post-move CONTENT edit.** `git mv` stages a RENAME. An edit to the moved file afterwards is a SEPARATE, UNSTAGED change, and `git status --porcelain` reports the pair as **`RM`** — R in the index, M in the worktree. An executor obeying Multi-agent rule 3 ("`git add <specific files>` only") builds the add-list by reading that status, sees the `R`, and treats the row as handled. Measured live: R44 Track A moved three fixtures and rewrote all three headers; the integration commit captured the moves as PURE RENAMES (`git show --stat` → ` | 0` on each) and left the ORIGINAL headers in the tree — including one carrying an order the SAME round had RETRACTED, and two declaring graduated fixtures to be open gaps. Three Core #14 false invariants, in the round retiring thirteen. Caught only because the executor re-read `git status` after the commit. ⚠ **The rename-detection display is the trap, not `git mv` itself** — the `R` is real, the `M` is real, and the compound code reads as one resolved row. **Fix candidates, cheapest first:** (a) a line in the Multi-agent orchestration rule — *"after `git mv`, `git add` the NEW path again once you have finished editing it; `RM` means half-staged"*; (b) a pre-commit check that refuses a commit whose index contains a rename whose worktree copy is still dirty; (c) have executors close with `git status --porcelain | grep -E "^[A-Z ][A-Z]"` and dispose of every second-column letter. ⊕ Related but distinct from the `git add -a` ban, which is about staging TOO MUCH; this is staging too little, and the standing rule is what causes it.

Everything below is **accepted**:

  ```gorget
  void main():
      Set[int] s = {1}
      for p in s.iter():
          print(p.bogus_field)        # read a field on an int
          print(p.bogus_method())     # call a method that does not exist
          p.bogus_field = 7           # WRITE to a nonexistent field
          String x = p                # bind an int into a String slot
          print(p + 1)
  ```

  **The discriminator is the `Iterator` protocol, not the element type and not `Ref`.**
  `Set[int].iter()` yields a plain `int`, so this is not a tuple-arity confusion:

  | loop form | `String x = <elem>` |
  |---|---|
  | `for p in s:` -- builtin, same collection | ✅ **rejected**, `1 error(s) found` |
  | `for p in d.items():` -- eager builtin returning `Vector[(K,V)]` | ✅ **rejected** |
  | `for p in s.iter():` -- userland `Iterator` | ❌ **accepted** |
  | `for k, v in d.iter():` -- destructuring, userland | ❌ **accepted** |

  stable and the builtin column is the **independent witness** that the language does know how to
  reject these (Readiness row 2 -- the checker's own acceptance cannot show you what it skipped).

  **Severity is CRITICAL, not "silent-accept".** `String` is a thin pointer. `String x = p` with

### ⚠ ADDENDUM 2026-09-05 — RE-GRADED CRITICAL → HIGH; THE MEMORY-SAFETY CLAIM IN THE BODY IS WITHDRAWN

**The body claims `String x = p` is a wild pointer read that "exits 0 printing nothing". That is
false.** The owner asked what exactly was being accepted, and running every case properly instead of
inferring from one unvalidated fixture gives this — **`p` is `int` 7 throughout**:

| loop body | `gg check` | `gg run` | observed |
|---|---|---|---|
| `print(p + 1)` | `OK` | rc 0 | prints `8` — **correct; `p` is genuinely typed at runtime** |
| `print(p.bogus_field)` | `OK` | rc 0 | prints **`0`** — silent wrong output |
| `p.bogus_field = 7` | `OK` | rc 0 | **write silently discarded** |
| `print(p.bogus_method())` | `OK` | rc 1 | build failure |
| `String x = p` | `OK` | rc 101 | **ICE**, `Tier 2a consume-site violation … untracked source consumed` |

Regenerate by substituting each body into `for p in s.iter():` over `Set[int] s = {7}` and reading
**both** rcs off the bare commands.

**So the accurate defect is narrower and still serious.** There is no wild read and no
memory-unsafety: the arithmetic case proves the value is correctly typed where it is *used*
legitimately. What is missing is the **check on member access** against the element type —
so field reads, field writes and method calls are unvalidated, and the downstream behaviour is
whatever each path happens to do.

**Two of those rows are the real severity, and neither is the one first claimed:**
- `p.bogus_field` reading **`0`** is silent wrong output (Core #8).
- `p.bogus_field = 7` **discarding a user write** is Core #10 verbatim — *"a `_ =>` fall-through
  that discards a write is a miscompile-class defect"*.

Per the standing severity ladder (mem-unsafety > silent-wrong-output > ICE > leak) this is **HIGH**.
⚠ **Do not let the withdrawn CRITICAL framing survive in a brief** — an executor scoping for
memory-safety would look for a wrong ownership tag and find nothing, because the write site is a
missing *type* on the loop binding, not a missing ownership decision.

**What does NOT change:** the check-acceptance itself, the discriminator table in the body (builtin
`for` rejects, `.iter()` accepts, eager `.items()` rejects), and the consequence for [[t0041]] —
promoting `for x in xs` as the default idiom still should not advance while member access on these
bindings is unchecked.

### ⚖ OWNER RULING 2026-09-05 — THIS IS A DEFECT; `gg check` MUST REJECT IT

Verbatim: *"Right, if p is an int, no fields should be accepted. gg check should reject that, no
question about it."*

**This closes SIX-QUESTIONS #1 for this item.** The accept/reject asymmetry between the builtin
`for p in xs:` (rejects) and `for p in xs.iter():` (accepts) is **not** two positions with different
ratified semantics — it is a hole, and the builtin's behaviour is the correct one. No design
question remains; the track is an implementation track.

**Consequences for scoping, in the owner's direction:**
- The **rejection belongs at `gg check`**, not at lowering. Today `String x = p` is caught by the
  Tier 2a consume-site validator as an ICE (rc 101) — that is the wrong layer and the wrong
  diagnostic. Core #1: fix at the write site, which is wherever the loop binding's element type is
  established for the builtin path and not for the `Iterator` path.
- The two silently-wrong rows (`p.bogus_field` reading `0`, `p.bogus_field = 7` discarding a write)
  must become **check-time rejections**, not corrected runtime behaviour — there is no correct
  runtime behaviour for a field that does not exist.
- Both loop forms are in scope: single-binding **and** destructuring (`for k, v in d.iter():`)
  showed the same hole, which is the signature of one missing write, not two omissions (Core #4).

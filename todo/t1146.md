- **🆕 [HIGH — a `--yes` mid-round deletes live executors; measured 2026-09-04 during R49] `scripts/round_cleanup.sh` has no live-agent keep-list.**
  - **MEASURED, not hypothetical.** With two track executors and six reviewers in flight, a `--dry-run` proposed removing **thirteen** worktrees, **eight of which were live** — including **both executors**. A `--yes` at that moment would have destroyed in-progress work on two signed-off tracks.
  - **The rule exists; the tool does not carry it.** AGENTS.md multi-agent rule 6 already says *"a live agent needs a keep-list"*. The script's default is `--force`.
  - ⭐ **THE FIX SHOULD DERIVE THE KEEP-LIST MECHANICALLY RATHER THAN TRUST THE CALLER.** The lock is already present and already carries the pid: `git worktree remove` refuses a live worktree with `cannot remove a locked working tree, lock reason: claude agent <id> (pid N)` and exits **128**. **The information the script needs is the information git is already printing at it.** Every worktree whose lock names a live pid is INELIGIBLE, and `--force` must never be the default for a locked path.
  - ⛔⛔ **THREE MEASURED INSTANCES BY 2026-09-04, AND THE THIRD IS WORSE THAN LOST WORK.** (i) A brief-review
    pass killed mid-command while running the measurement that decided its track's outcome. (ii) A second
    reviewer, same failure. (iii) ⛔ **A track EXECUTOR mid-execution — and because the Bash cwd resets
    between calls, it fell back to the DEFAULT working directory, which is the ORCHESTRATOR'S WORKTREE, and
    two relative-path writes landed there before it noticed the `Compiling gorget (/workspace/gorget-1)`
    line.** It contained and reverted them by explicit name and the orchestrator worktree verified clean —
    **but a deleted worktree does not merely lose an agent's work, it silently REDIRECTS that agent's WRITES
    into another tree.**
  - ⚠⚠ **AND THE `Edit` TOOL RESOLVES RELATIVE PATHS AGAINST THE ORCHESTRATOR WORKTREE TOO, NOT THE AGENT'S**
    — it refused the agent's first edit for that reason. ⇒ **this is AGENTS.md MA-7's exact hazard
    (*"an unqualified absolute path writes into MAIN"*) arriving through a SECOND door: not a mis-typed path,
    but a VANISHED cwd.** ⇒ **MA-7's remedy (worktree-relative paths) is INSUFFICIENT ALONE; an agent whose
    cwd disappears needs to STOP, not fall back.**
  - ⚠ **NOT CAUSED BY `round_cleanup.sh` IN THESE THREE CASES** — the orchestrator ran only a `--dry-run`,
    and its five hand-prune attempts all failed at **rc 128** (harness-locked). **Something else is reaping
    worktrees**, so the fix is not only the keep-list: **an agent must detect that its own cwd is gone and
    HALT rather than fall back to a default.**
  - ⚠ **ADJACENT, AND WHY THIS WENT UNNOTICED:** five long-idle worktrees in the same run were **all harness-LOCKED** and could not be pruned by hand either. **Disk therefore does not fall at round close the way the hygiene rule assumes**, and any accounting of "worktrees reclaimed" that does not separate *locked* from *dirty* will over-report. Disk was stable at 17% regardless — this is a correctness gap in the tool, not a capacity problem.

  - **⭐ THIRD INSTANCE, MEASURED 2026-09-04 (orchestrator, R49 mid-round prune).** With **six agents live**,
    `scripts/round_cleanup.sh` dry-run proposed `git worktree remove --force` on **every** `agent-*` worktree
    — all six live ones included. Its capture step flagged **3 worktrees with uncommitted work, and 2 of
    those were LIVE AGENTS** (an executor mid-fold and another mid-implementation). Running `--yes` would
    have destroyed both. ⚡ **Two compounding defects, not one:** (a) selection is by cleanliness alone, with
    no keep-list; (b) the capture uses bare `git diff`, which **silently omits untracked files**, so even the
    "capture first" half is lossy for a worktree holding new fixtures — exactly what an executor produces.
  - **What a correct run looks like** (done by hand this round, 34 → 18 worktrees, zero loss): build an
    explicit keep-list of live agent ids; skip any worktree with a non-empty `git status --porcelain`;
    remove **without** `--force`, reading the rc off the bare command per worktree; and treat a `locked`
    flag as a signal, not an obstacle — **`stat -c %Y` on the worktree separates a stale lock from a live
    agent** (six were idle 8–15 h and released cleanly; two idle under 2 h were left alone).
  - **INTENDED:** a `--keep <id>[,<id>…]` flag (or a `/tmp` keep-file the orchestrator writes before
    launching), `git add -A` before the capture diff so untracked work survives, and removal without
    `--force` so a dirty tree fails loudly instead of vanishing.

  ## ⛔ SECOND FACET, MEASURED 2026-09-06 (R51 orchestrator, from a live dry-run) — **THE CAPTURE STEP LOSES UNTRACKED FILES**

  This item's original facet is step **(b)**, SELECTION: which worktrees get removed. **This is step (a), CAPTURE: what the safety net actually saves — and it is the more dangerous of the two, because it fails while reporting success.**

  `scripts/round_cleanup.sh:36` (regenerate: `grep -n 'diff >' scripts/round_cleanup.sh`) is:

  ```
  run "git -C '$wt' diff > '$out'"
  ```

  **A plain `git diff` with no `git add -A` first.** AGENTS.md multi-agent rule 8 states the hazard verbatim — *"a plain `git diff` LOSES untracked files"* — so **the script contradicts a documented rule in the very file that prescribes the discipline it is implementing.**

  ⛔ **MEASURED LIVE, NOT HYPOTHETICAL.** A `--help` dry-run during R51 printed:
  `! …/agent-a718d61a65d32c8d5 has UNCOMMITTED work → capturing to /tmp/recover_agent-a718d61a65d32c8d5.patch`
  That worktree was at that moment an executor **creating NEW fixture files** — untracked by construction, since a new fixture has never been committed. The capture would have written a patch, reported success, and **silently dropped every new fixture**, after which step (b) removes the worktree with `--force`. **The one operation whose entire purpose is not losing work is the operation that loses it.**

  ⭐ **SIX-Q #4 — THIS HAS NO SUBJECT IN THE FIRST FACET, SO FIXING THE KEEP-LIST DOES NOT FIX IT.** A worktree that is *correctly* selected for removal — agent finished, work integrated — still loses its untracked files on the way out. The two facets are independent failures of one script and **each needs its own fix**; a keep-list makes the tool safe to *run*, not safe to *trust*.

  **INTENDED:** capture with `git -C "$wt" add -A` (or `git diff HEAD` after staging, per MA-8's prescription) so untracked files are inside the patch, and assert the patch is non-empty whenever `status --porcelain` was non-empty. ⚠ **And the guard for this cannot be a source-text lint** — it must apply the produced patch to a scratch clone and assert a deliberately-added untracked file survives the round trip, or it green-lights its own class (SIX-Q #2).

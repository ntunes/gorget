- **🆕🐛 [MED — BOTH LANES AGREE ON THE WRONG ANSWER (Core #8 red flag); found R47 Track D1 while building the ACCEPT control for the primitive-receiver reject] An `equip int:` block breaks the static call `int.parse(...)` in the same program.** The type NAME in receiver position is lowered as if `parse` were a user equip method on `int`:

  ```
  RUST gg   : undefined reference to `int64_t__parse'
  SELF-HOST : undefined reference to `int64_t__parse'
  ```

  - **Neither feature is at fault alone.** Remove the `equip` block, or remove the static call, and the program builds and prints `99`. They are independent language features (`tests/fixtures/equip_on_primitive.gg` covers the first, the `parse_*` corpus the second) and their combination has no ratified special case, so this is a defect, not a design.
  - The mechanism to look at is the static-call path: a `Type.method(...)` receiver is a TYPE NAME, not a value, and once an equip block registers methods for that primitive the call resolves through the equip mangling instead of the intrinsic. Seven-line repro: `tests/fixtures/known_gaps/equip_on_primitive_shadows_static_parse.gg`, wired `#[ignore]`d as `known_gap_equip_on_primitive_shadows_static_parse`, asserting the intended `99`.
  - INDEPENDENT of R47 Track D1's `reject_no_method_on_primitive`: it reproduces identically on the pre-fix driver, and the reject never sees a static call (the receiver is a type name, which resolves to no type at all). It is filed from that round only because the ACCEPT control fixture wanted the cell and could not have it.

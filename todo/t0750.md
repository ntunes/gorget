- **🆕🚨 [HIGH — A CoW COLLECTION ALIAS LOSES ITS VALUE SEMANTICS INSIDE A `while` LOOP, IN BOTH DIRECTIONS. Silent wrong values at rc 0, ASan-clean, on BOTH backends. Rust gg only — the SELF-HOST LANE IS CORRECT, so the oracle adjudicates this and the reference is the lagging lane.]** Straight-line, `Vector[String] alias = v` has correct CoW value semantics and `tests/fixtures/cow_transitive_alias.gg` pins it: `alias.push("b")` → `v=1 alias=2`; `v.push("b")` → `v=2 alias=1`. Put the identical mutation inside a `while` loop and **both directions break**: **(A) mutation THROUGH THE ALIAS loses every write** — 3× `alias.push` in a loop leaves `alias.len() == 1`, i.e. three appends vanish; **(B) mutation THROUGH THE ROOT never severs the alias** — both names then report the grown length, so value semantics silently degrades to **reference semantics**. Measured at HEAD on C and LLVM alike: `alias-loop 1 1` / `root-loop 4 4`. The self-host lane (`self_host_lowerer/driver.gg --emit-c`) prints `alias-loop 1 4` / `root-loop 4 1` — the intended answer — so this is Rust-side oracle hygiene, never a reason to dumb the self-host down. **SUSPECTED MECHANISM (not yet prototyped):** the materialize/sever rebind `cow_before_mutation` emits is discarded at the enclosing loop's `save_locals`/`restore_locals` boundary, the same shape `tests/integration.rs`'s `cow_borrow_outlives_push` records for String views — but the two hooks that hoist a materialize into the loop pre-header, `materialize_loop_carried_bare_params` and `materialize_scope_carried_bare_params`, both filter their candidate set with `ctx.is_bare_param` (`src/ir/lowering/stmts/mod.rs:2632` and `:2699`), so a LOCAL alias is outside the candidate set of that machinery entirely and no fix there reaches it. Whether A and B are one mechanism or two is **open** — they may share the loop-boundary root, or B may additionally need Case 2 (`cow_aliases_of` → clone into each alias) to be loop-carried. ⚠ **DISCRIMINATORS, so this is not merged with its neighbours.** NOT the `cow_loop_bare_param_*` family (`t0122`–`t0127`, `t0344`, `t0556`): every member of that family is a bare (borrow) PARAM or `self`, enforced mechanically by the two `is_bare_param` filters above, and its symptom is a per-iteration throwaway of a private copy (wrong counts, extra clones) rather than lost appends. NOT the alias-SPELLING UAF class (`t0703`, `t0699`): those are dangling STRING VIEWS into the collection — rc 139, ASan heap-use-after-free, realloc load-bearing (64 pushes); this is rc 0, ASan-clean and realloc-independent (3 iterations), and the wrong thing is the collection alias's own length. **INTENDED (asserted by the `#[ignore]`d `known_gap_cow_local_alias_loop_mutation_lost`):** `alias-loop 1 4` / `root-loop 4 1`. Found while landing `t0703`; the alias-resolution fix is a measured no-op on it (identical output before and after), which is why it is filed rather than folded.

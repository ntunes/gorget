- **🆕🚨 [HIGH — MEMORY UNSAFETY on the REFERENCE lane, in a program with no `unsafe`, no ownership operator and no FFI. Core #8: the lanes do NOT agree here, and the one that "works" is the unsafe one.]** A closure LITERAL at `unwrap_or_else` whose receiver's PAYLOAD is itself a `Callable`.
  - **THE PROGRAM.** `Option[Callable[String()]] o = None()`, `Callable[String()] h = hello`, `Callable[String()] f = o.unwrap_or_else((): h)`, `print(f())`.
  - **MEASURED 2026-09-04**, both lanes, at the R49 Track T1 landing:

    | lane | build | run | verdict |
    |---|---|---|---|
    | Rust gg (C) | ok | prints `hello`, **rc 0** | ⛔ `AddressSanitizer: stack-buffer-overflow`, **`READ of size 32`** |
    | Rust gg (C) `--sanitize` | ok | **rc 1**, ASan abort | the same program, seen |
    | self-host | **`cc` REJECTS** | — | `incompatible types when assigning to type 'Str' from type 'GorgetClosure'` |

  - **⭐ ONE ROOT CAUSE, TWO SYMPTOMS — AND TWO DIFFERENT WRITE SITES. Fix them in different places.** Both lanes resolve the expression to the payload's OWN return type (`String`) instead of the payload type (`Callable[String()]`). Where they put that wrong answer differs, and the emitted C says so exactly:
    - **RUST — the CALL-RESULT SLOT, not the closure signature.** The artifact is INTERNALLY INCONSISTENT: the closure is declared `GorgetClosure __Closure_0__call(const void* __p0)` (correct) and the call temp `__v24` is `#define`d onto `GorgetClosure __coal0` (also correct) — but the destination is `Str __s14 = {0}` and the copy is `memcpy(&__s14, &__v24, sizeof(Str))`, taking **32 bytes out of a 16-byte result**. It then copies 16 bytes back out of that slot (`memcpy(&__s11, (void*)__v25, sizeof(GorgetClosure))`), so the value round-trips through a wrongly-typed 32-byte intermediate. ASan names the object: *"`[224, 240) '__coal0'` … Memory access at offset 240 partially underflows this variable"*. ⇒ **The Rust fix is at the `unwrap_or_else` RESULT-SLOT typing; the closure signature is already right and must not be touched.** Regenerate: `gg build --emit-c <repro> -o /tmp/x` then `grep -n '__Closure_0__call\|sizeof(Str)' /tmp/x.c`.
    - **SELF-HOST — the CLOSURE SIGNATURE.** Here the wrong answer lands one layer earlier: `compute_closure_sig` emits `Str __Closure_0__call(void*)`, so the function itself is mistyped and `cc` refuses to assign a `GorgetClosure` to it. The self-host never reaches a slot-typing question because it cannot build.
    ⊕ So *"both lanes make the identical mistake"* is true of the TYPE they compute and false of WHERE they record it — which is why one lane overreads silently and the other fails to compile.
  - **⚠ THE VALUE LANES ARE STRUCTURALLY BLIND TO IT.** It prints the right answer and exits 0, so the parity ledger, the integration suite and the robustness map all score it green; only the sanitizer sees it. That is why the durable record is an ASan-gated pin and not a stdout assertion.
  - **⚠ THE CLOSURE LITERAL IS LOAD-BEARING — measured, not assumed.** `o.unwrap_or(h)`, the same payload and the same types with no closure literal, is ASan-CLEAN and builds on every lane. So this is the closure-return typing, not `unwrap_or_else` dispatch in general.
  - **⚠ PRE-EXISTING, NOT R49 TRACK T1 INFLOW — measured on BOTH sides of that landing.** Before T1's ambient-return override the self-host emitted `int64_t __Closure_0__call` here and `cc` rejected THAT (`returning 'GorgetClosure' but 'int64_t' was expected`); after, it emits `Str` and `cc` rejects that. **A different wrong type, the same CC-FAIL.** The Rust-lane overflow is untouched by T1 and reproduces on `main`.
  - **HOW IT WAS FOUND, and the lesson is about the ARGUMENT rather than the bug.** T1 justified its new override with *"at a builtin-method argument the ambient expected type is the receiver's own Option/Result, so the peel declines"*. That sentence is true of `or`/`and_then`/`flat_map`/`or_else`, which take a peeled WRAPPER, and FALSE of `unwrap_or_else`, which takes `enum_category.ok_type` — the PAYLOAD (`grep -n '_combinator_et = _recv_ec_uoe.ok_type' tests/fixtures/self_host_lowerer/lower_expr.gg`; that site's own comment says *"uoe returns the PAYLOAD (Some_0 / Ok_0), not the wrapper"*). **The peel declines because of the TYPES IN PLAY, not the position** — and it declines only while no payload in the corpus is a callable. Six Questions #6: the green cells were green for a reason unrelated to the rule they appeared to demonstrate.
  - **INTENDED, on both lanes:** prints `hello`, rc 0, sanitizer-clean. The closure's return type at a payload-typed destination is the PAYLOAD TYPE, not the payload's return type. Wired `#[ignore]`d twice — `sh_closure_literal_callable_payload_unwrap_or_else` (self-host build) and `security_closure_literal_callable_payload_overflow` (Rust ASan) — both RED-verified 2026-09-04 for the cited reasons, not merely failing.
  - ⊕ **The fix must not simply drop the ambient override**: it is what closes `t0877`'s other position. The guard wants to be *"the ambient type is the destination's own type"*, which at `unwrap_or_else` is the payload — so the override should take the payload TYPE, and only peel a `GtFnPtr` when the destination is genuinely a callable-typed **slot** rather than a callable-typed **value**.

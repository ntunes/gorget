- **[MED — AN UNIMPLEMENTED FEATURE IS DOCUMENTED AS IF IT EXISTS: `RawPtr[T]` has a numbered design section and a worked book example, and the compiler has never heard of it. Found 2026-08-29 by R47 Track C while trying to build a user-code UAF; disposition sharpened by its output review.]**
  - **VERIFIED AT HEAD.** `grep -rln 'RawPtr' src/ tests/ spec/` → **nothing**. Same for `ConstRawPtr`. It is documented in **two** files: `docs/book/21-interop.md` (6 occurrences, including a `## Raw Pointers` section with a worked `unsafe:` example) and `docs/language-design.md` (6 occurrences under **`### 11.3 Raw Pointers`** — a numbered design section, not marked planned or aspirational). `docs/language-reference.md` has zero, so the *spec* never claimed it; the book and the design doc do.
  - **THE BOOK'S OWN EXAMPLE DOES NOT COMPILE — and a reader does not even reach the real problem.** The snippet at `docs/book/21-interop.md:148-150` (fence `:147-151`) is `unsafe: / RawPtr[int] ptr = ... / int value = *ptr`. Its `...` is prose placeholder, not syntax, so what a reader typing it actually gets is a PARSE error, measured at HEAD 2026-08-29. ⚠ Pasted at TOP LEVEL exactly as printed it is worse still — a bare `unsafe:` block is not a top-level form, so it gives **two** parse errors of a different kind (`expected type, found ':'` at `1:7`, then `expected type, found INDENT`). Wrapped in a `void main():` so the block is legal, the real shape shows:
    ```
    $ gg check <the book's snippet, inside `void main():`>
    error: expected expression, found '..'
      ┌─ …:3:27
    3 │         RawPtr[int] ptr = ...
      │                           ^^
    1 parse error(s) found
    ```
    Substitute any real initialiser and the actual defect surfaces:
    ```
    $ gg check <RawPtr[int] ptr = 0>
    error[E_UndefinedName]: undefined name `RawPtr`
    1 error(s) found
    ```
    So the chapter is unusable twice over: the example as written does not parse, and fixing that only reveals that the type does not exist. That is the sharper half of this item — the design doc misleads a contributor, the book misleads a beginner following along.
    ⚠ **`null` is NOT part of this.** An earlier revision of this item quoted a transcript containing `undefined name 'null'`; that came from a reviewer's own probe (`RawPtr[int] p = null`), not from the docs. `grep -c 'null' docs/book/21-interop.md` → **0**, and `### 11.3 Raw Pointers` has none either — `docs/language-design.md`'s `null` mentions are all prose about Gorget deliberately *not* having null. Corrected here rather than silently, because a quoted transcript that does not reproduce is the exact defect class R47 exists to retire.
  - **⚠ FRAME IT AS "IMPLEMENT OR MARK PLANNED", NOT "THE DOCS ARE WRONG".** Per this project's own rule the docs state INTENDED behaviour and the code shows what IS, so a doc-vs-code conflict here is not automatically resolved in the code's favour. Two coherent dispositions and they are not interchangeable: (a) **implement** `RawPtr[T]`/`ConstRawPtr[T]` as the FFI escape hatch both documents describe (and give the book a snippet that parses), or (b) **mark both sections planned** and remove the worked example from the book until it exists. Which one is an owner call — it is a language-surface decision, not a typo.
  - **SCOPE NOTE.** `docs/language-design.md:2002` also uses `RawPtr[void]` to illustrate a *Sendable* rule ("RawPtr is NOT Sendable"), so the type is load-bearing in prose beyond its own section; whichever disposition is chosen has to reach that site too.

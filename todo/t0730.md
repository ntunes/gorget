- **[MED — ⚠ OWNER CALL, NOT A MECHANICAL FIX: `gg run --backend=llvm` and `gg run --target=freestanding` are ACCEPTED AND SILENTLY IGNORED. Found by the R47 Track C brief-review pass 1; re-filed 2026-08-29 because the breadcrumb that used to cite it had decayed.]**
  - **VERIFIED AT HEAD.** The `"run" =>` arm calls `try_build_ir(…, "c-lir", "native")` with both values hardcoded, and the `flags_with_values` skip-list swallows `--backend`/`--target` so they do not even reach the program as arguments. Same Core #10 silent-drop class as `--sanitize --backend=llvm` (t0723, fixed) and the freestanding/`--shared` combinations (rejected in R47 Track C) — **same file, same class, a sibling site.**
  - **WHY IT IS FILED RATHER THAN FIXED INLINE, stated precisely so the ground does not become a bad precedent.** NOT because it is a different subsystem — it is the same file and the same class. It is filed because **what `gg run --backend=llvm` should MEAN is an unratified semantics question**, i.e. Round-lifecycle step 7(ii), an owner call. Two coherent answers and they are not interchangeable: (a) **reject loudly**, matching the sibling combinations; or (b) **forward the flag**, making `run` a genuine second lane. Neither is obviously right, and the decision has consequences a mechanical fix would land silently — see below.
  - **THE RADIUS, MEASURED, because it is what makes this a decision rather than a chore.** `grep -c 'gg_command("run")' tests/integration.rs` → **6**. Under `GG_BACKEND=llvm` the harness appends `--backend=llvm` to `run`, so option (a) reddens all six. Two of them are **Rust parity ORACLES** (`assert_box_deref_asan_clean` and `self_host_collection_custom_elem_drop_wiring`), and an oracle must be the reference lane — so option (b) would silently start running the oracles on the backend they exist to check against. Either answer therefore needs a deliberate decision about those two sites, plus a change to `gg_command`'s `matches!` dispatch.
  - **CONSEQUENCE WHILE IT STANDS.** Every `gg_command("run")` test executes the **C** backend even under `GG_BACKEND=llvm`, so those cells are vacuous *as LLVM coverage* — the same vacuity family as the LLVM security job before R47 Track C, one subcommand over.
  - **WHERE THE CITATION NOW POINTS.** `tests/integration.rs`'s `gg_command` comment cites this id. It previously said "filed in TODO.md", and nothing under `todo/` matched (`grep -rln 'run --backend|gg run.*llvm|"run" =>' todo/` → no hits). ⊕ A second claim in the same comment is FALSE and no longer stands there: it said `check` does not get the backend flag "because the CLI rejects it there" — `gg check --backend=llvm` in fact exits 0 and ignores the flag. The real reason is that `check` does no codegen.

- **🆕🚨 [HIGH — Core #10 SILENT DROP: assigning to the VALUE binding of a dict loop is ACCEPTED and SILENTLY DISCARDED, rc 0, no diagnostic; measured 2026-08-27, orchestrator-verified in both spellings] `for k, v in d: v = 99` and `for k, v in &d: v = 99` both build rc 0, run rc 0, and leave `d` UNCHANGED** (`d["a"]` still `1`). ⚠ **THE VALUE POSITION IS SAFE TO WRITE THROUGH** — this is not a hazard being correctly refused, it is a write being swallowed. Three independent reasons the write is sound: **(1)** a dict's hash is computed from the **KEY alone**, so the value is not in the bucket index and changing it cannot misplace the entry; **(2)** in-place value mutation neither resizes nor rehashes, so there is no realloc and hence **no iterator invalidation**; **(3)** the only implementation obligation is **dropping the old value** when the new one is installed — the same residual the R45 Track C prototype already names as its first task. **CONTRAST, do not conflate:** the KEY positions genuinely are hazardous — `for x in &set` (the element IS the key) and `for k in &dict` (the binding IS the key) write through into the bucket index; their correct answer is reject or mutable-private-copy per the bare-form ruling (`docs/define-gorget/decisions.md:2566-2578`, owner 2026-08-18). ✅ **RATIFIED 2026-08-27 as D49 (owner): `for k, v in &dict` WRITES THROUGH TO `v`; `k` stays a private copy.** This was the open surface question and it is now closed — `v = ...` IS the sanctioned spelling under `&`. `for k, v in d` (bare) stays two private copies per the 2026-08-18 ruling. The opposite disposition, `for x in &set` / `for k in &dict` (where the binding IS the key), is a HARD REJECT under the same entry — see `t0694`; do not conflate them. **The current behaviour was already a defect either way** — accepting a write and discarding it is the worst of the three available outcomes. Sibling `t0693`: the alternative spelling `for k in d: d[k] = 99` aborts the compiler at rc 101, so **today there is NO working in-loop dict-value update idiom** (snapshotting via `d.keys()` first DOES work). **INTENDED:** prints `99`.

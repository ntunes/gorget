  - **THE CLASS, STATED WITHOUT AN INSTANCE.** When a destination slot is typed from one thing and the value written into it is typed from another, the two backends fail DIFFERENTLY: the C backend takes the copy length from the DESTINATION FIELD (in bounds, but a TRUNCATED value), the LLVM backend takes it from the SOURCE VALUE (an out-of-bounds DESTINATION WRITE). **So a C lane that is value-clean is not evidence** (Core #8) — measured twice now, and both times the C lane printed the right answer.
  - ⚠ **THE REMAINING TYPE DISAGREEMENT, WHICH IS AN OWNER QUESTION AND NOT A DEFECT.** The result slot of a void `map` is still minted `Option[int64]` rather than the receiver's `Option[String]`: `infer_closure_return_type` drops a recovered `unit` and falls through to its `I64_TYPE` last resort. Regenerate: `grep -n 'I64_TYPE$' src/ir/lowering/exprs/methods.rs`. **Nothing is written into that slot any more**, so the program is well-defined either way, and the graduated fixture pins the ABSENCE OF THE OVERRUN rather than the slot's type. What the result TYPE of a void `map` SHOULD be stays unprescribed — `callable_param_return_type`'s own comment records the ratified-today reading (*"runs `f` for its effect and keeps the receiver's payload type"*), and the annotated sibling `Option[String] r = o.map(void_f)` is REJECTED with "the result is `Option[void]`". **A ruling must leave `option_map_void_callable_param_no_slot_overrun` green.**
  - ⚠ **THE INSTRUMENT SEES A SMALL CORNER OF THE CLASS (SIX Q#2), AND THAT IS WHY "no witness" IS NOT "no defect".** The emitted USER IR is not ASan-instrumented — only the runtime C is — so a stack OOB write is invisible unless it trips the `memcpy` interceptor's OVERLAP check, which needs the overrun to land EXACTLY on the source buffer. **BOTH instances this item ever had were found by that accident.** A static bounds check over the emitted IR is the instrument that could enumerate the class; ASan-clean on the LLVM lane is not evidence that no overrunning aggregate copy exists.

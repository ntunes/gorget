- **[HIGH — UNDEFINED BEHAVIOUR IN EMITTED CODE: the LLVM backend copies overlapping stack slots with `memcpy`. Found 2026-08-29 by the FIRST EVER genuine run of the LLVM security lane, ~8 minutes in.]**
  - **REPRODUCED AT HEAD, deterministically.** `gg build --sanitize --backend=llvm` on a nested `match` over `Option[Option[int]]`, run under ASan:
    ```
    ERROR: AddressSanitizer: memcpy-param-overlap: memory ranges
      [0xfffff103f7a8,0xfffff103f7c0) and [0xfffff103f7b8,0xfffff103f7d0) overlap
      #0 __interceptor_memcpy   #1 main
    Address ... is located in stack of thread T0
    ```
    Two stack slots 0x18 bytes apart, copied 0x18 bytes — an 8-byte overlap. `memcpy` requires non-overlapping ranges; this is UB. The C lane builds the same source, runs ASan-clean and prints `inner-none`, so **the C lane is the oracle and it is correct.**
  - **MECHANISM.** The backend emits aggregate copies as `call ptr @memcpy(ptr %dst, ptr %src, i64 N)` against its own `declare ptr @memcpy(ptr, ptr, i64)`, with nothing establishing that the two slots are distinct. Where the copy is between slots that alias, the emitted call is ill-formed. Today it happens to produce the right answer; nothing guarantees that, and this is precisely the class an optimizer is entitled to exploit. `llvm.memmove` (or proving non-overlap and keeping `memcpy`) is the shape to reach for.
  - **NOT CAUSED BY THE SANITIZER WORK, ONLY REVEALED BY IT.** The emitted `.ll` is byte-identical with and without `--sanitize` (verified by diffing the two; the only difference is a filename string constant). The defect is pre-existing and of unknown age.
  - **WHY IT WAS INVISIBLE.** `tests/security.rs` never read the backend selector, so `.github/workflows/ci.yml`'s "Security tests (LLVM + ASan + UBSan)" job was a verbatim re-run of the C suite; and `--sanitize` was separately a silent no-op under `--backend=llvm` (t0723). Both were fixed in R47 Track C, and the resulting first real run of that lane surfaced this. **It is the argument for that gate, in one defect.**
  - **BLAST RADIUS IN THE SUITE: exactly 2 of 153.** `attack_64_deep_option_unwrap` and `attack_70_inline_none_nested`, both now wired `security_safe_except_on(…, "llvm", "todo/t0729", …)`. ⚠ That helper is NOT a skip: on the LLVM lane it asserts the trip **still happens**, so fixing this defect turns those two RED and forces the annotation's removal. **Fixing this item means deleting both annotations and restoring the plain `security_safe` calls, and graduating the repro out of `known_gaps/`.**
  - **SHAPE NOTES.** Two nesting levels suffice; `Option[Option[Option[int]]]` behaves identically. A plain `.unwrap()` chain over the same type does NOT reproduce — the nested MATCH is load-bearing.

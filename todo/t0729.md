- **[HIGH — UNDEFINED BEHAVIOUR IN EMITTED CODE: an aggregate copy overruns its destination slot on the LLVM lane. RE-SCOPED 2026-09-04: the originally filed instance is FIXED and its fixture graduated; the CLASS is live at HEAD in a green, non-`#[ignore]`d, top-level fixture.]**
  - **REPRODUCED AT HEAD, deterministically.** `gg build --sanitize --backend=llvm` on `tests/fixtures/known_gaps/llvm_option_map_void_callable_result_slot_oob.gg`, run under `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1:exitcode=99`:
    ```
    ERROR: AddressSanitizer: memcpy-param-overlap: memory ranges
      [0xffffc20238b8,0xffffc20238d8) and [0xffffc20238c0,0xffffc20238e0) overlap
      #0 __interceptor_memcpy   #1 void_map
    ```
    ASan says OVERLAP because the overrun lands on the copy's own SOURCE, which sits immediately after the destination slot. It is an out-of-bounds DESTINATION WRITE. The C lane builds the same source, prints `hello%` and is ASan- and leak-clean; `hello%` is the intended output on both lanes.
  - **MECHANISM — TWO DEFECTS, ONE LOUD.** Measured on the same source at HEAD, both lanes:
    ```
    LLVM   %s17 = alloca %Option__int64_t              ; 16 B = 8 tag + 8 payload
           call ptr @memcpy(ptr %s17+8, ptr %s16, i64 32)    <- SOURCE-sized
    C      __gg_Option__int64_t __s17 = {0};
           memcpy(__v44, __v30, sizeof(int64_t));            <- DEST-FIELD-sized
    ```
    **The mistyped result slot is UPSTREAM of both backends** — both allocate a void `map`'s result as `Option[int64]`. What differs is the aggregate copy's LENGTH: the C backend takes it from the DESTINATION FIELD and writes 8 bytes (in bounds, but a TRUNCATED `String`); the LLVM backend takes it from the SOURCE VALUE and writes 32.
  - ⚠ **THE C LANE'S CLEANLINESS IS NOT A VINDICATION OF THE LOWERING (Core #8).** It is clean because a void `map` DISCARDS its result, so nothing reads the truncated payload. **And fixing the LLVM length alone would silence ASan while leaving the type disagreement in place** — the same trap this item's ORIGINAL prescription (`llvm.memmove`) was: memmove tolerates overlap and would have preserved the overrun, making a live defect invisible.
  - **WHAT IS OPEN, AND IT IS NOT A SCOUT'S CALL.** The result TYPE of a void `map` is undecided. `tests/fixtures/combinator_callable_param_same_type.gg`'s header records that `callable_param_return_type` DROPS a `unit` recovery ON PURPOSE — minting `unit` as the result payload measured rc 139 on BOTH backends, strictly worse than the `I64_TYPE` default it replaced — and the annotated sibling `Option[String] r = o.map(void_f)` is REJECTED with "the result is `Option[void]`". So the `I64_TYPE` fallback is a documented retreat, not an oversight. Sizing LLVM's aggregate copies from the DESTINATION (as C already does) removes the memory-unsafety; deciding the slot's type removes the truncation.
  - **BLAST RADIUS: A GREEN TOP-LEVEL FIXTURE.** `tests/fixtures/combinator_callable_param_same_type.gg` — GREEN, non-`#[ignore]`d, top-level — contains this exact cell (`void_map`) and trips identically: rc 99, `memcpy-param-overlap`, `#1 void_map`. A plain `--backend=llvm` build of either program exits 0 with correct output — benign BY LUCK, which Core #8 refuses.
  - ⚠ **THE INSTRUMENT SEES A SMALL CORNER OF THE CLASS (SIX Q#2).** The emitted USER IR is not ASan-instrumented — only the runtime C is — so a stack OOB write is invisible on this lane unless it trips the `memcpy` interceptor's OVERLAP check, which needs the overrun to land EXACTLY on the source buffer. **This item's original instance was found by that accident, and so was this one.** A static bounds check over the emitted IR is the instrument that can enumerate the class; ASan-clean on the LLVM lane is not evidence that no overrunning aggregate copy exists.
  - **WHAT THE ORIGINAL FILING COVERED, AND WHY IT IS CLOSED.** A nested `match` over `Option[Option[int]]` with the inner `None()` built inline allocated that temp with the OUTER Option's type, so the copy length followed the wrong type and overran by 8. That is FIXED: `%s2` is now `%Option__int64_t` and the copy is 16 — exactly the destination field's size. **Arch-independent by direct x86_64 measurement**, not inference: filing-era `memcpy(224(%rsp), 240(%rsp), 24)` — [224,248) against [240,264), an 8-byte overlap; HEAD `memcpy(232(%rsp), 248(%rsp), 16)` — [232,248) against [248,264), disjoint. The length is a CONSTANT OPERAND in the emitted IR, so in-bounds-ness is decidable from the IR alone and no frame layout on any target changes it. The repro graduated to `tests/fixtures/nested_option_match_inline_some_none.gg` with two live tests, and the two `security_safe_except_on` annotations it reddened (`attack_64_deep_option_unwrap`, `attack_70_inline_none_nested`) were removed.
  - ⛔ **DO NOT re-derive the closure from a SAME-BASE aliasing scan.** A detector that resolves both memcpy operands to their base alloca and flags same-base pairs returns ZERO on the ORIGINAL reproducing IR — the operands are two DISTINCT allocas and the overrun merely lands on the neighbour. Such a scan would have returned zero on the buggy compiler too. The enumerating instrument must be a BOUNDS check, not an aliasing check.

- **🆕🐛 [MED — DESIGN SMELL: a type whose whole reason to exist is its two ends has no way to name them.
  Surfaced 2026-09-03 by the R49 Track F closure-shape work, which had to give Deque its own row in a
  protocol-keyed table and noticed the aliasing that made the row necessary.]
  `Deque` IS `Vector` WITH A DIFFERENT NAME — there is no deque API.**
  - **MEASURED at HEAD** (`gg check`, one probe each):

    | program | result |
    |---|---|
    | `Deque[String] d = Deque[String]() ; d.push_back("a")` | `E_NoMethodFound: no method 'push_back' found on type 'Deque[String]'` |
    | `Deque[int] d = Deque[int]() ; d.push_front(1)` | `E_NoMethodFound: no method 'push_front' found on type 'Deque[int]'` |
    | `d.push("a")` / `d.each(…)` / `d.sort_by_key(…)` | ✅ work — they are Vector's |

  - **MECHANISM.** `src/ir/lowering/builtins.rs:633` is literally
    `methods: VECTOR.methods, // Same interface as Vector`. The protocol carries its own
    `base_name`, `drop_fn`, `clone_fn` and `collection_kind`, but its METHOD SET is Vector's by
    reference, so nothing end-specific can be declared without breaking the alias.
  - ⭐ **THE COMPILER ALREADY BELIEVES THOSE METHODS EXIST — in the layer BELOW the one that rejects them.**
    `src/ir/lowering/exprs/methods.rs:2747` and `:2820` both list
    `"push" | "add" | "extend" | "send" | "push_back" | "push_front"` as owning-value / consuming positions,
    and `docs/devbook/11-copy-on-write.md:442` documents that row as the CoW materialization boundary. So
    the ownership rules for `push_back`/`push_front` are written, documented, and **unreachable**: no
    receiver type in the language declares either method. That is a Core #14 shape — an invariant asserted
    in a table with nothing enforcing that the table's subjects exist.
  - **INTENDED — and it is a real design question, not a one-line fix.** Either
    **(a)** Deque gets its own `methods` array with `push_back` / `push_front` / `pop_front` / `pop_back`
    (and `push`/`pop` as aliases for the back), which is what the name promises and what the consuming-position
    tables already assume; or **(b)** Deque is retired as a distinct protocol, because a Vector alias that
    cannot be used as a deque earns nothing and costs a protocol row every table has to remember (this one,
    `CLOSURE_SHAPES`, `HANG_CENSUS`-style censuses, …). ⛔ What is not defensible is the current state:
    a type named for its ends that rejects both.
  - ⊕ **NO DOC TEACHES THE MISSING API**, so nothing is currently lying to a reader —
    `grep -rn "push_back\|push_front\|pop_front" docs/book/ docs/devbook/` finds only the CoW
    consuming-position table. That makes (b) cheaper than it looks and (a) purely additive.
  - **REPRO OWED:** a `known_gaps/` cell per end-method asserting the INTENDED behaviour once the direction
    is picked — under (a) the four methods working, under (b) the `E_NoMethodFound` with a diagnostic that
    says Deque has no end-specific API rather than implying a typo.

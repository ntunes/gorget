- **🆕⚖ [HIGH — AN UNRATIFIED DESIGN AXIS THE COMPILER HAS ALREADY ANSWERED THREE DIFFERENT WAYS. Owner asked to revisit it 2026-09-06; measured at HEAD the same day.]**

  ## THE LEDGER DOES NOT SETTLE IT
  `grep -niE 'namespace' docs/define-gorget/decisions.md` → **two hits, both about DIAGNOSTIC naming.** ⇒ **the type-vs-value namespace axis is unratified.** The nearest thing is **D0′'s shadow-reject (owner 2026-09-05)** — *"a **value** may not take a **type's** name"* — which **presupposes** an answer rather than stating one, and is **UNBUILT**.

  ## MEASURED AT HEAD — the compiler answers differently in three positions

  | probe | result |
  |---|---|
  | `struct Foo` + `int Foo = 5` (declare both) | **check rc 0, builds, runs, prints 5** |
  | `int Vector = 5` — value takes a BUILTIN type's name | **check rc 0, builds, runs, prints 5** |
  | `struct Callable[T]` — type takes a builtin type's name | **check rc 0** |
  | `struct Owned[T]` — the name `[[t1408]]` says is in NO type list | **check rc 0** |
  | `Callable[int(int)] Callable = twice` — value shadows the type **in its own declaration** | **check rc 0, runs, prints 42** — the TYPE position still resolves |
  | ⛔ `struct Foo` + `int Foo = 7`, then `Foo f = Foo(1)` | ⛔ **check rc 1 — `E_NotAFunction`: `` `Foo` is not a function ``** |

  ⇒ **DECLARATION: separate. TYPE POSITION: separate, the type still resolves. CALL POSITION: they COLLIDE, the VALUE WINS, and the type becomes unreachable.**

  ⛔ **AND THE DIAGNOSTIC NAMES THE WRONG CAUSE.** The user wrote a constructor call; the compiler reports *"`Foo` is not a function"*. The real cause is that a local shadowed the type — **nothing in the message says so**, so the fix a reader reaches for (make `Foo` a function) is wrong.

  ## WHY THIS IS NOT MERELY COSMETIC
  The current state is **not** "separate namespaces" and **not** "unified" — it is **separate where nothing forces a choice and unified where something does**, with the tie broken silently in favour of the value. **A user who names a local after their own struct loses the constructor**, at a distance, with a misleading message.
  ⊕ **`[[t1408]]` shows the type side cannot even answer consistently:** *"is this name a TYPE?"* has **two independent implementations** — a hardcoded `BUILTIN_GENERIC_TYPES` list in `resolve.rs` and a separate `matches!` in `types.rs` — **and `Owned` is covered by neither.** A namespace with two incomplete oracles cannot enforce a rule about itself.

  ## THE DECISION THIS NEEDS
  **(1) UNIFY** — one namespace; a name is a type or a value, never both. D0′'s shadow-reject becomes the enforcement, and its scope question (does it also forbid a **type** taking a builtin type's name?) is then answerable rather than guessed. Cost: every collision currently accepted becomes an error, and `[[t1408]]`'s two oracles must first be merged into one, or the rule is enforced by a list that does not know about `Owned`.
  **(2) KEEP SEPARATE** — then the CALL-position collision is a **defect to fix**, not a rule to enforce: a constructor call must reach the type even when a value of that name is in scope, and D0′'s shadow-reject should be **withdrawn** rather than built.
  ⚠ **Either answer is coherent. What is not coherent is today's mixture**, and it is the mixture that produces a wrong diagnostic on ordinary code.

  ⊕ **`[[t1548]]` is HELD on this** — it assumed a type-shadow ruling that was never made. **Answering this resolves it in one direction or removes it in the other.**

  ---
  ## ⭐ THE `[]` OVERLOAD IS THE SAME QUESTION (owner, 2026-09-06 — measured the same day)

  `[]` carries **two meanings**: **generic instantiation** (`Vector[int]`, `Pair[int](4, 5)`) and **indexing** (`v[i]`). **Both are live and both work:**

  | probe | result |
  |---|---|
  | `Pair[int](4, 5)` — instantiate-then-call in one expression | **rc 0, runs, prints 4** |
  | ⛔ `struct Holder[T]` **plus** `Vector[int] Holder = [10,20,30]`, then `Holder[1]` | **rc 0, runs, prints 20** — it **INDEXED** |

  ⇒ **`x[a](b)` has two readings, and today the tie is broken silently in favour of the VALUE** — the same rule as the call-position collision above, and equally unstated.

  ⭐⭐ **AND THAT PROVES THE MACHINERY FOR THE FIX ALREADY EXISTS.** In the second probe `Holder` is **both** a generic type and a value **in the same file**, and `Holder[1]` still resolved to indexing. **A parser committing on syntax alone could not have known** — so **RESOLUTION already decides which meaning `[` carries.** ⇒ **under a unified namespace the head is exactly one thing, so `x[a](b)` is DETERMINED with no new rule and no new syntax.**

  ## ⭐ MIGRATION COST, MEASURED: **ZERO**
  **650** user type names are declared in-tree. **SAME-FILE collisions — a type and a value sharing a name in one file: 0, across 0 files.**
  ⚠ **A first pass said 47 and was WRONG**: it collected type names tree-wide and value names tree-wide, so a value `M` in one file "collided" with a type `M` in an unrelated file. **Per-file is the only measurement that means anything here, and it is zero.**
  ⇒ **unifying breaks nothing that exists.** The cost is entirely in `[[t1408]]`'s prerequisite — two incomplete oracles for *"is this name a type?"* must merge first, or the rule is enforced by a list that does not know about `Owned`.

  ## ⚠ NOT THE SAME QUESTION AS *"TYPES AS VALUES"*
  Unification asks whether a **NAME** may denote both a type and a value. **Types-as-values** asks whether a type **IS** a first-class value. **Unification is a PRECONDITION for types-as-values to be coherent** (otherwise *"which `Foo`?"* has no answer) — **but it does not commit to it.** Keep them separable so the first decision does not silently buy the second.

- **🆕🧹 [MED — A CORE #6 LADDER STUCK ON ITS MIDDLE RUNG, DELIBERATELY. Filed 2026-09-06 by R51 Track A's executor.]**

  `GG_BOX_RECEIVER_GUARD` ships at **`count`**, and `box_receiver_guard_wired_into_ci` asserts that value rather than `fatal`. Three measured reasons, in ascending order of how hard they are to fix:

  1. **0 RESIDUAL IS NOT 0 DEFECTS.** Under the receiver-place fix the declaration guard is silent on every constructed cell — including `todo/t1513`'s program, which still prints garbage at rc 0. A `fatal` guard at 0 residual would stand GREEN over that. (Measured both ways: shipping state + `fatal` → build rc 0, program garbage at rc 0; pre-fix control → rc 101.)
  2. **THE COUNT IS A FUNCTION OF PROGRAM SHAPE.** `ensure_extern` synthesizes ONE declaration per mangled symbol, so the guard fires once per SYMBOL: a file with five broken receiver places reports **1**. And placing a working owned-local read in front of a broken one in the same file takes a genuinely-broken pre-fix program to **0** fires. ⇒ a count-mode ratchet on it is **not monotone in the defect count**, which is the property Core #6 assumes.
  3. **THE PROMOTION NEEDS A CORPUS ARGUMENT.** Not "`t1513` is closed" — the shape-sensitivity in (2) survives that closure. What would justify `fatal` is a demonstration that no *program shape* can drive a live defect to 0 fires, which is a claim about the emitter, not about any one item.

  ⊕ The value guard `validate_box_get_ptr_result_consumed` is a different case: it is permanently RED at 3 known programs and its burn-down direction is `todo/t1513` + `todo/t1526`'s write sites. A permanently-red-at-n guard is the NORMAL case for the ledger idiom (`tests/gaps/BOX_RECEIVER_BURNDOWN.txt`), not a defect in it.

  **INTENDED:** either the declaration guard's subject becomes per-defect rather than per-symbol and it graduates to `fatal`, or the reason it stays at `count` is a ratified property of the emitter rather than an open item.

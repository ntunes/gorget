- **[MED — ggdef ORACLE HYGIENE; the same generic equip gets two different subset answers depending on how it is spelled] `register_equip` (`spec/ggdef/src/elaborate/mod.rs`) rejects on `eq.generic_params.is_some()`.** That field carries only the LEADING type-parameter list. So:
  - `equip Cell[T]:` — `generic_params == None`, the type args ride on the target — **ELABORATES**. `cargo run -q -p ggdef -- run tests/fixtures/cow_generic_equip_mutator_view_uaf.gg` prints `helloworld`.
  - `equip [T] Cell[T]:` — `generic_params == Some([T])` — **REJECTED** with `elaboration error: generic \`equip\` blocks are excluded from phase 0`. `cargo run -q -p ggdef -- run tests/fixtures/cow_generic_equip_named_recv.gg` is the standing repro.
- **These are the same construct.** Both fixtures declare a generic `Cell[T]` and equip it; the only difference is where the type parameter is written. A subset boundary drawn on a spelling is a Layering-rule-2 defect in the oracle (a decision made from surface syntax rather than from typed metadata), and it means the oracle's coverage of the generic-equip class depends on an author's stylistic choice.
- **This is oracle hygiene, not a lowering bug** — both Rust gg and the self-host accept both spellings and agree on both fixtures. It matters because ggdef is the truth axis: a fixture written one way gets adjudicated and the identical program written the other way does not.
- **Two candidate resolutions, and picking between them may be an owner call:** (a) elaborate BOTH spellings (see `todo/t0874` — the exclusion goes away entirely); (b) reject BOTH until generic equips are in the subset, which loses the currently-working `equip Cell[T]` adjudication including the one that caught a live use-after-free. (b) is strictly worse for coverage; (a) is the real fix and is the same work as `t0874`. Either way the gate must stop keying on the spelling.

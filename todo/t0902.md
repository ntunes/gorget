- **🆕🐛 [MED — C BACKEND ONLY, LLVM IS CORRECT (Core #9 lane divergence); `gg check` rc 0, `gg build` fails at `cc`; found 2026-08-31 by R48 Track D2 while widening t0840's payload-type axis] `Shared[String]("a literal")` does not compile on the C lane.** Three lines:
  ```
  void main():
      Shared[String] s = Shared[String]("hi")
      print(f"{s.get()}")
  ```
  `gg build` → `error: incompatible type for argument 1 of 'Shared__GorgetString__new'`. The wrapper the same backend emitted one line earlier is `static inline Shared__GorgetString Shared__GorgetString__new(Str val)` (`emit_shared_wrapper`, `src/backend/c_lir/helpers.rs`), and the call site is `Shared__GorgetString__new((const char*)__v0.data)` — the `Str` argument marshalled as if the parameter were tagged `CStr`. `--backend=llvm` builds and prints `hi`, so the C emit boundary is the lane that is wrong.
- **DISCRIMINATED from `t0840` (the handle-marshalling class it was found beside):** no container, no element slot, no `AbiKind::VoidElem` position. This is argument marshalling into a synthesized inline wrapper, and it reproduces with the `Shared` on its own.
- **THE SHAPE MATTERS:** feeding the SAME constructor a `String` VARIABLE (`String j = a + b; Shared[String](j)`) compiles and runs on both lanes. That is why `tests/fixtures/known_gaps/shared_vector_payload_types.gg` builds its payload from a concatenation — a dodge around THIS gap, recorded here rather than buried there.

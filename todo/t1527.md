- **🆕🚨 [HIGH — `gg check` ACCEPTS a `shared` variable passed where `Shared[T]` / `Mutex[T]` / `RWLock[T]` is expected, and the compiled program SIGSEGVs. Found 2026-09-06 by R51 Track C while building the POSITIVE controls for the D51 coercion-identity migration.]**
  - **THE SHAPE IS THE COERCION ARM'S OWN STATED RATIONALE.** `src/semantic/typecheck.rs`'s shared-wrapper arms carry the comment *"A shared variable has type T but may be passed where Mutex[T] or Shared[T] is expected (e.g., spawned functions that receive the raw wrapper)"*. That is exactly this program, on the **BUILTIN** path — no user shadow, nothing exotic:
    ```
    void worker(Shared[int] c):
        print(1)

    void main():
        shared int counter = 0
        worker(counter)
    ```
    **MEASURED at `8e6b8d2d3`:** `gg check` → rc 0, *"OK: no semantic errors"*. `gg run` → C emits `warning: passing argument 1 of 'worker' makes pointer from integer without a cast [-Wint-conversion]` (`expected 'void *' but argument is of type 'int64_t'`) and the binary is **terminated by SIGSEGV (signal 11)**. The `async` + `spawn worker(counter)` spelling — the one the comment literally describes — crashes identically, in `__shared_token_worker`.
  - **⚠ PRE-EXISTING, AND MEASURED AS SUCH RATHER THAN ASSUMED.** R51 Track C reverted its whole diff, rebuilt, and re-ran: same `-Wint-conversion`, same SIGSEGV. The migration it shipped moves the arm's guard from a name compare to a typed flag and answers `true` for the builtin on both sides of the change; it touches no lowering.
  - **⚠ IT IS ALSO WHY FIVE FIXTURES ARE `check`-ONLY.** `tests/fixtures/coercion_identity/builtin_{shared,mutex,mutex_import,rwlock_import,mutex_ret}_coerces.gg` are the accept-side pins for D51's four seed seams and for `unify`'s SECOND coercion arm. They are wired to `check_gg_ok`, **not** `run_gg`, solely because of this defect — promote all five to `run_gg` the round it is fixed.
  - **⛔⛔ IT IS TWO DIRECTIONS, NOT ONE, AND THEY FAIL DIFFERENTLY. The arms are transparent BOTH ways** (`Generic → T` and `T → Generic`), and the mirror of the program above is a live second cell:
    ```
    int take_int(int x):
        return x + 1

    void main():
        Mutex[int] m = Mutex[int](7)
        print(take_int(m))
    ```
    **MEASURED at `24156ed68`:** `gg check` rc 0; C emits the INVERSE conversion warning (`makes integer from pointer without a cast`, *"expected `int64_t` but argument is of type `void *`"*); the program **exits 0** having printed a raw handle pointer where `8` was expected (e.g. `187651999621793` — ⚠ **A POINTER VALUE, DIFFERENT ON EVERY RUN under ASLR**; the digits illustrate, they do not reproduce).

    |---|---|---|---|
    | **A** | bare `T` → `W[T]` parameter | `int64_t` → `void*` | **SIGSEGV, signal 11** |

  - **⚖ OWNER ASK — THE DIRECTION IS UNRATIFIED, AND IT IS TWO QUESTIONS.** That the compiler must not accept-then-crash and must not accept-then-print-a-pointer is not in doubt; **which** correct behaviour it owes is not, and ⛔ **the two arms do not share an answer:**
    - **ARM A — (a) MAKE IT WORK** = lowering MATERIALIZES a wrapper around a scalar at the coercion boundary, so the callee gets a real `Shared[int]` handle. This is what `gg check`'s acceptance currently promises and what the arm's own comment says the arm is FOR. **(b) REJECT** = a `shared int` is an `int` with a concurrency marker; there is no `Shared` allocation anywhere in the program, and conjuring one silently is the kind of magic D31's spelling philosophy refuses.
    - **ARM B — (a) MAKE IT WORK is a MATERIALLY HARDER QUESTION, and phrasing it as "materialize the wrapper" hides that.** The conversion here runs the other way: it would UNWRAP a live `Mutex[int]` into an `int` at an argument boundary — **an IMPLICIT LOCK ACQUISITION**. ⚠ **CITE THIS CAREFULLY: D53's ruling TEXT is about `E_MoveWithoutOperator` at the enumerated consuming positions, not about lock acquisition — an owner following a bare "D53" pointer will not find `.lock()` there.** What D53 supplies is the PREMISE, in two parts: `Mutex`/`RWLock`/`Guard` are in its single-owner set, whose whole point is that these values have no implicit-copy path and must be handed over in writing; and the way a program reads a lock's payload today is the explicit `m.lock()` → `Guard[T]`, which is live and is what every fixture in `tests/fixtures/mutex_*` does. So the inference — *a lock must not silently decay to its payload at a call site* — is D53's spirit applied to a position D53 never enumerated, which is exactly why it is an ASK and not a citation. **(b) REJECT** is correspondingly cheaper here than for arm A: nothing about the ratified design suggests a lock should silently decay to its payload at a call site.
    ⇒ **an answer of "(a)" to arm A does not imply "(a)" to arm B, and a single yes/no would ratify the harder half by omission.** Both repros assert **(a)** — matching what the checker already says — but that is the filer's choice, not a ruling. **Same shape as `[[t0710]]` before D51 ratified its direction.**

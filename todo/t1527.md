  ## ⭐ THE THREE OPTIONS, AND WHY THE ASYMMETRIC ONE IS REFERENCE-GRADE (orchestrator, 2026-09-06, re-measured at HEAD)

  **Both arms pass `gg check` and `gg build`. Measured:** arm A **`run_rc = 139` (SIGSEGV)**; arm B **prints a pointer at `rc 0`** where `8` is correct (the value is ASLR-varying — illustration, never a constant to reproduce).

  **OPTION 1 — REJECT BOTH.** ⛔ **Rejects a shape D53 RATIFIES.** `shared int x` desugars to the `Shared[T]` wrap, so passing it where `Shared[int]` is expected is the **intended** use — rejecting it makes `shared` unusable at its own primary call site.

  **OPTION 2 — MATERIALIZE BOTH.** Arm A wraps (correct, cheap). ⛔ **Arm B UNWRAPS — an implicit lock acquisition at an ordinary call argument, with NO keyword and NO ordering discipline**, where `shared`'s ratified implicit acquisition has **both** (a keyword opt-in, and *"the compiler emits the ordering"*).

  ## ⭐ OPTION 3 — ASYMMETRIC: **FIX A AS A DEFECT, DECIDE B AS SEMANTICS.** Reference-grade.
  It is reference-grade because **it separates a BUG from a DECISION instead of treating both as one question.**
  - **ARM A IS NOT A SEMANTICS QUESTION.** D53 ratifies the `shared int x` → `Shared[T]` desugar, so the checker accepting it is **correct**; the SIGSEGV is a **LOWERING GAP** — the desugar yields the right TYPE and the wrong RUNTIME REPRESENTATION. **Nothing to rule on: make the lowering match the ratified desugar.**
  - **ARM B IS THE QUESTION, and it is the cell D53 never enumerated.** Regenerate: `grep -n 'no operator is needed' docs/define-gorget/decisions.md` — D53 rules that at a plain non-consuming call they are *borrowed, so no **operator** is needed*. **That is a statement about the MOVE OPERATOR and is silent on whether the value may silently change TYPE there.** Rejecting arm B is consistent with D53's own framing of an explicit `Mutex` as the **systems path**.

  ## ⚠ THE SUB-QUESTION A RULING MUST NOT LEAVE IMPLICIT
  **`shared int c` passed to an `int` parameter is ACCEPTED TODAY** — measured, `check rc 0`, with only a warning that `c` never crosses a concurrency boundary. That is the **unwrap direction for `shared`**, and it is **not** obviously the same cell as arm B.
  ⇒ ⭐ **the rule is probably not *"wrapper types never coerce"* but *"the `shared` KEYWORD buys implicit acquisition; an explicitly-spelled `Mutex` does not."*** **Say which, or an implementer will pick one and the other becomes an accident.**

  ## ⭐ WHAT `shared` ACTUALLY IS — and the precise arm-A mechanism (owner asked 2026-09-06)

  **It is NEITHER `Shared[T]` nor `Shared[Mutex[T]]` categorically.** From the introducing commit `a666c39df` (2026-03-06, *"`shared` keyword with token semantics for safe concurrency"*, modelled on **DragonFlyBSD's kernel token model**):

  > *"A `shared` binding is **always ARC-wrapped** (heap-allocated, atomically reference-counted) and **optionally sync-wrapped**. **Custody Flow Analysis (CFA)** in the borrow checker determines whether a Mutex, RwLock, or Atomic is also needed based on how the binding's borrows cross spawn and await boundaries."*

  ⇒ **ARC is UNCONDITIONAL; the LOCK is a per-binding STRATEGY.** Four of them (`src/semantic/mod.rs:64-70`, regenerate `grep -n 'ArcOnly' -A 8 src/semantic/mod.rs`): **`ArcOnly` · `ArcMutex` · `ArcRwLock` · `ArcAtomic`**, carried on `AnalysisResult` as *"`shared`-binding strategies"* and assigned by the **final CFA pass** (`docs/devbook/10-ownership-safety.md`). `shared(rwlock)` / `shared(atomic)` are **user overrides**; bare `shared` lets CFA pick.

  ⚠ ⛔ **THEREFORE D53's SENTENCE IS A SIMPLIFICATION, NOT THE GENERAL RULE.** *"The documented concurrent counter is already `Shared[Mutex[int]]`; `shared int x` desugars to the same wrap"* is **true of the `ArcMutex` case D53 was discussing** — a counter mutated across spawn — and **false as a universal**: a `shared` binding that is read-only across boundaries is **`ArcOnly`**, i.e. `Shared[T]` with no lock at all. **Anyone reasoning from that sentence as a definition will get the wrong type.**

  ## ⭐ AND THE ARM-A MECHANISM IS SHARPER THAN "A LOWERING GAP"
  Emitted C for the arm-A repro (`gg build --emit-c`):

  ```c
  __v1 = (int64_t)0LL;
  __v2 = Shared__int64_t__new(__v1);   // the ARC wrap IS built, into __v2 (void*)
  ...
  worker(__v8);                        // but __v8 is __coal3 — an int64_t
  ```
  `void worker(void* __p0);` — the parameter ABI is correct.
  ⇒ **the wrap is NOT missing. The call site reads the WRONG SSA VALUE** — the pre-wrap scalar instead of the handle. ⭐ **That confirms arm A is a lowering defect and NOT a semantics question, on evidence rather than on a reading of D53** (which, per the correction above, could not have settled it anyway).

- **[LOW — ggdef SUBSET GAP, Core #9 note] `meta for` as a MATCH-ARM generator is outside the ggdef subset, so that shape has no definitional adjudication.** `spec/ggdef/src/elaborate/mod.rs` rejects it by name: *"`meta for` match arms are phase 2"*, raised when a `match`'s arm list contains an item that is not a plain arm. Verify: `cargo run -q -p ggdef --release -- run tests/fixtures/cow_user_mutator_meta_generated_arm.gg` → `ggdef: elaboration error @ …: \`meta for\` match arms are phase 2`.
- **Why it matters now.** `tests/fixtures/cow_user_mutator_meta_generated_arm.gg` (landed 2026-08-29 with the `t0699` fix) pins a use-after-free that only reproduces in a `meta for`-generated arm. It is verified on C, LLVM and the self-host lowerer lane, but the ORACLE cannot see it: on this shape "all three implementations agree" is the only available evidence, which Core #8 rates necessary-not-sufficient. The same shape carries real stdlib code — `lib/xtd/dataframe.gg`'s `Column` methods (`null_count`/`is_null`/`col_len`/`value_as_str`/`dtype_name`) are all written this way — so the unadjudicated surface is not exotic.
- **Fix** = elaborate the generator: bind the meta loop's variables per iteration and emit one `StmtArm` per binding, the same expansion the two compilers already perform. The neighbouring `match guards are outside the phase-0 subset` rejection in that function is a separate, independently-filed boundary — do not conflate them.

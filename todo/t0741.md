- **🆕🐛 [HIGH — latent today, but it is the reason a shipped safety check has to be weaker than its Rust counterpart; found R47 Track D1 by MEASUREMENT, not by reading] The self-host resolves an identifier receiver to the WRONG definition in two independent shapes, and answers a confident wrong TYPE for it.** Not "unknown" — *wrong*. `ctx.resolution_map` and `types.expr_types` are both keyed on `span.start`, and two mechanisms make that key lie:

  1. **A `match` ARM BINDING leaks past its arm.** A LATER local with the same name resolves to the arm's binding. `case Ok(v)` binds an `int`; the subsequent `Vector[int] v` is then answered as `int` by `infer_expr_type`. Minimal shape committed at `tests/fixtures/sh_match_arm_binding_shadow_shape.gg` (wired LIVE as `sh_match_arm_binding_shadow_shape`; it is a SHAPE PIN, green on every lane — see below for why there is no red repro). Same shape in the corpus: `tests/fixtures/generic_typearg_well_typed.gg:38-39`.
  2. **An f-string interpolation's sub-expressions carry SYNTHETIC spans**, and the map mis-answers there too. `char_methods.gg`'s `String c1` reads back as `int` inside `f"{c1.is_alphanumeric()}"`; so do `dataframe_basic.gg`'s Column, `tensor_basic.gg`'s Tensor, `tensor_linalg.gg`, `tensor_reshape.gg`, `dataframe_*.gg` (9 files) and `string_conversions.gg`'s `Option[int]`. The EFString arm of `walk_expr_closures_inner` (`self_host_typechecker/typecheck.gg`) already documents that inference is unreliable there — it deliberately scopes its own inference to four tag-check intrinsics for this reason — but the scope of the unreliability was never measured.

  - **WHY THERE IS NO RED REPRO, and why it is filed anyway.** The defect is currently LATENT at runtime: the lowerer resolves these identifiers correctly, so only the typechecker's answer is wrong and nothing downstream consumed it. It became visible the moment something did. R47 Track D1 added `reject_no_method_on_primitive` (`self_host_typechecker/typecheck.gg`), the self-host mirror of Rust gg's `E_NoMethodFound` chokepoint for a method absent on a primitive receiver, and with a per-receiver-kind admission table **it refused 12 VALID corpus programs** — every one of them an instance of 1 or 2 above.
  - **WHAT IT COSTS TODAY.** The reject had to be weakened to survive: it consults the UNION of every primitive's method table instead of the receiver's own (`any_prim_method_admitted`), plus a registry-wide name check, so it refuses only a name that is *nobody's* method. That is sound but strictly weaker than Rust, and it is what leaves `known_gaps/sh_len_on_float_silently_miscompiles.gg` open (`3.0.len()` accepted, runs, prints garbage; Rust rejects).
  - **THE EXECUTABLE INSTRUMENT** — this is what makes the item verifiable rather than a note. Restore the per-receiver-kind dispatch in `reject_no_method_on_primitive` (reject when the RECEIVER's own table has no entry), rebuild the self-host driver, and run the emit-C census over the corpus: for every `tests/fixtures/*.gg` and `spectests/run/*.gg`, run `driver <f> lib --emit-c` and compare the accept/reject verdict against the pre-change driver. **Today that census reports 12 new rejects of programs Rust gg accepts; when this item is fixed it reports zero, and `sh_len_on_float_silently_miscompiles.gg` graduates in the same round.**
  - **DO NOT "FIX" THIS BY NARROWING THE ADMISSION TABLE.** That re-introduces the 12 false rejects. The fix is at the resolution layer — the write site — not at the reject that reads it (Core #1).

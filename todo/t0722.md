- **🆕🚨 [HIGH — a FALSE INVARIANT COMMENT that a fix is actively resting on (Core #14), found 2026-08-29 by the R46 Track C scout, orchestrator-verified at HEAD]** `src/ir/lowering/stmts/patterns.rs` (~`:205-215`) asserts, of match-scrutinee staging: *"Collections (Vector/Dict/Set/HashMap/HashSet/Deque) and `String` are safe under value-typed Borrow regardless because they carry a runtime `cap == 0 ↔ view` discriminator — the borrowed copy is marked as a view and drops elide."* **For an owned `String` that is false.** `AssignMode::Borrow` lowers to `gorget_string_copy_cow` (`src/backend/c/runtime/runtime_string.c:215`), which **deep-copies**; it does not produce a `cap == 0` view. The comment describes a safety property the runtime does not provide, and `src/ir/lowering/exprs/insts.rs:3022` already documents this exact failure mode in another position — so the knowledge exists in-tree and this site contradicts it.

The scout prototyped **both** obvious fixes for `t0705` and each closed one cell while leaving the other, *because* of this third defect underneath: `source_at_last_use` is computed only for `Expr::Identifier` (`patterns.rs:~401`), so an unnamed temp can never reach `AssignMode::Move`, yet the transfer block fires anyway — unregistering and zeroing the source into a non-owning view. **`t0705` is not fixable as a one-liner until this is settled**, and any attempt will look half-successful, which is the dangerous shape.

- **🆕🐛 [HIGH — Core #9 LANE DIVERGENCE, under-rejection: self-host ACCEPTS a D53 unique-lock copy that Rust rejects] `variant_field_types` has no rows for IMPORTED struct fields.**
  ```
  # holder.gg
  struct XHolder:
      Mutex[int] lock
      int tag
  # main.gg
  from holder import XHolder
  XHolder h = XHolder(Mutex[int](5), 1)
  v.push(h.lock)
  ```
  → Rust gg: `error[E_MoveWithoutOperator]: cannot copy \`h\` … wrap the sub-place in \`Shared[Mutex[T]]\``. Self-host driver: **rc=0, emits 4214 bytes of C.**
  Measured at HEAD on both lanes; the self-host verdict is identical before and after R48 Track P's structural-resolver swap, so this gap is upstream of it and untouched by it.
  **THE DISCRIMINATING AXIS IS CROSS-MODULE, NOT GENERIC-VS-CONCRETE** — and that matters, because the long-standing note at `infer.gg:416-425` says the table *"misses generic-struct / imported / equip fields"*, which is now only two-thirds true. Verified this round: the LOCAL concrete form rejects (`d53_unique_lock/mutex_field_local_push_reject.gg`) and so does the LOCAL GENERIC form (`d53_unique_lock/mutex_generic_struct_field_push_reject.gg`). Only the imported form slips. Re-measure the "45 false positives" figure in that note before resting on it.
  ⊕ **THIS ITEM CORRECTS `todo/t0392` RV-A(5)**, which is the ORIGIN of that premise: *"self-host has NO complete per-struct field registry (variant_field_types is lazily populated … the scout measured 45 false positives without it)"*, filed 2026-07-16. The prerequisite-track conclusion still stands — a complete registry is the right fix — but "lazily populated" is not the mechanism. The table is populated EAGERLY and COMPLETELY for the module being checked (`typecheck.gg:5974-5985`, walking `sdef.fields` per `IStruct` item); it is MODULE-LOCAL, and that is why imported structs miss. Whoever picks up RV-A(5) should size it against cross-module registration, not against laziness, and re-measure the 45.
  ⊕ Sibling from the same RV-A batch: **RV-A(6)** ("self-host parses newtype/tuple `.0` as EFieldAccess \"0\"") is the ancestor of R48 Track P's `RTTuple` arm in `lvalue_value_type` and of `todo/t0943` (the Rust lane's `._N` alias hole). RV-A(6) is now partly discharged: the self-host handles both spellings through one shared `tuple_field_index` rule; what remains under it is the Rust side, which is t0943.
  ⚠ **BOTH self-host resolvers read the SAME table with the SAME key** — `infer_expr_type` (`infer.gg:433-434`) and the structural `lvalue_value_type` (`typecheck.gg:1493-1494` / `:1499-1500`). So this is **not** fixable at a read site without writing the same repair twice; it is a "one source of truth per axis" boundary.
  **THE PRODUCER IS THE WRITE SITE**: `typecheck.gg:5974-5985` walks `sdef.fields` for the `IStruct` items of the module BEING CHECKED and does `types.variant_field_types.put(f"{sdef.name}.{field.param_name}", …)`. An imported struct is not an `IStruct` item in this module's AST, so no row is ever written — the table is not "sparse", it is module-local by construction. Fix there (register imported struct defs' fields too), or give the safety walk a complete per-struct field registry the way Rust has (`struct_field_names` + `DefInfo.field_types`, `src/semantic/safety/helpers.rs`).
  **Blast radius is wider than D53.** Every gate that asks a type question about a field place inherits the hole: D53 unique locks, D4/D12 drop-taint, the get-chain kind gate. The repro pins the D53 cell because that is the one an executable test could be authored for this round.

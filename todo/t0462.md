- **🆕🚨 [HIGH — Core #10 SILENT DROP with TWO OPPOSITE FACES, one a wrong-REJECTION and one a wrong-ACCEPTANCE; filed 2026-08-23 by R44 Track E, grep-before-file done] An ARRAY SIZE that is not a bare integer literal silently resolves to ZERO.** `src/semantic/types.rs:535-542` `ast_type_to_resolved`'s `ast::Type::Array` arm reads the size as `match &size.node { ast::Expr::IntLiteral(n) => *n as usize, _ => 0 }` — a literal is the only spelling it understands and everything else mints `0`. **Face (a), wrong REJECTION:** `int[2 + 1] a = [10, 20, 30]` → `gg check` rc 1, ``type mismatch: expected `int[0]`, found `int[3]` ``; identically, a const-generic signature `void g[const int N](int[N] xs)` called with an `int[3]` is rc 1 with the same message, so const-generic array parameters are unusable. **Face (b), wrong ACCEPTANCE:** the same expression as a struct field (`struct Buf: int[2 + 1] data`) is rc 0 through `gg check` **and** `gg build`, emitting `struct __gg_Buf { uint8_t data; }` — a three-element int array typed as one byte, all the way to a binary. **Causation proved by break-and-watch** (`_ => 0` → `_ => 99`, rebuild): both rejecting probes flip to ``expected `int[99]` ``, so this arm — not any substitution pass — is the producer. ⚠ **What an honest fix would NOT break, measured rather than inferred:** the language reference's `struct FixedArray[T, const int N]: T[N] data` is rc 0 at HEAD **and rc 0 under a break at this arm** — `gg parse` shows `T[N]` in a field position parsing as `Type::Named { "T", generic_args: [N] }`, because `Ident[…]` is generic-argument syntax, so `Type::Array` is structurally unreachable from it. **The shapes that DO depend on this arm are `int[2 + 1]` and `int[N]` in a function signature; warn about those.** Intended behaviour is the spec's own: `docs/language-reference.md:455`/`:458` give `array_type = type "[" const_expr "]"` with *"Size must be a compile-time constant"*, so `int[2+1]` must be accepted as `int[3]`. **DURABLE REPRO:** `tests/fixtures/known_gaps/array_size_const_expr_not_evaluated.gg` + the `#[ignore]`d `array_size_const_expr_not_evaluated`, asserting the INTENDED size-3 behaviour wired to RUN. **This is an accept/reject move, so it is a Core #9 three-lane change** (ggdef row + `spec_conformance` + SH disposition) — that is why it is filed rather than fixed inside a walker track. ⚠ **NOT the `meta`-constant cell:** `meta int N = 3` + `int[N]` was a different producer (`semantic/meta.rs substitute_type` dropping the size expression), fixed in R44 Track E and pinned live by `tests/fixtures/known_gaps/meta_const_array_size_local.gg`, `tests/fixtures/known_gaps/meta_const_array_size_param.gg` and `tests/fixtures/known_gaps/meta_const_array_size_return.gg`;

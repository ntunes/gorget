- **🆕🐛 [MED — a LEAK from ordinary safe syntax, BOTH backends, `gg check` clean; found 2026-09-03 by R48 Track T-a1 while ASan-attributing the three rows that round admitted to `tests/sanitize/LEAK_ALLOWLIST.txt`] `vector.flat_map(f)` leaks the `Vector[U]` the callee returns — one backing array per input element, plus the elements it still owns.**
  ```gorget
  Vector[String] fan(int n):
      Vector[String] out = []
      out.push(int_to_str(n * 10))
      return ^out

  void main():
      Vector[int] nums = [1, 2, 3]
      auto out = nums.flat_map(fan)
      print(out.get(0).unwrap())    # prints 10, leaks 777 bytes in 6 allocations
  ```
  **MECHANISM.** `flat_map` is `(T) -> Vector[U] ⇒ Vector[U]`: the callee mints a fresh vector per input element, the expander drains its elements into the accumulator, and the drained HUSK is then owned by nobody — no drop is registered for it and none is emitted. Core #3, at the producer: a freshly-materialized owned droppable value with no ownership tag.
  ⭐ **THE CALLEE IS A NAMED FUNCTION IN THE REPRO, DELIBERATELY**, so `todo/t0953`'s closure-literal environment leak cannot contaminate the record set. With an inline `(int n): fan(n)` the same program additionally leaks `__gorget_closure_env_alloc*1`.
  ⭐ **DIRECT vs INDIRECT is the discriminator against `todo/t0954`.** The ASan report groups this one as
  ```
  Direct   leak: gorget_array_push <- fan <- __adapt_fan <- main       (the husk's backing store)
  Indirect leak: str_alloc_copy <- gorget_string_adopt <- gorget_int_to_str <- fan <- __adapt_fan
  ```
  — the Strings are INDIRECT, i.e. reachable from the leaked husk, so they are a consequence of this defect and not a second one. `t0954`'s leaked Strings are DIRECT and have no leaked container above them: there, the accumulator array is freed and its elements are not; here, the husk is not freed at all. Two different defects, and the fixture that admitted them exhibits BOTH.
  ⭐ **RECORDS vs ALLOCATIONS.** Three husks from one `Vector[String] out = []` site share one allocation stack, so ASan reports **one RECORD in three ALLOCATIONS**. The record count is the number of producing SITES; the allocation count scales with the input length.
  **DISCRIMINATED from `todo/t0954`** — see above; that one is the ACCUMULATOR's missing `elem_drop` and is reachable with plain `map`, which mints no intermediate vector at all.
  **DISCRIMINATED from `todo/t0873(b)`** — that is `elem_drop` never synthesised for a `Callable` element type. Nothing here is a `Callable`, and the leaked object is a whole container, not an element.

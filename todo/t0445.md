- **Compiler footguns (latent type-system validation gaps, same class as `Ordinal`):**
  - **(C3) Phantom static methods pass `gg check`, fail at C build/link.** `String.from("x")`/`int.from(5)`/`int.try_parse(s)` all report "OK" but `gg build` fails (implicit-decl / undefined-reference / phantom symbol). Root: `resolve_static_method_type` (`typecheck.rs:4717`, called `:1740`) returns `None` for an unknown `Type.method()` + the call FALLS THROUGH → the backend name-mangles into a nonexistent runtime symbol (rule-2 violation). Fix: emit a `NoSuchMethod`/`UnknownStaticMethod` diagnostic at typecheck. Canonical working: `String("x")`, `int.parse(s)`→Option, `parse_int(s)`→Result.
  - **`.unwrap()`/`.expect()`/`.unwrap_or()` on a NON-Option/Result is a silent no-op pass-through** (`methods.rs:588`, the `matches!(method_name, "unwrap"|"expect"|"unwrap_or")` arm returns the receiver unchanged). A genuine type confusion (e.g. `channel_exec(...).unwrap()` on a plain `CommandResult`) is silently swallowed. Fix (design call; verify no stdlib/self-host relies on the no-op first): make it a typecheck error or at minimum a lint.

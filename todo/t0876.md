- **🆕🧹 [MED — THE EMITTED C IS NOT REPRODUCIBLE: the SAME compiler binary on the SAME input emits two different files run to run; found 2026-08-31 while A/B-ing a lowering change's blast radius] `gg build F --emit-c-lir` is non-deterministic in declaration ORDER.** Measured, 10 runs of each of two binaries on each of two fixtures:
  - `tests/fixtures/generic_callable_ref.gg` — 10 runs of ONE binary split **6/4** between two md5s; the second binary split **7/3** between the *same* two. The whole difference is one line, `__gg_Option__int64_t __adapt_do_advance(void* __env, void* __p0) { return do_advance(__p0); }`, emitted one line earlier or later.
  - `tests/fixtures/spawn_closure_copy.gg` — 3 runs of ONE binary produced **two** different md5s. The whole difference is one line, `typedef struct { void* __task; void (*__drop)(void*); } Task__int64_t;`.
- **Reproduce (no new fixture needed — both are committed corpus fixtures):**
  ```
  for i in $(seq 10); do ./target/debug/gg build tests/fixtures/generic_callable_ref.gg --emit-c-lir 2>/dev/null | md5sum; done | sort | uniq -c
  ```
  Two distinct hashes ⇒ reproduced. Same command on `spawn_closure_copy.gg`.
- **Mechanism — one trigger is pinned at file:line.** `src/backend/c_lir/mod.rs:934` declares `let mut adapter_fids: HashSet<u32> = HashSet::new();` and `:946` does `for fid_raw in &adapter_fids` to EMIT the `__adapt_*` forwarding functions. `std::collections::HashSet`'s default `RandomState` is seeded PER PROCESS, so that loop's order — and therefore the order those functions appear in the output file — is a function of the hash seed. That is exactly the `__adapt_do_advance` line that moves in `generic_callable_ref`. Sibling candidates for the `typedef` case and for the rest of the class: the `seen` sets and `by_variant` maps in `src/backend/c_lir/emit_types.rs`. Everywhere else the tree uses `rustc_hash::FxHashMap`, which is deterministic for a fixed insertion sequence; these sites are the exceptions. ⚠ Six-questions #5: this is about emission ORDER, not emission — the *set* of declarations is stable and the content is byte-for-byte the same; only the position of a line moves.
- **HOW WIDE IS THE CLASS — regenerate, never quote.** Two independent measurements, both on 2026-08-31:
  - The R48 Track C output review censused the FULL corpus and found **≥40 of 2177** fixtures affected.
  - The executor re-measured over the 353-fixture `generic|equip|trait|closure|cow_` corpus with only **3 emits each** and found **2** (`generic_callable_ref`, `spawn_closure_copy`). ⚠ Three emits is a WEAK detector — a fixture that flips 50/50 is missed with probability 0.25, and a rarely-flipping one is missed almost always. The two numbers are consistent; the smaller one is a floor, not a contradiction.
  - Command (raise the rep count until the number stops moving):

- **⚠ WHAT THIS DOES *NOT* INVALIDATE — read this before citing the item.** It does **not** overturn the R48 Track C "no clone/RSS re-bomb" conclusion. That conclusion rests on the **2×2 clone-meter table** (driver built by the PRE compiler vs the POST one × BASE source tree vs HEAD source tree), which reads RUNTIME counters — `array_clone` / `string_clone` were identical **to the digit** for both binaries at fixed input. Runtime allocation counts cannot be moved by the ORDER declarations appear in the emitted C. The byte-identical-driver-C observation is corroboration, and it is the half this item weakens.
  ⊕ **The self-host driver appears IMMUNE, and the caveat is stated rather than hidden.** 18 consecutive emits from an untouched binary are byte-identical (34,768,294 bytes, one md5). A single earlier outlier came from a batch that overlapped a `cargo build`, i.e. the binary changed underneath the census — a confounded observation, not evidence of a flip. So: no flip observed in 18 clean samples; "immune" is the best-supported reading and is NOT proven, because absence of a rare flip in 18 samples is weak evidence. **And the mechanism of that immunity is now MEASURED, not assumed: the driver's emitted C contains ZERO `__adapt_*` functions**, so `adapter_fids` is empty and the `mod.rs:946` loop never runs — the pinned trigger cannot fire on it (`grep -c '__adapt_' <driver.c>` → 0). That is why the Track C re-bomb A/B on the driver was reproducible while two corpus fixtures were not: the corpus fixtures pass named functions where closures are expected, and the driver does not. ⚠ It says nothing about the OTHER suspected sites in `emit_types.rs`; a driver flip from one of those is not excluded. ⚠ Either way, a future emitted-C A/B on the driver should take several samples per side rather than one.
- **Why it matters beyond tidiness.** (a) Reproducible builds: two identical checkouts produce different `.c` and therefore different object files. (b) It silently corrupts the tree's own favourite instrument — SEVERAL rounds have argued "no blast radius" from a BYTE-IDENTICAL emitted-C A/B; on any fixture in this class that comparison is a coin flip, and a diff it reports may be pure noise (which is exactly how this was found: two DIFF rows in a 342-fixture A/B turned out to be the same binary disagreeing with itself). Any future emitted-C A/B should sample each side more than once, or this should be fixed first. (c) A declaration-order flip is benign in C *today* only because the moved lines happen to have no ordering dependency; a typedef that moved BELOW its first use would be a build break appearing at random.
- **Not caused by, and not fixed by, the per-function-prescan centralisation (R48 Track C)** — both binaries in the measurement above produce both outputs, and the base-commit binary does too.
- **Fix:** make the emit path's ordering decisions read a deterministic container (`FxHashMap` + an explicit sort, or an `IndexMap`/`Vec` keyed by first-appearance). Then add the guard this class owes (Core #6): a test that emits one fixture twice in one process — or the same fixture from two processes — and asserts byte-equality. A census of `std::collections::Hash{Map,Set}` under `src/backend/` and `src/lir/` is the enumeration to work from.

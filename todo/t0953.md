- **🆕🐛 [MED — a LEAK from the most ordinary syntax in the language, BOTH backends, `gg check` clean; found 2026-09-03 by R48 Track T-a1 while ASan-attributing the three rows that round admitted to `tests/sanitize/LEAK_ALLOWLIST.txt`. THE SINGLE LARGEST CLASS IN THAT ALLOWLIST — `__gorget_closure_env_alloc` is one of its two biggest frames.] A closure LITERAL at a call-argument position leaks its environment.**
  ```gorget
  int apply(Callable[int(int)] f, int x):
      return f(x)

  void main():
      int base = 40
      Vector[int] nums = [1, 2, 3]
      auto out = nums.map((int n): n + base)   # 16 B leaked
      print(f"{apply((int n): n + base, 1)}")  # 16 B leaked
  ```
  ⭐ **THE CLASS IS WIDER THAN THE ALLOWLIST'S INHERITED CHARACTERISATION, and this is the finding.** `tests/sanitize/LEAK_ALLOWLIST.txt`'s big-groups table describes the frame as *"every builtin HOF call (map/filter/fold) leaks an 8-byte env, UNBOUNDED per call"* — prose the file itself labels *"inherited characterisation, not a measurement"*. Measured: **a plain USER function taking `Callable[int(int)]` leaks the same frame with no builtin HOF anywhere in the program.** So the write site is the closure-literal ARGUMENT, not the HOF expander, and a fix aimed at the HOFs would leave the wider case open (Core #4).
  ⭐ **DISCRIMINATING MEASUREMENTS.** All `gg build --sanitize`, records off the ASan report:

  | probe | HEAD |
  |---|---|
  | `nums.map((int n): n * 10)` — non-capturing, builtin HOF | `__gorget_closure_env_alloc*1`, **8 bytes** |
  | `nums.map((int n): n + base)` — CAPTURING, builtin HOF | `__gorget_closure_env_alloc*1`, **16 bytes** |
  | `apply((int n): n + base, 1)` — CAPTURING, plain user fn | `__gorget_closure_env_alloc*1`, **16 bytes** |
  | `nums.map(label)` — a NAMED function, no closure literal | **no env record** (`todo/t0954`'s element leak only) |

  The named-callee row is the negative control: remove the literal and the env record disappears, so the literal is the producer. The 8-vs-16 byte split is why the repro CAPTURES — a non-capturing closure gets a placeholder env and a net built from those is measuring a different allocation.
  **DISCRIMINATED from `todo/t0873(b)`** — that is a COLLECTION's `elem_drop` never being synthesised for a `Callable` element type (`src/lir/lower/insts.rs`), so the env the VECTOR still holds is never freed at array teardown: one record per ELEMENT, and it needs a `Vector[Callable]`. This one has no collection of closures at all; the env leaks at a call that has already returned.
  **DISCRIMINATED from `todo/t0949`** — that is a `Vector[Callable]` INDEX READ materializing by a compiler-inserted clone; it scales with the number of READS and requires the element to have been stored first.
  **DISCRIMINATED from `todo/t0771`** — that is an ESCAPING closure capturing a PARAMETER and storing the borrowed handle, i.e. a use-after-free, not a leak. Here the closure does not escape and the captured value is a local.
  **WHY IT MATTERS BEYOND THE RECORD COUNT.** `docs/devbook/11-copy-on-write.md` lists closure captures among the consuming positions where the destination must OWN, and closures are one of the single-owner-by-design carve-outs. An env minted at an argument position and abandoned means that boundary is not being closed at all for the literal form — the value has an owner on the way in and none on the way out.

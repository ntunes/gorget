- **🆕🛡 [MED — A GENERATOR WHOSE OWN EXIT CODE DESCRIBES THE STATE IT JUST REPLACED. Observed 2026-09-05 by the R50 orchestrator, twice in ten minutes, while integrating two tracks.]**

  **Controlled repro** (not an anecdote -- a scratch item, settled, then removed, with the write isolated to ONE invocation):

  ```
  cat > todo/t9999.md <<'EOF'
  id = "t9999"
  ... minimal front matter, areas = ["guards"] ...
  EOF
  python3 scripts/todo_index.py --write >/dev/null 2>&1   # settle the pointer in
  python3 scripts/todo_index.py --write >/dev/null 2>&1
  rm todo/t9999.md
  cp TODO.md /tmp/before.md
  python3 scripts/todo_index.py --write                   # EXACTLY ONCE
  #   -> todo_index: 1 problem(s)
  #        TODO.md:5899: pointer to a missing todo/t9999.md
  #   -> rc 1
  diff -q /tmp/before.md TODO.md                          # -> DIFFERS
  grep -c 't9999' TODO.md                                 # -> 0
  ```

  **The single run BOTH removed the row AND reported that row as a problem.** `grep -c` is 0 afterwards, so the write landed; the diagnostic and the rc describe the tree as it was *before* that same run's write. This is the discriminating measurement: without it the symptom is indistinguishable from "the first run legitimately failed and the second legitimately succeeded".

  **Why this is not cosmetic.** `--write` is the documented remedy the `todo_index_is_current` lint prescribes, and it is run at nearly every integration, usually inside a chain. A `&&` after it short-circuits on the false rc 1 and silently skips whatever the caller put next; a `||` fires a bogus repair path. The failure is *quiet in the direction that matters* — the caller's next step is skipped and nothing says so.

  ⚠ **THIS IS A CORE #13 DEFECT IN THE INSTRUMENT, NOT A UX WART.** The rule is *verify the verifier — pick an instrument that can SEE the failure class*. An index validator that cannot see its own write is structurally unable to answer the one question it is invoked to answer. A caller cannot distinguish "the index is stale" from "the index was stale and I just fixed it".

  **Shape of the fix (not prescribed — the executor measures):** validate against the bytes just written, or split the two jobs so `--write` reports only what it wrote and `--check` is the sole rc authority. Whichever lands, the guard is a test that runs `--write` on a tree with exactly one missing pointer and asserts **rc 0 on the first invocation** (Core #6: it must FAIL against today's script).

  **Sibling to check in the same pass:** `scripts/todo_index.py --check` — does *it* read the tree fresh, or share the same stale-view helper? If they share it, the lint that gates every round is reading the same lagging state, and this item's scope is the lint, not the writer.

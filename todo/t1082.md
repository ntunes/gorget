- **🆕🐛 [HIGH — THREE CELLS OF ONE FAMILY: a `Box[Trait]` collection's element type reads back WITHOUT THE BOX at three separate boundaries. Found 2026-09-04 by R49 Track M2 while closing the trait-object pack; each cell measured at pristine HEAD and again under that fix, unchanged by it.]**
  - **THE FAMILY.** Where the pack class M2 closed was about *whether* the destination type reaches a consuming position, this is about *what the element type IS* by the time the typechecker and the mangler read it. The Box is stripped, leaving the bare trait (or `int64_t`), and each boundary fails in its own way:

    | # | boundary | cell | symptom |
    |---|---|---|---|
    | 1 | `.get()`-chain method mangle | `Deque[Box[Speaker]]` `q.get(0).unwrap().speak()` | builds, then **`undefined reference to 'int64_t__speak'`** at link |
    | 2 | method LOOKUP on the receiver | `q.push_back(Box.new(Robot("R2")))` | **`error[E_NoMethodFound]: no method 'push_back' found on type 'Deque[trait Speaker]'`** |
    | 3 | index-assign DESTINATION typecheck | `Vector[Box[Speaker]] v`, `Box[Robot] b`, `v[0] = ^b` | **`error[E_TypeMismatch]: type mismatch: expected 'trait Speaker', found 'Box[Robot]'`** |

  - ⭐ **THE DISCRIMINATOR IS MEASURED AND IT IS WHAT MAKES THIS ONE FAMILY RATHER THAN THREE FILINGS.** On the SAME receiver, the shapes that DO work localise the loss precisely: `q[0].speak()` (index read) resolves and runs, so cell 1 is the `.get()`-chain and not the collection; `q.push(...)` resolves and runs, so cell 2 is `push_back`'s lookup and not `Deque`; and `v[0] = Box.new(Robot(...))` (temp form) lowers and runs, so cell 3 is the destination-side typecheck and not index-assign as such. Every failing cell has a working sibling one token away.
  - **CONSEQUENCE, cell 3 specifically.** It is why the only spelling that can reach `lower_index_assign`'s trait-object pack is the TEMP form. That BOUNDS the pack there — it cannot see a live named source, so it cannot create a double owner — but it is a reject the language should not be issuing: a `Box[Robot]` moved into a `Vector[Box[Speaker]]` slot is exactly what the method path accepts at `v.push(^b)`.
  - ⚠ **ACCEPT/REJECT ASYMMETRY, NOT NECESSARILY A DEFECT IN ALL THREE (SIX Q#1).** Cells 1 and 2 are unambiguous — a link failure and a method the receiver demonstrably has. Cell 3 is an asymmetry between `v.push(^b)` (accepted) and `v[0] = ^b` (rejected) for the identical value and destination; check the design record before assuming the ACCEPT direction is the correct one to unify on.

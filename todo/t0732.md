- **[MED — `shared(atomic) int` LEAKS 8 BYTES ON BOTH BACKENDS, and no gate in this tree can see it. Adjudicated 2026-08-29 by R47 Track C, which was asked to confirm a suspected LLVM lane divergence and found something different underneath.]**
  - **MEASURED AT HEAD, deterministically, both lanes.** `gg build --sanitize [--backend=llvm]` on the two-task repro, run under `ASAN_OPTIONS=detect_leaks=1:exitcode=99`: **20/20 runs exit 99 on each lane** (this shape is stable — see the axis note below for the shapes that are not), reporting
    ```
    Direct leak of 8 byte(s) in 1 object(s) allocated from:
      #0 __interceptor_malloc   #1 gorget_atomic_int_new   #2 main
    ```
    Repro: `tests/fixtures/known_gaps/shared_atomic_int_never_dropped_leak.gg`, wired `#[ignore]`d as `shared_atomic_int_is_dropped` (`tests/integration.rs`).
  - **THE SHIPPED FIXTURE ALREADY EXERCISES IT.** `tests/fixtures/security/attack_87_atomic_counter_race.gg` leaks the same 8 bytes. Nothing reports it, for three independent reasons: it is wired as `security_safe`, which runs under `ASAN_OPTS_NO_LEAK` = `detect_leaks=0`; `scripts/sanitize_sweep.sh` does run `detect_leaks=1` but enumerates `find tests/fixtures -maxdepth 1`, so it never descends into `tests/fixtures/security/` (t0731); and the robustness map's `asan` lane covers a different corpus. **A leak sitting inside a memory-safety fixture, inside the security suite, invisible to all of it.**
  - **⚠ THE "LANE DIVERGENCE" IT WAS FILED AS DOES NOT EXIST — do not go hunting one.** On `attack_87`'s own 4-task shape C reports on every run while LLVM usually reports nothing, which is what the R47 scout saw and reasonably read as an LLVM divergence. It is a measurement artifact, and **the rate is not a fixed number** — it is load- and machine-sensitive: measured **0/20** by the executor, **3/10** by the output reviewer on the same box under different load. Expect no particular figure to reproduce; re-measure with `for i in $(seq 20); do ASAN_OPTIONS=detect_leaks=1:exitcode=99 ./bin; echo $?; done`. It is a stop-the-world REACHABILITY effect — a worker still live at exit, its stack or a pool structure still referencing the block, so LSan classifies it reachable rather than leaked — not different codegen. Two independent checks: an extern-`malloc` leak injected into the 4-task LLVM binary IS reported, so LeakSanitizer is present and looking on that lane; and both lanes report the leak on the short shape.
  - **⚠ THE AXIS IS PER-TASK WORK, NOT TASK COUNT.** The obvious rule is the wrong one, so it is written down measured — 20 runs per cell, LLVM lane: `2 tasks x 1 increment` **20/20** · `4 tasks x 1` **20/20** · `2 tasks x 10000` **4/20** · `4 tasks x 10000` (`attack_87`) **0/20**. Four tasks with no loop is perfectly stable; two tasks with the loop already flakes. "Use fewer tasks" would let someone write a flaky repro and believe they had followed the rule. **THE RULE IS: keep the concurrent work SHORT, so no worker is still live when the process exits.**
  - **PROCESS NOTE worth keeping.** Two review passes reasoned about this row from the fixture's wiring alone and reached opposite conclusions ("cannot redden the gate", therefore "not a defect"). The first was right and the second did not follow. One 10-run execution on each lane settled it, and turned a suspected lane divergence into a real cross-lane leak.
  - **ON FIXING IT.** Graduate the repro to a live `security_safe_no_leak` fixture, and consider re-wiring `attack_87_atomic_counter_race` as `security_safe_no_leak` at the same time — it is a `shared(atomic)` fixture whose bug class is stdout-invisible, which is exactly that helper's stated subject.

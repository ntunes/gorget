- **🆕🧹 [MED — UNBOUNDED DISK LEAK IN THE SHIPPED DRIVER, one leaked directory per `gg run`; measured 2026-09-03 at R49 open, where the accumulated residue was **161,898 directories / ~37 GB** in `/tmp`] `gg run` never deletes its build scratch directory, because `tempfile::TempDir`'s cleanup is a destructor and the command exits via `process::exit`.**
  - **MECHANISM, read at HEAD.** `tempfile::tempdir()` returns a `TempDir` RAII guard that removes the
    directory in its `Drop` impl **and nowhere else**. Every arm that opens one terminates through
    `std::process::exit`, which ends the process **without unwinding and without running destructors** —
    so `Drop` never executes on ANY path, success or failure. The directory, the emitted `<stem>.c` and
    the linked `<stem>` binary all survive.
  - ⚠ **CORRECTED 2026-09-03 by the R49 Track H scout — THIS ITEM'S FIRST EXIT-SITE SET WAS WRONG, and
    the sibling question it asked is now ANSWERED: ALL THREE ARMS LEAK.** The original text cited
    `:3081` success / `:3095` signal / `:3097` failure plus *"~30 earlier error exits between `:2598` and
    `:3097`"*. Those are real `process::exit` calls, but they live in the
    `command == "test" && Path::new(filename).is_dir()` multi-file aggregation block (`:2944-3098`),
    **which opens no tempdir at all** — it spawns per-file `gg` subprocesses. The `:2596` tempdir's scope
    ends at `:2634`. The mechanism and the fix shape were right; the exit-site set was not. The true set,
    measured with a private `TMPDIR` swept to zero (`gg build -o …` leaks **0** — the discriminator holds):

    | tempdir | arm | scope | non-returning exits in scope | leaks |
    |---|---|---|---|---|
    | `src/main.rs:2596` | `gg <file>.gg` shorthand (`:2581`) | 2581–2634 | 6 × `process::exit` + `propagate_child_status(:2633)` | **1 per run** |
    | `src/main.rs:3288` | `"run" =>` (`:3286`) | 3286–3342 | 3 × `process::exit` (`:3290`, `:3333`, `:3339`) + `propagate_child_status(:3335)` | **1 per run** |
    | `src/main.rs:3510` | `"test" =>` (`:3343`) | 3343–3716 | 26 × `process::exit` + `propagate_child_status(:3715)` | **1 per run** |

    `propagate_child_status` is `-> !` and ends in `process::exit` (`:40-52`), so **all 38 terminations
    skip the `Drop`.** Fix all three arms in one pass — fixing only `run` leaves the class open (Core #4).
  - ⭐ **WHERE THE VOLUME COMES FROM, and it is not the obvious place.** `run_gg` — the ~2,000-fixture
    workhorse — uses `gg build` and leaks NOTHING. The 161,898 directories come from **`gg run` used as the
    Rust ORACLE** at `tests/integration.rs:41052` and `:41283` (the comparison / runtime-diff helpers),
    invoked once per fixture across the corpus on every parity and sanitize sweep.
  - ⊕ **THE FALSE BELIEF IS WRITTEN DOWN IN THE TREE (Core #14).** `tests/integration.rs:2293-2295`:
    *"No cleanup: `gg run` builds into a `tempfile::tempdir()`, so it leaves nothing beside the fixture.
    (The previous body's remove_file calls were dead code asserting the opposite.)"* An invariant-asserting
    comment with no enforcing guard — the guard below is its enforcement, and the comment gets DELETED.
  - ⚠ **`gg build` is NOT affected and the contrast is the discriminator.** `build` writes its
    artifact to the user's chosen output path and its tempdir is dropped normally; DONE.md's `t0840`
    entry records the consequence from the other side — *"`gg build` deletes its tempdir"* is why that
    round needed a `CC=` shim to capture the generated C. Only `run` leaks, and it leaks on every
    invocation.
  - **RED-VERIFIED 2026-09-03**, on a `/tmp` swept to zero `.tmp*` entries first:
    ```
    $ printf 'void main():\n    print("hi")\n' > /tmp/leakprobe.gg
    $ ls -A /tmp | grep -c '^\.tmp'          # 0
    $ ./target/debug/gg run /tmp/leakprobe.gg # prints: hi
    ```

    One run, one leaked directory, holding both the emitted C and the linked executable.
  - **WHY IT MATTERS BEYOND TIDINESS — it is an operational hazard the project has already paid for.**
    The residue scales with the round-close battery, which invokes the run path across a ~2,200-fixture
    corpus on five lanes, repeatedly, every round. At R49 open the accumulation measured **161,898
    directories totalling ~37 GB**, against ~2.9 GB of all other `/tmp` content combined — i.e. the
    leak was **93%** of the scratch volume. `TODO.md`'s own handover records the cost of the same
    class in a different guise: *"crashes = disk accumulation"*, and R48 lost the F3 scout's worktree
    to a disk crash. A gate that fills the disk is a gate that eventually fails for a reason unrelated
    to the code under test.
  - **INTENDED:** all three arms remove their scratch directory on every exit path, error and signal
    included. **A Core #1 write-site fix, not a read-side sweep:** ⛔ do NOT add a reaper that scans
    `$TMPDIR` for orphans — it cannot distinguish this driver's directories from another live process's,
    and it races. **Confine the destructor-bearing scope instead.**
  - ✅ **FIX PROTOTYPED AND MEASURED 2026-09-03 (R49 Track H scout, ~40 lines, compiled first try):**
    split `propagate_child_status` into `child_exit_code(status, hint) -> i32` (carrying the
    `LINT-CHOKEPOINT-FALLBACK` marker) plus a one-line wrapper; then wrap each arm body as
    `let __code = (|| -> i32 { … })(); process::exit(__code);`, turning every inner `process::exit(n)`
    into `return n`. No signature plumbing, and `tmp_dir` drops at closure exit. **Measured: `gg run`
    leak → 0.** Gates green under the prototype: `cargo test --test lints
    child_exit_status_propagation_chokepoint` ok; `cargo test --test integration
    gg_run_propagates_signal_death` → 2 passed. **Cost: 35 `exit`→`return` conversions** (run 3 +
    shorthand 6 + test 26), mechanical, one shared helper. ⊕ Add a lint sibling to
    `child_exit_status_propagation_chokepoint` forbidding a raw `process::exit` in a destructor-bearing
    scope, so the next added exit cannot silently reintroduce the class.
  - ✅ **GUARD PROTOTYPED AND DEMONSTRATED RED IN BOTH DIRECTIONS (Core #6, devbook/25).** Four cells,
    each with its own private `TMPDIR` so it is race-free under parallel workers, counting directories
    only, with `gg build` as the NEGATIVE CONTROL. At unpatched HEAD it FAILS naming **all three** leaking
    arms with the control green; with only the `run` fix applied it FAILS naming exactly the **two**
    remaining arms. That per-cell directional sensitivity is what makes it a ratchet rather than a
    tolerance band.

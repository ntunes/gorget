- **🆕🐛 [CRITICAL — `gg check` passes, the binary SEGVs, and the compiler's OWN diagnostic recommends the crashing spelling] `.clone()` on a `Callable` segfaults.** Four lines, no generics, no collections:
  `Callable[int(int)] h = (int x): x + 1` / `Callable[int(int)] g = h.clone()` / `print(g(1))` → `terminated by SIGSEGV (signal 11)`; `gg check` prints `OK: no semantic errors`. Isolated at R48 close: a Dict read of a Callable is fine (`clone2` probe green), so the crash is `.clone()` on the Callable itself, not the container.
  **`Callable[T]` is in the single-owner carve-out — "no clone path in the lowering" (AGENTS.md § Ownership at Consuming Positions).** So the method must be REJECTED at check time (Core #10 lower-or-reject); lowering it to a shallow handle copy is the miscompile.
  ⛔ **The reachability is the sharp part.** `E_MoveWithoutOperator` renders "write `!{name}` to move or `{name}.clone()` to copy" (`src/semantic/errors.rs:1596`) for EVERY single-owner type, `Callable` included. A user who does what the compiler tells them gets a segfault. D53 already ruled the unique-lock diagnostic must name `^source` or `Shared[Mutex[T]]` and **never** `.clone()`; the same reasoning applies to every carve-out member with no clone path.
  ⊕ Related and NOT the same item: the message also spells the move sigil `!`, which D27 replaced with `^` — that sweep is `t0311`/`t0312`.
  **Fix shape:** reject `.clone()` on a type with no clone path at check time (one predicate, the carve-out set, not a name match), and derive the diagnostic's remedy list from that same predicate so it cannot advise an operation the lowering does not have. Core #9: lands on Rust gg + self-host, ggdef abstains (Callable out of subset).

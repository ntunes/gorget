- **🆕🚨 [HIGH — `<` `>` `<=` `>=` ON A STRUCT ARE ACCEPTED AND ANSWERED FROM ALLOCATION ADDRESSES, WITH THREE DIFFERENT ANSWERS ACROSS LANES AND ONE THAT IS NOT A POSSIBLE TOTAL ORDER. Split out of D46's `==` work (R49 Track F-G) because it is a different class by size and by remedy.] The ordering siblings of the equality gap D46 closed.** `gg check` accepts `a < b` on a struct with no `Comparable` impl. **REGENERATED 2026-09-04 on `struct P: int x` with `P a = P(1)` / `P b = P(2)`, printing `a<b`, `a>b`, `a<=b`, `a>=b`:** `gg check` **rc 0**; **C** prints `false true false true` ⇒ implies `a > b`; **LLVM** prints `false false false false` ⇒ **not a possible total order** (a total order cannot make both `a<=b` and `a>=b` false); **ggdef** rejects, `error: ordered comparison of struct and struct`. The R49 F-G brief additionally measured that **ASan — the same C backend with only the allocator changed — implies `a < b`, the OPPOSITE order**; that row was not re-run here (it needs the sanitize harness: `scripts/sanitize_sweep.sh` on the same fixture). Allocation addresses leak into program semantics: a program that sorts by `<` changes behaviour when you link a different allocator.
  - **WHY IT IS NOT MERELY D46's NEXT ROW.** The `==` fix touched **2 pre-existing files** over the whole tree. The ordering gate's blast radius is DRAMATICALLY larger, and it is dominated by `String`, which is registered `Equatable` / `Hashable` but **NOT `Comparable`** — verified at HEAD: `has_trait_impl_by_name`'s only intrinsic paths are `is_numeric_primitive && is_numeric_trait`, `is_hashable_primitive && is_hashable_trait` (`Hashable`/`Equatable` only) and the Cloneable/Displayable/Debuggable set, and `String` is not a numeric primitive. So a naive D46-shaped gate rejects `"ab" < "ac"` — which compiles and prints `true` / `false` / `true` correctly today (measured). And `Comparable` is **not derivable at all** (`src/semantic/derive.rs`), so the teaching diagnostic cannot say *"add `@derive`"* the way D46's does.
    ⚠ **DO NOT REUSE THE 938-SITES / 91-FILES / 929-`String` FIGURES FROM THE R49 BRIEF WITHOUT REGENERATING THEM.** They come from a throwaway prototype of the ordering gate and cannot be reproduced by grep — a text scan for ` < ` over the tree returns thousands of lines, most of them generic brackets, shifts and prose. **To regenerate: build the gate (the `BinaryOp::Lt | Gt | LtEq | GtEq` arms of `eq_comparable_blame`'s sibling), then run `gg check` over every `.gg` in the tree and diff the exit codes against a pristine build** — the method this round used for the `==` half.
  - **⚖ IT CARRIES AN OWNER ASK, ALREADY OPEN IN THE LEDGER (2026-09-04): SHOULD `String` BECOME `Comparable`?** That question decides whether this is a small fix or a language change. The ledger records the measurement that reframes it: **string ordering ALREADY WORKS, correctly, today** — `gorget_str_cmp` is byte-wise `memcmp` with a length tiebreak, registered in the LIR runtime table and already used to order string keys in the sort machinery. The implementation performs byte-lexicographic ordering; only the TRAIT REGISTRY does not record it. The naive-gate hazard exists *precisely because* the registry and the lowering disagree.
  - **THE CLASS FIX ALREADY LANDED (R49 Track F-G), so this item is the AXIS, not the mechanism.** `op_trait_and_method` (`src/semantic/typecheck.rs`) is now EXHAUSTIVE over all 31 `BinaryOp` variants with its `_ => None` catch-all deleted, and the four ordering arms are written as an EXPLICIT `=> None` citing this id. rustc's exhaustiveness check is therefore the guard that a NEW `BinaryOp` variant cannot silently join the ungated set — which is exactly how `Eq` slipped past for the life of the language. Behaviour on the ordering axis is UNCHANGED by that fix, proven two independent ways (31/31 variants compared identical; zero ordering hits in a full-corpus scan).
  - **INTENDED:** ordering on a type with no ordering impl is a check-time rejection with a teaching diagnostic, on all four lanes, once the `String: Comparable` question is ruled. Until then the operators stay ungated deliberately, and the explicit `=> None` arms record that.

- **🆕🐛 [HIGH — TWO FACES, ONE ROOT, both `gg check`-clean; found 2026-08-17 by the Track-E brief-review pass 2, orchestrator-reproduced] `Dict[K, Option[<heap>]].values()` MIS-TYPES THE PAYLOAD as `int64_t`.** Iterating a Dict's values where the value type is `Option[<heap type>]` loses the payload's type — the slot carries the Option's scalar representation instead. What that produces depends only on the readback: **FACE 1, `unwrap()` → SILENT WRONG ANSWER** (`gg check` OK, `gg build` 0, runs and prints **`0`** where the payload is the String `"aa"`, no diagnostic anywhere); **FACE 2, `match v: case Some(s)` → BROKEN C REACHES THE USER** (`gg check` OK, `gg build` exit 1 with `error: incompatible types when assigning to type 'Str' from type 'int64_t'` — a C-compile failure of generated code is by definition an ICE and must never surface as a raw `.c:` error, per `docs/language-design.md:120`). The `int64_t` in face 2's message is what identifies the shared root, so fix it once at the `values()` payload typing, not twice at the readbacks. By Core #8 face 1 is the worse of the two: a loud failure beats a silent wrong answer. ⚠ **DISTINCT from the `unwrap()`-on-a-borrowed-payload DOUBLE FREE filed above** — there the discriminator is `unwrap()` (a `match` readback is rc 0) and the program CRASHES; here BOTH readbacks are broken and neither crashes, so this is a typing defect in `values()`, not the payload-ownership defect. Payload must be heap-forced (a literal is a false negative).

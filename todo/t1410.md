- **🆕🚨 [HIGH — THE WRAPPING OPERATORS LOWER TO UNDEFINED BEHAVIOUR ON THE C LANE. Found by R50 Track H while keeping a fixture off an unrelated UBSan trip.]** `+%`, `-%` and `*%` exist to say *wrap, do not trap*. On the C backend they emit a plain signed `+` / `-` / `*`, which C leaves **undefined** on overflow — precisely the input the operator exists to handle.

  **MEASURED at HEAD** (non-constant operands, so the folder cannot hide it — with literals the whole expression is constant-folded and the probe is accidentally green):
  ```gorget
  int a = 3335314298909070151 + seed(mk("a", "b"))
  int b = 31 - seed(mk("", ""))
  int c = a *% b
  ```
  `gg build --sanitize` → `runtime error: signed integer overflow: 3335314298909070346 * 31 cannot be represented in type 'long int'`. The printed answer is right today; the *permission* the compiler has been given is the defect.

  ⭐ **THE WRITE SITE, and it is three siblings in one shape** (regenerate: `grep -n "__builtin_mul_overflow\|__builtin_add_overflow\|__builtin_sub_overflow" src/backend/c_lir/mod.rs`): `Inst::Add`, `Inst::Sub`, `Inst::Mul` each test `*overflow == Overflow::Trap` and, when it holds, emit the correct `__builtin_*_overflow` guard. **The `else` branch — which is exactly the `Overflow::Wrap` case — emits `{d} = ({ct}){l} * ({ct}){r};`.** The wrapping intent survives GIR (`GirBinOp::MulWrap`) and LIR (`Inst::Mul { overflow: Overflow::Wrap }`) intact and evaporates at the C-emit boundary. **Layering rule 1: lossy on syntax, lossless on invariants — this drops one.**

  ⭐ **THE LLVM LANE IS CORRECT, WHICH MAKES THIS A LANE DIVERGENCE IN DEFINED-NESS.** `src/backend/llvm/mod.rs` emits bare `add` / `sub` / `mul`, and `grep -c "nsw" src/backend/llvm/mod.rs` → **0**; LLVM's flagless integer ops are *defined* to wrap two's-complement. So the same source is well-defined on LLVM and UB on C — "both backends agree" cannot be invoked here, because they do not (Core #8).

  ⛔ **THE BLAST RADIUS IS THE STANDARD LIBRARY, NOT AN EXOTIC CORNER.** `lib/std/hash.gg`'s `FxHasher` is written `self.state = self.state *% 31 +% v` — correctly, using the wrapping operators — in `write_int` / `write_bytes` / `write_string` **and** their `equip FxHasher with Hasher` mirrors. Every `@derive(Hashable)` struct with a String field, and every `hash_of[String]` on a long enough string, therefore executes signed overflow UB:
  ```
  gg build --sanitize <any Dict[UserStruct, V] program with a ~20-char key field>
  # -> runtime error: signed integer overflow: ... * 31 cannot be represented in type 'long int'
  ```
  **This is why a new fixture must keep its key strings short** — an unrelated cell would sanitize-fail for this reason and read as its own defect (that is how it was found).

  **THE FIX** is the standard one and is local to the three `else` branches: perform the operation in the **unsigned** counterpart (`(uint64_t)l * (uint64_t)r`, cast back), where wraparound is defined by the C standard. No language-level change, no LIR change — the tag is already there and already correct.

  ⚠ **WHAT DISCRIMINATES IT.** Not `t1407` (that is `gorget_array_fill` duplicating one buffer into N slots — a runtime-C ownership bug, not an emitted-arithmetic one) and not a trapping-arithmetic item: the `Overflow::Trap` path is *correct*, and it is the presence of that correct sibling in the same `match` arm that shows the `Wrap` branch was an omission rather than a decision.

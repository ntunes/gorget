- **🆕🐛 [HIGH — NON-TERMINATION + OOM FROM A `gg check`-CLEAN PROGRAM, both backends; found 2026-09-05 by the orchestrator while measuring R2]** Mutating a collection inside a `.iter()` loop **hangs and is OOM-killed**.

  ```gorget
  Dict[int, int] d = {}
  d.put(1, 10)
  d.put(2, 20)
  for k, v in d.iter():
      d.put(k + 100, v)     # gg check: OK — then rc 137, SIGKILL
  ```
  The builtin spelling **rejects the identical program**:
  `error[E_MutationWhileBorrowed]: cannot mutate `d` while `for-loop over `d`` borrows from it`.

  **Regenerate:** run both spellings under `./target/debug/gg check` and then `./target/debug/gg run`, reading
  each rc **off the bare command**.

  ⛔ **THIS IS A DEFECT UNDER EITHER SIDE OF R2, WHICH IS WHY IT IS FILED SEPARATELY FROM THAT RULING.**
  R2's ruling direction is **bare = snapshot, `&` = reject**. `.iter()` does **neither** — it does not reject,
  and it does not snapshot. **Whatever R2 settles, the current behaviour is wrong.**

  ⚠ **DO NOT "FIX" IT BY MAKING `.iter()` REJECT** without checking R2's state first: under the ruling
  direction the **bare** form is meant to be **accepted with a materialize**, so a reject here could have to be
  undone one round later. **The safe, ruling-independent half is that non-termination is never the answer.**

  ⊕ **Same family as the R2 asymmetry generally:** the userland `Iterator` protocol and the builtin `for`
  disagree about mutation-during-iteration. Related: [[t1361]] (member access on a `.iter()` binding is
  unchecked — a *different* defect on the same surface, and already owner-ruled to reject).

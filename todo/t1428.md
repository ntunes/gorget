- **🆕🚨 [HIGH — AN UNBOUNDED LEAK IN `fold`'s ACCUMULATOR SLOT, ON BOTH BACKENDS. Found by R50 Track K's scout while triaging the 31 unbaselined robustness-map rows; pre-existing, not introduced by that work.]** `words.fold("", (acc, e): acc + e)` over 6 elements leaks **28 bytes in 6 allocations**, and the count grows with the collection:

  ```
   8 B / 1 alloc   __gorget_closure_env_alloc                     <- t0953, already filed
  20 B / 5 objects gorget_str_cat <- __Closure_0__call            <- THIS ITEM
  ```

  **⭐ THE DISCRIMINATOR IS A NEGATIVE CONTROL, NOT A READING OF THE FRAME.** Replacing the closure with a named callee — `String cat(String, String)` plus `words.fold("", cat)` — still leaks **20 B / 5 objects** through `gorget_str_cat <- cat <- __adapt_cat`, and the 8-byte env record is gone. ⇒ **the accumulator leak is the FOLD's, not the closure's**, and it is not a second face of `t0953`.

  ⊕ **And it is the accumulator SLOT specifically, not string-producing HOFs generally**: `hof_fold` (int accumulator) and `hof_map_strings` (a `map` that produces Strings) leak only the 8-byte env. Each iteration's `acc + e` materialises a fresh String, the slot is overwritten with the successor, and the predecessor is never registered for drop — **Core #3 at the fold's accumulator write, one layer above the closure call.**

  ⚠ **The root cause has NOT been traced to a write site in `src/`.** The attribution above is measured (negative control + both backends + per-element scaling); the producer is not yet located.

- **🆕🐛 [MED — SELF-HOST lane, two arms of one helper; found R48 Track A while porting the `t0770` fix to the self-host]** A closure LITERAL the self-host cannot type is emitted `int64_t`-returning whatever it actually returns: `error: incompatible types when returning type 'Str' but 'int64_t' {aka 'long int'} was expected`.
  - **THE TWO ARMS, one helper** (`tests/fixtures/self_host_lowerer/lower_closures.gg::guess_return_type`):
    - **(a) an `Ok(..)` / `Error(..)` body with no `expected_type` in scope.** The `Some(x)` sibling arm MINTS `Option__U` from the payload directly, but the Result constructors are gated on `expected_type` being a Result — and at a closure-ARGUMENT site that is `-1`. So `go((String s): Ok(mk(s, "?")))` types the closure `int64_t`.
    - **(b) a body that is a bare closure PARAMETER identifier** — `(String e): e`. The `EIdentifier` arm consults `gmod.fn_sigs` only. Rust gg temporarily registers the closure's params as locals before running its body inference ("Tier 1c", `src/ir/lowering/closures.rs`); the self-host does not, so the param is invisible.

  - **⚠ (b) IS CORRECT AS ORIGINALLY FILED — RETRACTION OF THIS ERRATUM'S OWN FIRST VERSION.** An earlier version of this erratum asserted that `guess_return_type` *"has NO `EIdentifier` arm at all"*. **That is false and it was false when written.** The arm exists, at the same 8-space indent as its sibling arms of `match sexpr.expr`, and it reads `gmod.fn_sigs` and nothing else:
    ```
    case EIdentifier(name):
        # Look up from fn_sigs (could be a variable holding a closure)
        if gmod.fn_sigs.contains(name):
            return gmod.fn_sigs.get(name).unwrap()
    ```
    Regenerate with `grep -n 'case EIdentifier(name):' tests/fixtures/self_host_lowerer/lower_closures.gg` — the first hit is the one inside `guess_return_type` (`grep -n 'int guess_return_type' <same file>` bounds it). ⭐ **A neither-guessed-nor-inferred second witness sits 46 lines below the arm**: `grep -n 'EIdentifier arm consults' tests/fixtures/self_host_lowerer/lower_closures.gg` returns the tree's own comment saying *"`guess_return_type`'s EIdentifier arm consults `fn_sigs` only"*.
    **THE ARM IS INERT, NOT ABSENT.** A bare LOCAL or a closure PARAMETER is never in `fn_sigs`, so the `if` fails, control falls off the arm, and the function reaches its `return I64_TYPE` default — producing output IDENTICAL to having no arm, which is exactly how an author who did not read the source mistook one for the other.
    ⚡ **THE LESSON, recorded because this is a filed item's most load-bearing field:** *"the symptom is identical"* is not evidence about the MECHANISM. An inert arm and an absent arm emit the same wrong C; only reading the source tells them apart, and the erratum asserted the source had been read. **The remedy differs too:** widening the arm to consult LOCAL types closes (b) and (c); "add the missing arm" would have been written beside the one that already exists.
  - **⊕ (c) A BARE LOCAL IDENTIFIER BODY FAILS IDENTICALLY — GENUINE, and it WIDENS (b)'s scope.** `String s = mk("hel","lo"); Callable[String()] f = (): s` → the same `error: incompatible types when returning type 'Str' but 'int64_t' was expected`.   - **⊕ (d) A METHOD-CHAIN BODY FAILS TOO.** `Vector[String] v = …; Callable[String()] g = (): v.get(0).unwrap()` → same error. The `EMethodCall` arm does not carry the collection's element type back out.

- **[MED — `--sanitize --backend=llvm` instruments the RUNTIME ONLY; generated user code carries no shadow checks. Found 2026-08-29 while making the LLVM sanitizer gate real (t0723).]**
  - **MEASURED AT HEAD.** With `GORGET_KEEP_RUNTIME=1 gg build --sanitize --backend=llvm`, the runtime object `__gorget_runtime_<stem>.o` carries **10** `__asan_report_*` references and the user object `__gorget_user_<stem>.o` carries **0**. Repro + the standing assertion of the intended state: `tests/fixtures/known_gaps/llvm_sanitize_user_code_not_instrumented.gg`, wired `#[ignore]`d as `llvm_sanitize_instruments_user_code` (`tests/integration.rs`). That test asserts the user `.o` DOES reference `__asan_report_*`, and carries a control asserting the runtime `.o` does — so it cannot pass by the build silently losing the flag entirely.
  - **WHY.** `--sanitize` reaches the runtime `cc -c` and the final link. It cannot reach the step between them, which is `llc`: `llc` consumes finished IR, and ASan instrumentation is an IR-level pass that has already not run by then. Closing this needs (a) `sanitize_address` attribute emission in `src/backend/llvm/`, and (b) the emitted IR surviving the instrumentation passes — an R47 scout bisect measured **two independent incompatibilities**, with inline shadow checks and with stack poisoning, each reproduced under a `-passes=verify` no-op roundtrip control that rules out the `opt` roundtrip itself. **The real content of that finding is that this backend's IR is incompatible with ASan's passes — a statement about `src/backend/llvm/`, not "ASan is hard".** `clang` is also absent from the current dev box (`which clang` → not found), which blocks the obvious alternative of routing user code through clang.
  - **COVERAGE SPLIT, so nobody has to re-derive it.** CAUGHT on this lane: all leaks (LeakSanitizer is interceptor-based, hence complete); UAF/double-free/overflow whose free *or* faulting access goes through the runtime — which is most of Gorget's heap traffic; interceptor classes (`memcpy`/`strlen`/…); UB inside the C runtime. NOT CAUGHT: stack-buffer-overflow in generated user code; a direct load/store from a user frame into freed heap touching no runtime function; UBSan on generated user code.
  - **THE TRAP FOR WHOEVER PICKS THIS UP.** A leak-based check CANNOT tell instrumented from merely-linked — LeakSanitizer works fine on a wholly uninstrumented binary. Verified by partial revert: with the sanitize flags on the link command and off the runtime `cc -c`, a leak control still reported and `ldd` still listed `libasan.so.8`, while `__asan_report_*` references went 10 → 0. Use an `__asan_report_*` artifact scan, as `sanitizer_gate_is_real_on_both_backends` (`tests/security.rs`) does.
  - **SCOPE NOTE.** Partial coverage is the shipped state, stated in `src/main.rs`'s `add_sanitize_flags`, in `docs/book/appendix-cli.md`, and in `docs/devbook/19-llvm-backend.md`. The C backend remains the lane the safety gates run on.

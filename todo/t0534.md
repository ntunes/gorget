- **⭐🆕 [HIGH — DENSE INDEX-MAP LAYOUT for `Dict`/`Set`; design OWNER-RATIFIED 2026-08-03 as D39 (`docs/define-gorget/decisions.md`), NOT implemented. Pure performance + capability work: NO accept/reject surface change, so Core #9's three-lane tax does NOT apply.]** Today `Dict`/`Set` store hash-slot-primary (`keys`/`states` indexed by slot) plus a side vector `order` of slot indices. `gorget_map_remove` tombstones the slot (`states[idx] = 2`) and **never touches `order`**; `gorget_map_keys` walks `order[0..order_len]` skipping dead slots. So the *i*-th live element is NOT `order[i]` — **ordinal access is O(n)**, and `order_len ≥ count` with the slack clearing only at a rehash. Move to the **dense index-map layout**: a dense `entries` array in insertion order (no holes, length == `count`) plus a hash `indices` table mapping hash → position. Rank becomes O(1); iteration becomes a dense walk instead of a filtered one; memory drops from `keys[cap] + states[cap] + order[cap]` to `entries[count] + indices[cap]`. Well-known design — Rust `indexmap`, Zig `std.ArrayHashMap`, Python's compact dict, Swift `OrderedSet`, .NET 9 `OrderedDictionary`.
  - **RATIFIED SHAPE (D39), do not re-litigate:** six types, two axes, no aliases. Bare = ordered, `Hash` = unordered, `Stable` = ordered-and-stable-under-removal. `Dict`/`Set` → dense · `HashMap`/`HashSet` → **UNCHANGED** (open addressing + linear probing `idx = (idx+1) & mask` + tombstones + tombstone *reuse*, which ordered mode disables; plus no index-table indirection on lookup — that is their whole reason to exist) · `StableMap`/`StableSet` → today's tombstone layout preserved for its real profile (O(1) order-preserving removal + address stability), in its **own module `lib/std/stablemap.gg`** per the `std.slotmap` precedent, which tiers it out of `std.collections` and the book's collections chapter.
  - **`remove` preserves order (O(n)); `swap_remove` is the O(1) marked opt-in.** Not a choice — the reference already promises insertion-order iteration as a global invariant, and `Vector` already ships the identical pair. Keep the names (`fast_remove` rejected: name the hazard, not the reward). Unmarked = safe default, marked = opt-in.
  - **⚠ ORDINAL ACCESS IS `.nth(i)` / `.key_at(i)`, NOT `[]`. D38's `s[i]` reject STANDS — do not implement it as withdrawn and do not add positional `[]`.** The ambiguity is layout-independent and survives this change: `d[0]` = value for KEY 0 while `s[0]` = element at POSITION 0, same operator, same operand type. Consistent rule: `[]` takes the collection's *lookup key*; a set has none, so `[]` is undefined there. Do NOT name the accessor `.ordinal(…)` — `Ordinal` is taken (`src/semantic/traits.rs:627-637`, enum variant index) and runs the inverse direction. **Two sub-questions D39 leaves OPEN for the accessor phase (deliberately last):** (i) the exact name — `.nth(i)` is clean for a set, but on a map it must first answer *"returns what?"* (`key_at` / `value_at` / `entry_at`); (ii) **do `HashSet`/`HashMap` get an ordinal accessor at all?** Recommendation: **no** — they stay open-addressed under D39, so it would be O(n) *and* return an arbitrary element, i.e. a footgun wearing an O(1)-looking name; same reasoning as their `[]` reject. The escape hatch is `.items()`, documented "(unordered)", where the arbitrariness is visible at the call site.
  - **SCOPE, measured 2026-08-03:** ~79 lines touching `order`/`states` in `src/backend/c/runtime/runtime_map.c`, 9 in `runtime_set.c`; struct at `src/backend/c/runtime/runtime_preamble.c:357-377`, **mirrored in `src/lir/types.rs:143,170`** (two shapes carry an `order_len` field — Layering rule 3 duplication to keep in sync or unify). Splitting dense from tombstone also removes today's `if (m->order)` dual-mode branching, so each implementation ends up simpler than the one that serves both.
  - **⚠ INTERACTION THAT NEEDS DESIGN, not mechanical porting:** `try_resolve_index_element_ptr` admits `Array | OrderedMap | Map`, i.e. Gorget hands out **interior pointers into map storage** for `&d[k]` write-through. Tombstoning never relocates; dense `shift_remove` relocates every subsequent entry. Lands on the filed R6 realloc-UAF axis → owes ASan fixtures, not reasoning. (Partly bounded by the ratified transient-view model: no stored borrows, D10 exclusivity, so a view should not outlive the statement.)
  - **MEASUREMENT THE SCOUT OWES (end-to-end, per the scout rule — build AND run, never source-read):** (1) **the lookup-indirection cost.** Dense adds a *dependent* load on every `contains`/`get` (hash → `indices` → position → `entries`) but probes a compact index array instead of scanning wide key storage — so large keys likely favour dense and small keys (`Set[int]`) likely favour today's. Direction is not assumable; measure both, by key size. (2) Does any real corpus/self-host/dogfood workload do **order-preserving-removal-heavy** work on an ordered map? That is the only profile dense makes worse, and it decides how prominent `StableMap` needs to be. (3) Peak RSS + alloc counts alongside wall-clock, per the perf rule.
  - **NAMED FALLBACK, with a lower bound behind it:** O(1) rank *and* O(1) order-preserving removal is **impossible** — order-preserving removal decrements every subsequent rank, so O(1) rank requires materialised ranks and one removal invalidates O(n); this is dynamic partial sums / list indexing, with a known logarithmic-ish lower bound (Fredman–Saks, cell-probe). Therefore a **Fenwick tree over live flags** — O(log n) rank *and* O(log n) removal, tombstones retained so nothing relocates and address stability survives — is essentially **optimal** for wanting both. Carry it as the named alternative if (2) says remove-heavy ordered workloads are real. Not the default: O(log n) `[]` invites the same "is this cheap?" confusion as O(n).
  - **DOC WRITE-THROUGH owed:** `Dict`/`Set` reference entries gain the cost table and the `.nth()`/`.key_at()` accessors; `std.stablemap` gets its own reference section stating its profile AND that it is **not** ordinally indexable ("Stable" does not convey that on its own); book collections chapter stays four types. D38's no-positional-indexing paragraph needs **no** change under the ratified shape.

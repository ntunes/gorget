- **🆕🐛 [HIGH — check-clean MISCOMPILE, filed 2026-08-10; found by the Fable review, orchestrator-verified] `catch` on a VOID fallible call miscompiles — `gg check` clean, `gg build` fails with a raw C error leaking to the user.** Probe: `void act() throws String: throw "boom"` + `act()! catch (e): print("recovered")` → `gg check` reports "OK: no semantic errors"; `gg build` exits 1 with `vc1.c:3701:11: error: void value not ignored as it ought to be`. Two defects in one: (a) the void success-type cell of `catch` is not handled in lowering; (b) **a C-compile failure of generated code is by definition an ICE and must never surface as a raw `.c:` error** — `language-design.md:120` already promises "errors should point to source, not generated C". Fix (a); for (b) trap C-compiler failure and render an ICE with the *Gorget* span, exit 101. Class-guard (Core #6): have the integration harness grep build stderr for C-compiler ERROR lines (`\.c:` co-occurring with `error:`) on every fixture and fail on sight — NOT bare `\.c:`, which is red-on-arrival everywhere (pass-5 measured: a pre-existing `-Wmissing-field-initializers` leak prints 3 `.c:` WARNING lines on a two-line hello-world; that leak is filed on the A38 track). Axis-complete fixtures per Core #12: success-type × {void, scalar, resource} × {inline, block} × {`catch`, `rethrow`}. ⚡ Rides round E0 (D45). Note D45 pin 4 retires `rethrow` at E3 — this fix still nets BOTH forms while they exist (the rethrow cells become the tombstone-diagnostic cells at E3).

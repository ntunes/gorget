## (A) ⚠ THE SHIPPED C RUNTIME HAS THE DIRECT-CHILD-KILL DEFECT, IN THE PRODUCT

`src/backend/c/runtime/process_spawn_runtime.c` is `include_str!`'d at `src/backend/c/c_runtime.rs:201`, so it is **linked into every binary `gg` produces**. It is a sixth hand-rolled runner, and it is the class verbatim:

| line | what it does |
|---|---|
| `:44` | `pid_t pid = fork();` — the child does `dup2`×3 + `execvp` (`:62`) with **no `setpgid(0, 0)`**, so it is never a group leader |
| `:90` | `gorget_process_kill` → `kill(proc->pid, SIGTERM)` — **direct child only** |
| `:206` | deadline path → `kill(proc->pid, SIGKILL); waitpid(...)` — **direct child only**; a grandchild survives |
| `:132-145` | `gorget_process_wait_timeout` — a `waitpid(WNOHANG)` + `nanosleep(5ms)` poll loop whose own comment says *"or -2 on timeout (**child is NOT killed**)"* |
| `:171` | `timeout_ms < 0` ⇒ `poll_timeout = -1` — blocks forever on `open_fds` |

`src/proc_guard.rs`'s module doc calls the direct-child kill *"the reason this module exists"*, and names a second defect — a grandchild holding the pipe write end with no deadline above it. The shipped runtime has both. ⊕ `src/backend/c/runtime/process_runtime.c:6` is blunter still: `int status = system(cmd);`.

- **DISPOSITION: DEFER, deliberately, with the same argument that applies to `src/main.rs` below.** A deadline or a process-group change in the PRODUCT is user-visible behaviour, not a harness cleanup: `setpgid(0,0)` detaches the child from the terminal's foreground group, so Ctrl-C stops reaching it and `gg` would have to forward the signal. That is a language-surface decision about what `std.process` promises, and it deserves its own scout rather than a reflex.
- **WHAT IS NOT DEFERRABLE, and should be checked first when this is taken:** the `-2 on timeout (child is NOT killed)` contract means a Gorget program that times out a child **leaks it by design**. Decide whether `std.process`'s timeout is a *kill* or a *poll*, then make the C match the decision.

  **MECHANISM.** `src/parser/expr.rs:1360-1364` disambiguates `expr[...]` with `try_parse(|p| { let type_args = p.parse_generic_type_args().ok()?; p.check(&Token::LParen).then_some(type_args) })`. For `fs[0](21)` the type parse FAILS on the integer literal, the combinator backtracks, and the `[0]` survives as an index. For `fs[n](21)` a bare identifier parses perfectly well as a type NAME `n`, the `(` follows, and the parser commits to a generic call `fs[n](21)` — the index read is DELETED from the AST. The typechecker then sees a call to `fs`, which is a Vector, and correctly says it is not a function. The diagnostic is honest about the AST it was given; the AST is wrong.
  `src/parser/tests.rs:1053` (*"Regression: arr[0] should still produce Index, not a generic call"*) shows the reference compiler guards the LITERAL spelling deliberately — the variable spelling was never covered.

It does NOT retire this one, on either lane, because the type parse genuinely SUCCEEDS here: there is no failure to signal. This is the residual ambiguity itself, and it bites the reference compiler identically.
  **SIX QUESTIONS #1 — is this a defect or two positions with different ratified semantics?** `docs/define-gorget/decisions.md` does not settle `expr[ident](args)`. Two coherent answers exist and the choice is a language decision, not an implementation one:
  * **Index wins on a VALUE receiver.** `fs` is a local of Vector type, not a type name, so `fs[n]` cannot be a generic instantiation. Resolve the head first, then disambiguate. This is what a reader expects and it makes the accept set spelling-independent.
  * **Turbofish requires a type-name head.** Restrict the generic-call reading to a head that RESOLVES to a type or a generic function, and make everything else an index. Same outcome here, narrower blast radius on `Name[T](args)`.

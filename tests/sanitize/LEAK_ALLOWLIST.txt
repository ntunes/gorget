# LEAK ALLOWLIST — sanitize sweep (LeakSanitizer)
#
# Resource debt, not soundness. Tolerable in bulk WHILE IT BURNS DOWN; the
# corruption list next door is the one that must stay near zero.
#
# Measured 2026-08-18 by the first corpus-wide sweep: 316 of 1697 fixtures that
# build-and-run leak (18.6%, ~540KB total). That number is not luck — every
# fixture is gated on stdout, and a leak is stdout-invisible while a
# use-after-free usually is not, so the corpus selects FOR leaks and AGAINST
# corruption. This list is the backlog that selection created.
#
# ⚠ SHRINK-ONLY, enforced by `sanitize_allowlists_shrink_only` in tests/lints.rs.
# Removing a name is the normal outcome of a fix. ADDING one means a new leak
# shipped — fix it instead.
#
# FORMAT:  <fixture-stem> TAB <top-frame>*<records>[,<top-frame>*<records>...]
#
# A trailing `+` on a count — `__gorget_spawn_worker*2+` — means "at least this
# many; the COUNT is not pinned". It is for the handful of concurrency fixtures
# whose leak count is genuinely racy (how many workers had leaked by exit).
# Pinning an exact count there would make this gate FLAP, which is the defect it
# exists to remove; the mechanism stays pinned, only the multiplicity does not.
# The sweep's `count-drift` census names the rows that earn the marker — do not
# add one without that evidence.
#
# ⚠ THE TOLERANCE IS PINNED, NOT JUST THE ROW COUNT. `sanitize_allowlists_shrink_only`
# asserts the exact number of rows, of (fixture, class) pairs, of tolerated leak
# RECORDS, and of `*N+` signatures. Widening `*2` to `*99` is one character, it
# leaves the row count untouched, and it re-opens the very case this column
# exists to catch — so it fails the lint, which names the number to move. A
# widening is an admission; make it deliberately or not at all.
#
# The second column is what the fixture is tolerated FOR, and it is checked.
# A bare stem — which is all this file used to carry — tolerated ANY leak in
# that fixture forever: a second, entirely unrelated mechanism appearing inside
# an already-listed fixture was invisible to the gate. 124 of these 313 rows
# exhibit two or more distinct mechanisms, all of which used to hide behind one
# name. The gate now fails on a mechanism the row does not name, AND on one
# more record of a mechanism it does — COUNTS, not a set, because a set cannot
# see a SECOND leak of a class the fixture already exhibits. That case is the
# gate's own positive control (tests/fixtures/sanitize_selftest/).
#
# The key is the leak record's ALLOCATION SITE: the first stack frame that is
# not an allocator interceptor or the runtime's global alloc shim — the same
# "top frame" the big-groups table below has always been written in. The count
# is RECORDS (distinct allocation stacks), never bytes and never objects: those
# move with trip counts and data sizes, and are a lower bound under a
# conservative root set anyway.
#
# ONE ROW PER FIXTURE. The classes are columns, not extra rows, so the ceiling
# in tests/lints.rs keeps counting FIXTURES and stays comparable to every value
# it has ever held. `scripts/sanitize_sweep.sh` reads column 1 only.
#
# To regenerate a row after a deliberate change, take column 4 of the sweep's
# own verdicts.tsv. Widening a row is an admission, not a fix, and the sweep
# prints a "TIGHTEN these rows" advisory whenever a fixture leaks LESS than its
# row admits.
#
# The big groups (top frame -> fixtures), so a fix can retire many rows at once:
#   __gorget_closure_env_alloc   77   every builtin HOF call (map/filter/fold)
#                                     leaks an 8-byte env, UNBOUNDED per call
#   str_alloc_copy              104   7 sub-classes; `parse_int` alone spans 22
#   gorget_shared_new            38   every `shared` local
#   gorget_array_push            38
#   gorget_mutex_new             37
#   gorget_map_clone             16
#   gorget_dict_new              16
#   gorget_channel_new           16
#   CRYPTO_* / OPENSSL_*         15   keygen results the caller never frees
#
